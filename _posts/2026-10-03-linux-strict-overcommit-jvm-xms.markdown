## 문제와 배경

한 대의 리눅스 서버에서 cron으로 Java 배치 여러 개를 돌리는데, 그중 하나가 실행 도중에 죽었습니다. JVM이 남긴 크래시 로그(`hs_err_pid<pid>.log`)의 첫 줄은 이랬습니다.

```text
# Native memory allocation (mmap) failed to map 12288 bytes for ...
```

메모리 부족이라는 뜻인데, 상황을 보면 앞뒤가 맞지 않았습니다.

- 힙은 최대 크기의 일부만 쓰고 있었습니다. 힙 OOM(`java.lang.OutOfMemoryError: Java heap space`)이 아닙니다.
- `free -m`으로 보면 물리 메모리가 기가바이트 단위로 비어 있었습니다.
- 실패한 요청은 고작 12KB였습니다. 스레드 하나를 새로 만들면서 스택 가드 페이지를 잡으려던 것이었습니다.
- 같은 JVM 옵션으로 다른 서버나 개발 PC에서 돌리면 아무 문제가 없었습니다.

원인은 메모리를 세는 방식에 있었습니다. 이 서버는 커널이 메모리를 **실제로 쓴 양**이 아니라 **쓰겠다고 약속한 양**으로 세는 엄격 오버커밋 모드였고, 그 약속의 상당 부분을 각 JVM의 `-Xms`가 차지하고 있었습니다.

## 리눅스는 메모리를 두 장부로 셉니다

프로세스가 `mmap`이나 `malloc`으로 메모리를 요청하면, 커널은 그 순간 물리 페이지를 내주지 않습니다. 주소 공간만 약속해 두고, 프로세스가 실제로 그 페이지에 값을 쓸 때 물리 메모리를 붙입니다. 그래서 메모리 상태는 두 가지로 볼 수 있습니다.

| 관점 | 무엇을 세는가 | 어디서 보는가 |
|---|---|---|
| 실사용 | 실제로 물리 페이지가 붙은 양 | `free`, `AnonPages`, 프로세스의 RSS |
| 커밋 | 프로세스들에게 약속한 쓰기 가능 메모리의 합 | `/proc/meminfo`의 `Committed_AS` |

커밋 쪽이 실사용보다 훨씬 큰 것은 흔한 일입니다. 프로그램은 대개 잡아 둔 만큼 다 쓰지 않기 때문입니다. 이 차이를 커널이 얼마나 허용할지 정하는 설정이 `vm.overcommit_memory`입니다.

| 값 | 동작 |
|---|---|
| `0` (기본) | 휴리스틱으로 판단합니다. 터무니없이 큰 요청만 거절하고, 커밋 총량이 물리 메모리를 넘어도 대체로 허용합니다. |
| `1` | 무조건 허용합니다. |
| `2` (엄격) | 커밋 총량이 `CommitLimit`을 넘는 요청은 크기와 상관없이 거절합니다. |

엄격 모드의 한도는 다음과 같이 계산합니다(huge page 예약분은 빼고 셉니다).

```text
CommitLimit = swap 크기 + 물리 메모리 × (vm.overcommit_ratio / 100)
```

`overcommit_ratio`의 기본값은 50입니다. 예를 들어 RAM 16GB, swap 2GB인 서버라면 한도는 2 + 16 × 0.5 = 10GB입니다. 물리 메모리가 16GB여도 **약속은 10GB까지만** 할 수 있다는 뜻입니다.

엄격 모드의 장점은 분명합니다. 메모리가 정말 모자랄 때 OOM killer가 엉뚱한 프로세스를 죽이는 대신, 할당 요청이 그 자리에서 깔끔하게 실패합니다. 대신 실사용이 한참 낮아도 약속 장부가 차면 아무것도 새로 받을 수 없습니다.

## `-Xms`는 쓰지 않아도 장부에 오릅니다

JVM은 힙을 두 단계로 잡습니다.

1. **예약(reserve)**: `-Xmx` 크기만큼 주소 공간을 `PROT_NONE`으로 잡아 둡니다. 쓰기 불가 매핑이라 커밋 장부에 오르지 않습니다.
2. **커밋(commit)**: 그중 실제로 쓸 수 있게 열어 둘 부분을 읽기·쓰기 가능으로 바꿉니다. 이 순간 커밋 장부에 오릅니다.

시작할 때 커밋하는 크기가 바로 `-Xms`입니다. 객체를 하나도 만들지 않았어도, 물리 페이지가 하나도 붙지 않았어도, `-Xms1g`로 뜬 JVM은 `Committed_AS`에 1GB를 올려 둡니다. GC가 힙을 줄이는 경우에도 `-Xms` 아래로는 내려가지 않으므로, 이 몫은 JVM이 살아 있는 동안 계속 장부에 남습니다.

힙만이 아닙니다. 스레드 스택(`-Xss`, 64비트 기본 1MB)도 스레드를 만들 때 통째로 커밋됩니다. Metaspace, 코드 캐시, GC 자료구조, glibc malloc 아레나도 각자 몫을 더합니다.

이제 배치 JVM 여러 개가 각자 `-Xms1g` 안팎을 지정하고 같은 서버에 떠 있다고 해 봅시다.

```text
CommitLimit                  10.0 GB
상주 프로세스(DB 클라이언트, 에이전트 등)   2.5 GB
배치 JVM 6개 × (힙 1GB + 비힙 약 0.3GB)  7.8 GB
---------------------------------------------
Committed_AS                 10.3 GB  → 한도 초과
실제로 쓰고 있는 메모리            약 4 GB
```

실사용은 4GB 남짓인데 장부는 한도를 넘었습니다. 이 상태에서는 다음 요청이 무엇이든 거절됩니다. 그 요청이 이미 돌고 있던 JVM의 스레드 하나라면 그 JVM이 죽고, 새로 뜨는 JVM의 초기 힙이라면 시작조차 하지 못합니다. 그래서 증상이 힙 OOM이 아니라 네이티브 할당 실패로 나타납니다.

### 대표적인 오류 메시지

```text
# 실행 중에 스레드나 내부 버퍼를 만들다 실패한 경우
# Native memory allocation (mmap) failed to map 12288 bytes for ...
java.lang.OutOfMemoryError: unable to create native thread: possibly out of memory or process/resource limits reached

# 시작하면서 초기 힙을 커밋하다 실패한 경우
OpenJDK 64-Bit Server VM warning: INFO: os::commit_memory(...) failed; error='Not enough space' (errno=12)
```

`errno=12`(`ENOMEM`)인데 `free`에 여유가 있다면 커밋 한도를 먼저 의심해 볼 만합니다.

### 왜 이 서버에서만 재현될까

기본 모드(`0`)인 개발 PC나 다른 서버에서는 커밋 총량이 물리 메모리를 넘어도 커널이 대체로 허용합니다. 같은 JVM 옵션, 같은 배치라도 재현되지 않는 이유입니다. 운영 서버에서만 나는 이상한 장애처럼 보이지만, 실제로는 서버의 커널 설정 하나 때문에 갈리는 경우가 많습니다.

### 방아쇠는 대개 동시 기동입니다

평소에는 한도 아래에서 잘 돌다가 특정 시각에만 터진다면 cron 일정부터 확인해 봅니다. 정각(`0 * * * *`)이나 30분 같은 눈에 띄는 시각에 여러 작업이 몰려 있기 쉽습니다. 앞선 배치가 처리량이 늘어 평소보다 길어지면서 다음 정각까지 넘어가면, 평소에는 겹치지 않던 JVM들이 한꺼번에 떠 있게 됩니다. 각자 잡아 두는 `-Xms`가 더해지면서 장부가 순식간에 찹니다.

## 확인하는 법

### 서버 전체

```bash
# 2이면 엄격 오버커밋입니다
sysctl vm.overcommit_memory vm.overcommit_ratio

# 한도와 현재 약속 총량, 실사용을 함께 봅니다
grep -E '^(CommitLimit|Committed_AS|AnonPages|MemAvailable)' /proc/meminfo

# 약속 총량이 한도의 몇 %인지
awk '/^CommitLimit/{l=$2} /^Committed_AS/{c=$2} END{printf "commit usage: %.1f%%\n", c*100/l}' /proc/meminfo
```

`Committed_AS`가 `CommitLimit`에 가까운데 `AnonPages`가 한참 낮다면, 쓰지 않는 약속이 장부를 채우고 있다는 신호입니다. 순간값이라 놓치기 쉬우므로, 문제가 되는 시각 전후로 1분 간격 정도로 기록해 두면 봉우리를 확인할 수 있습니다.

### 프로세스별

커널은 프로세스별 커밋량을 바로 보여 주지 않습니다. 대략적인 값은 쓰기 가능한 private 매핑의 크기를 더해서 구할 수 있습니다.

```bash
# 각 Java 프로세스의 쓰기 가능 private 매핑 합계(MB) — 커밋량의 근사치입니다
for pid in $(pgrep java); do
  awk -v p="$pid" '$2 ~ /^rw.p$/ {
      split($1, a, "-"); s += strtonum("0x" a[2]) - strtonum("0x" a[1])
    } END { printf "%s\t%.0f MB\n", p, s/1048576 }' "/proc/$pid/maps"
done
```

`strtonum`은 GNU awk 기능이므로 `gawk`가 필요합니다. JVM 쪽에서 더 정확히 보려면 Native Memory Tracking을 켭니다.

```bash
# 실행 옵션에 -XX:NativeMemoryTracking=summary 를 추가한 뒤
jcmd <pid> VM.native_memory summary   # 영역별 reserved / committed
jcmd <pid> GC.heap_info               # 힙의 현재 committed 크기
```

NMT 출력에서 `reserved`는 예약만 한 주소 공간이고, 장부에 오르는 것은 `committed` 쪽입니다.

### 이미 죽은 뒤라면

`hs_err_pid*.log`에서 두 가지를 봅니다.

- 첫 줄이 `Native memory allocation ... failed`인지
- 메모리 절에 찍힌 `/proc/meminfo`에서 `Committed_AS`가 `CommitLimit`에 붙어 있는지

이때 힙 사용량이 `-Xmx`보다 한참 낮다면 **힙을 늘리는 것은 답이 아닙니다.** `-Xms`까지 같이 키우면 오히려 장부를 더 채웁니다.

## 대응과 한계

| 대응 | 효과 | 한계 |
|---|---|---|
| 실행 시각 분산 | 동시에 떠 있는 JVM 수를 줄여 봉우리를 낮춥니다 | 앞선 작업이 길어지면 다시 겹칩니다. 작업이 늘면 다시 몰립니다 |
| `-Xms`를 실사용 수준으로 축소 | 장부에 미리 올리는 몫이 줄어듭니다 | 힙이 커지는 동안 GC가 더 자주 돌 수 있습니다. 실측으로 확인해야 합니다 |
| 스레드 수·`-Xss` 점검 | 스레드당 스택 커밋을 줄입니다 | 풀 크기를 줄이면 처리량에 영향이 있을 수 있습니다 |
| swap 추가 또는 `overcommit_ratio` 상향 | `CommitLimit` 자체가 올라갑니다 | 서버 전역 설정입니다. 실제 메모리가 모자랄 때의 보호막이 얇아집니다 |
| `overcommit_memory`를 `0`으로 | 약속 장부로 거절하지 않습니다 | 진짜 부족 상황에서 깔끔한 할당 실패 대신 OOM killer가 개입합니다 |

### `-Xms`를 줄일 때의 판단

`-Xms`를 `-Xmx`와 같게 두라는 조언은 흔합니다. 힙이 커졌다 줄었다 하는 비용을 없애 지연을 안정시키려는 것이고, 장시간 떠 있는 서비스에서는 타당합니다. 하지만 짧게 돌고 끝나는 배치 여러 개가 한 서버를 나눠 쓰는 환경에서는 그 이점보다 커밋 장부를 미리 채우는 비용이 클 수 있습니다.

줄일 때는 감으로 정하지 말고 실측합니다. GC 로그(`-Xlog:gc`)로 실제 힙 사용 최고치와 GC 빈도를 본 뒤, 최고치보다 약간 큰 값에서 시작합니다. 줄인 뒤에도 같은 입력량으로 처리 속도와 GC 횟수가 비슷한지 비교하면 됩니다. 실제로 배치 하나의 `-Xms`를 절반 이하로 줄였을 때 처리 속도 차이는 측정 오차 수준이었습니다.

### 원리는 남습니다

시각 분산과 `-Xms` 축소는 재발 확률을 낮출 뿐, 원리를 없애지는 못합니다. 다른 작업이 여전히 큰 `-Xms`를 쓰고 있고 같은 시각에 몰리는 일정이 남아 있다면, 같은 고갈은 다른 배치에서 다시 일어날 수 있습니다. 커널 설정을 바꾸는 것이 근본 대책처럼 보이지만, 서버 전체의 동작이 달라지므로 다른 프로세스까지 고려해야 합니다. 그래서 순서는 이렇게 잡는 편이 안전합니다.

1. 서버에 뜨는 JVM들의 `-Xms`와 실행 시각을 표로 모읍니다.
2. 실사용보다 크게 잡힌 `-Xms`부터 줄이고, 동시 기동을 분 단위로 펼칩니다.
3. `Committed_AS / CommitLimit`을 봉우리 시각에 다시 기록해 여유가 생겼는지 확인합니다.
4. 그래도 한도에 붙는다면 그때 swap이나 `overcommit_ratio` 조정을 검토합니다.

한 가지 덧붙이면, 이런 장애는 배치가 조용히 실패한 채 넘어가기 쉽습니다. 크래시가 나도 다음 실행이 정상이면 아무도 모를 수 있으므로, 배치 성공 여부를 종료 코드뿐 아니라 결과물로도 판정해 두는 것이 좋습니다.

## 정리

- `vm.overcommit_memory=2`인 서버에서 커널은 실제 사용량이 아니라 **약속한 총량(`Committed_AS`)** 으로 할당을 거절합니다.
- JVM의 `-Xms`는 쓰지 않아도 그 크기만큼 약속 장부에 오르고, JVM이 살아 있는 동안 내려오지 않습니다.
- 그래서 `free`에는 여유가 있는데 새 스레드나 새 JVM이 `errno=12`로 실패합니다. 증상은 힙 OOM이 아니라 네이티브 할당 실패입니다.
- 확인은 `sysctl vm.overcommit_memory`와 `/proc/meminfo`의 `CommitLimit`·`Committed_AS`부터 합니다.
- 대응은 실행 시각 분산과 `-Xms` 축소가 먼저이고, 커널 설정 변경은 서버 전체 영향을 따져 본 뒤에 합니다. 어느 쪽도 원리 자체를 없애지는 못합니다.

## 문제와 배경

앞의 세 편에서 만든 구조를 다시 요약하면 이렇습니다. 폴러가 cron으로 Jira를 주기적으로 조회하고, 처리할 이슈가 있으면 `claude -p`로 헤드리스 세션을 띄웁니다. 세션은 한 번에 한 단계(분석, 설계, 구현, 검증)만 진행하고 Jira 댓글로 사람의 확인을 요청한 뒤 멈춥니다. 사람이 승인하거나 댓글을 달면 다음 폴에서 세션이 이어집니다.

이 구조가 실제로 돌기 시작하자 질문이 바뀌었습니다. 처음에는 「돌아가는가」였는데, 운영을 시작하고 나서는 다음 셋이 남았습니다.

- 한 번 실행할 때 얼마가 들고, 그 숫자를 믿어도 되는가
- 리포트에 찍힌 숫자가 틀렸을 때 그것을 누가 알아채는가
- 에이전트가 「검증했다」고 말할 때 실제로 무엇을 확인한 것인가

이 글은 이 세 질문에 대한 운영 기록입니다. 금액, 실행 횟수, 처리 건수 같은 운영 수치는 싣지 않습니다. 수식에 들어가는 숫자는 설명을 위해 만든 예시 값입니다.

## 실행당 비용을 재는 원장

### 원장 한 줄의 구조

`claude -p --output-format json`으로 실행하면 세션이 끝날 때 결과 JSON에 비용과 토큰 사용량이 함께 나옵니다. 폴러는 세션이 끝나면 이 값을 읽어 JSONL 파일에 한 줄씩 붙입니다. 이것을 이 글에서는 원장이라고 부릅니다.

```python
import json, time
from pathlib import Path

LEDGER = Path.home() / "issue-agent" / "usage.jsonl"

def append_usage(issue_key: str, log_file: Path, outcome: str, exit_code: int) -> None:
    """세션 로그의 마지막 JSON 결과를 읽어 원장에 한 줄 붙입니다."""
    try:
        result = json.loads(log_file.read_text().strip().splitlines()[-1])
    except (OSError, ValueError, IndexError):
        return  # JSON이 아니면 API 호출이 없던 실행이므로 행을 만들지 않습니다
    usage = result.get("usage", {})
    row = {
        "ts": time.strftime("%Y-%m-%dT%H:%M:%S"),
        "issue": issue_key,
        "log_file": str(log_file),          # 중복 행을 접는 기준
        "session_id": result.get("session_id"),
        "cost_usd": result.get("total_cost_usd", 0),
        "num_turns": result.get("num_turns", 0),
        "cache_read": usage.get("cache_read_input_tokens", 0),
        "cache_write": usage.get("cache_creation_input_tokens", 0),
        "output": usage.get("output_tokens", 0),
        "outcome": outcome,                  # success / failed / quota ...
        "exit_code": exit_code,
    }
    with LEDGER.open("a") as f:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
```

구조는 단순한데, 운영하면서 이 원장에서 결함이 여러 번 나왔습니다. 공통점은 모두 예외 없이 조용히 틀렸다는 것입니다.

### 결함 1: 실패한 세션이 원장에 없었습니다

처음 구현에서 적재 호출은 「종료 코드 0이고 상태가 완료」인 분기 안에만 있었습니다.

```python
if success:
    append_usage(...)   # 여기에만 있었습니다
    ...
else:
    ...                 # 실패 분기에는 적재가 없었습니다
```

실패한 세션도 토큰을 씁니다. 몇십 턴을 돌다가 사용 한도에 걸려 끝난 세션이면 적지 않은 양을 씁니다. 그런데 원장에는 그 행이 없으니, 실패가 늘수록 총액이 조용히 작아집니다. 원장의 실체는 「비용 원장」이 아니라 「성공 비용 원장」이었습니다.

고친 방법은 적재를 분기 밖으로 빼고 `outcome` 필드를 함께 남기는 것입니다. 분기 밖으로 빼기만 하면 원장만 보고는 성공과 실패를 가를 수 없어서, 성공률을 원장에서 계산할 수 없게 됩니다. 반대로 `outcome`이 있으면 같은 파일에서 비용과 성공률을 함께 볼 수 있습니다.

이때 몇 가지 경로는 일부러 적재하지 않습니다.

| 경로 | 처리 | 이유 |
|---|---|---|
| 세션 이어받기가 만료돼 바로 끝난 실행 | 행 없음 | API를 호출하지 않아 로그가 JSON이 아닙니다. 파싱 실패 시 반환하는 구조가 자동으로 거릅니다 |
| 다른 실행이 이슈를 잡고 있어 바로 물러난 실행 | 행 없음 | 정산 함수에 들어오기 전에 반환합니다 |
| 시뮬레이션(실제 CLI 미호출) | 명시적으로 제외 | 비용이 없고, 다른 판정도 같은 플래그로 이미 제외합니다 |
| 1턴 만에 끝난 실패 | 행 있음, 금액 0에 가까움 | 실행했다는 사실은 맞으므로 분모에 들어가는 편이 정확합니다 |

이 수정은 적재 경로를 넓히는 변경이라 테스트 격리가 특히 중요했습니다. 원장, 상태 파일, 로그 경로를 모두 환경 변수로 임시 경로에 돌리지 않으면 테스트가 실제 원장에 행을 씁니다. 실제로 폴러 모듈을 불러오는 단위 테스트가 실제 로그 핸들러를 물려받아 테스트용 이슈 키로 된 유령 행을 남긴 적이 있습니다.

### 결함 2: 세션은 끝났는데 정산이 돌지 않은 실행

실패 분기 문제와는 별개로, 세션 자체는 정상 종료했는데 폴러의 정산 단계가 돌지 않아 행이 빠진 실행도 있었습니다. 폴러 로그에는 발사 기록만 있고 완료나 실패 기록이 없었으며, CLI 실행 로그에는 종료 기록이 있었습니다.

원인을 고치기 전에 먼저 한 일은 「빠졌다는 사실이 어디에도 표시되지 않는」 상태를 없애는 것이었습니다. 비용 분석기가 원장, 실행 스크립트 디렉터리, 세션 로그를 서로 대조해 원장에 없는 실행을 찾아내고, 그 비용을 회수해 총액에 넣고, 몇 건을 회수했는지를 리포트에 표시합니다.

그런데 이 회수 지표도 처음에는 틀렸습니다. 리포트가 생성되는 시각에 아직 돌고 있는 세션은 당연히 원장에 행이 없습니다. 이것을 미적재로 세면 건수가 부풀고 비용이 하루 앞당겨 잡힙니다. 지금은 폴러 로그에 완료나 실패 마커가 있는 실행만 미적재로 셉니다.

### 결함 3: 이중 계산과 누적이 줄어드는 현상

원장이 커지면서 일일 리포트와 주간 리포트에 이슈별 비용을 붙였는데, 여기서 같은 계열의 결함이 연달아 나왔습니다.

- **같은 이름, 다른 창**: 일일 리포트의 `cost_by_issue`는 그날 하루치, 주간 리포트의 같은 키는 그 주 전체입니다. 두 파일을 이어 붙여 집계하면 같은 비용이 두 번 더해집니다.
- **잘못된 접기 기준**: 원장에 같은 실행이 두 번 적힌 행을 접으려고 `session_id`를 기준으로 쓰면, `--resume`으로 이어진 여러 실행이 같은 세션 ID를 공유하므로 서로 다른 실행이 한 행으로 삼켜집니다. 접기 기준은 실행 단위로 고유한 로그 파일 경로여야 했습니다.
- **누적이 줄어듦**: 회수분은 그 날짜 창의 로그에서만 계산되는 값입니다. 이것을 누적 합계에 더하면, 다음 날 창이 바뀌면서 그 값이 빠지고 누적이 오히려 감소합니다.
- **전 기간 스캔**: 어떤 판정 함수가 조회 기간을 보지 않고 원장 전체를 훑었습니다. 그러면 특정 날의 사고 하나가 그 뒤 모든 날짜의 리포트에 경고로 실립니다. 원장은 지우지 않으므로 이 경고는 영원히 매일 뜹니다.
- **주간 창의 빈틈**: 주간 리포트가 월요일부터 금요일 발송 시각까지만 집계해서, 금요일 저녁과 주말의 실행은 어느 리포트에도 잡히지 않았습니다.

다섯 가지 모두 원인이 같습니다. 값에 「어느 구간의 값인가」가 적혀 있지 않았습니다. 원장 한 줄에는 시각과 이슈와 금액이 있지만, 그것을 어느 창으로 잘라 봤는지는 함수 인자에만 있습니다. 집계 결과가 함수 밖으로 나가는 순간 창 정보가 사라집니다.

그래서 집계 결과에 창을 함께 싣도록 바꿨습니다.

```json
{
  "cost_by_issue": {"issue-a": 1.23, "issue-b": 0.45},
  "cost_window": {"since": "2026-08-24T00:00", "until": "2026-08-25T00:00"}
}
```

리포트 창도 「발송 시각까지」가 아니라 완결된 단위로 옮겼습니다. 일일 리포트는 다음 날 아침에 전날 하루치를, 주간 리포트는 월요일 아침에 지난주 월요일부터 일요일까지를 보냅니다. 발송 시각이 창 안에 있으면 그 뒤의 활동은 늘 잘립니다.

### 새 집계 코드를 쓰기 전에 확인하는 것

같은 모양의 결함이 반복해서 들어와서 결국 점검표를 만들었습니다. 새 규칙을 만든 것이 아니라 실제로 난 결함에서만 뽑은 것입니다.

1. 전 기간을 훑어 판정하고 그 결과를 그날 리포트에 싣는가. 그렇다면 창 필터가 있는가.
2. 결과에 판정 창을 함께 담았는가.
3. 그 창에서만 나오는 값을 누적에 더하고 있지 않은가. 누적은 영구 보존되는 원천에서만 만듭니다.
4. 같은 값을 두 곳에서 따로 계산하고 있지 않은가. 본문은 반올림한 총액을, 첨부는 원값을 더해 한 푼 차이가 난 적이 있습니다. 항등 검사를 붙인다면 반올림한 뒤의 값도 대조합니다.
5. 조기 반환이 다른 사실까지 숨기지 않는가. 「활동이 없었다」와 「돈이 들지 않았다」는 다른 사실입니다. 활동이 없는 날 리포트 본문이 일찍 반환하면서 그날의 비용까지 사라진 적이 있습니다.
6. 회귀 테스트가 여러 날짜를 건너가며 보는가. 하루짜리 검사로는 창 계열 결함을 하나도 잡지 못합니다.
7. 격리 검증이라면 산출물 경로를 전부 옮겼는가. 상태 파일과 로그만 옮기고 실행 로그 디렉터리를 그대로 두면, 격리했다고 믿는 채로 실제 경로를 오염시킵니다. 지금은 폴러가 이 조합을 거부하고 종료합니다.

## 비용은 어디에서 나오는가

### 실행 한 번의 비용을 세 항으로 나눕니다

원장의 토큰 필드를 성분별로 나눠 보면 비용 구조가 보입니다. 실행 한 번의 비용은 대략 다음과 같습니다.

```text
실행 1회 비용 ≈ C × T × p_read       (캐시 읽기: 턴마다 맥락 전체를 다시 읽음)
             + C × p_write           (캐시 쓰기: 실행 경계에서 맥락을 다시 저장, 하한 근사)
             + O × p_out             (출력)

C = 살아 있는 맥락 크기(토큰), T = 턴 수, O = 출력 토큰
```

예시 값으로 계산해 보면 감이 옵니다. 맥락 20만 토큰, 30턴이면 캐시 읽기가 600만 토큰입니다. 출력이 1만 토큰이라면 캐시 읽기 단가가 출력 단가보다 훨씬 싸더라도 양이 압도적이라 캐시 쪽이 비용의 대부분을 차지합니다. 실측도 같은 모양이었습니다. 비용 대부분이 캐시 읽기와 쓰기였고, 세션이 실제로 만들어 낸 산출물인 출력 토큰은 작은 몫이었습니다.

이 분해에서 곧바로 나오는 결론이 있습니다.

- **손댈 수 있는 항은 맥락 크기, 턴 수, 실행 횟수입니다.**
- 「답을 짧게 쓰라」고 지시하거나 `--effort`를 낮추는 것은 출력 항만 건드립니다. 출력 항이 작으면 절감의 상한도 작습니다.
- 모델을 바꾸는 것은 모든 항의 단가에 곱해지는 큰 지렛대입니다. 다만 단계별 품질 요구가 달라서, 이 에이전트에서는 비용 설계와 분리해 따로 판단하기로 했습니다. 모델 라우팅을 쓴다면 「어느 단계가 어느 정도의 모델을 견디는가」를 먼저 재야 하고, 그 측정 없이 내리면 재시도와 되돌림이 늘어 오히려 비쌉니다.

### `--resume`은 맥락을 이어받지만 캐시는 이어받지 못했습니다

메시지 단위로 캐시 쓰기를 보면, 큰 쓰기가 거의 전부 실행 경계에 몰려 있었습니다. 직전 메시지와의 간격이 폴러의 재발사 주기와 일치하는 메시지들입니다. 그 메시지에서 캐시 읽기는 아주 작았습니다. 즉 `--resume`으로 세션을 이어받으면 대화 맥락은 그대로 들어오지만, 그 맥락 전체가 실행마다 캐시에 다시 쓰였습니다.

재발사 간격은 1시간 캐시 TTL 안에 들어오는 경우가 많았기 때문에 「TTL이 만료돼서 다시 썼다」는 설명은 맞지 않았습니다. 이 구분이 중요한 이유는 처방이 정반대이기 때문입니다. TTL 만료가 원인이면 재발사 간격을 좁히면 됩니다. 이어받기 구조가 원인이면 간격을 좁혀도 효과가 없고 실행 횟수만 늘어 손해입니다. 이것은 공식 문서의 계약이 아니라 이 환경의 세션 로그에서 직접 관찰한 결과입니다.

결과적으로 체인(같은 이슈를 `--resume`으로 이어 가는 실행 묶음)이 길어질수록 맥락이 쌓이고, 턴당 단가가 체인 깊이에 따라 계단식으로 올라갔습니다. 새로 시작한 세션의 턴당 단가가 가장 쌌고, 깊은 체인일수록 크게 비쌌습니다.

### 체인 은퇴 정책

그래서 일정 조건에서 `--resume`을 끊고 새 세션으로 갈아타는 정책을 넣었습니다. 맥락은 대화 대신 이슈별 인계 파일로 넘깁니다. 이 정책은 새 메커니즘이 아니었습니다. 세션 기록이 보존 기간을 넘겨 사라지면 폴러가 새 세션으로 시작하는 경로가 이미 있었고, 그 경로를 탄 직후의 세션들이 턴은 더 많이 쓰고도 비용은 더 적게 쓴 것을 확인했습니다. 우연히 일어나던 리셋을 정책으로 부르는 것입니다.

처음 판정식은 이렇습니다.

```python
def should_retire_chain(state, now) -> bool:
    if state.is_closing_stage:            # 종결 단계는 원래 이어받지 않습니다
        return False
    if not state.last_session_ok:         # 직전이 실패면 인계 파일이 갱신되지 않았을 수 있습니다
        return False
    if now - state.last_session_ended_at <= timedelta(minutes=55):
        return False                      # 캐시가 아직 살아 있으면 끊는 것이 손해입니다
    if state.chain_runs < 3:              # chain_runs = 이 체인에서 성공한 실행 수(생성 세션 = 1)
        return False
    return True
```

임계값은 손익분기로 정했습니다. 리셋으로 얻는 것은 줄어든 맥락만큼의 캐시 쓰기와 캐시 읽기이고, 잃는 것은 인계 파일을 읽는 비용과 새 세션이 이미 기각한 접근을 다시 탐색하는 위험입니다.

```text
리셋 이득 S(k) ≈ ΔC(k) × (p_write + T(k) × p_read)
  ΔC(k) = k번째 실행의 맥락 크기 − 새 세션의 맥락 크기
리셋 손실 ≈ 인계 파일 읽기 + 재탐색 위험 R
→ S(k)가 R의 최악값보다 넉넉히 큰 첫 k를 임계로 둡니다
```

설계를 검토하면서 몇 가지를 고쳤습니다.

- **`chain_runs`의 정의**: 처음 문서에는 「재개 횟수」와 「실행 횟수」가 섞여 있었습니다. 한 칸 차이인데 실제 임계가 하나 밀리면서 절감 추정이 크게 달라졌습니다. 정의를 하나로 고정하고 테스트 기대값도 거기에 맞췄습니다.
- **인계 파일 갱신 확인은 소프트 가드로**: 「인계 파일이 직전 세션 이후 갱신됐을 것」을 필수 조건으로 두면, 인계 파일을 갱신하지 않는 세션은 영원히 은퇴하지 않습니다. 그런 세션일수록 맥락이 크고 비쌉니다. 가장 비싼 경우만 골라 면제하는 셈이라, 한 번만 보류하고 경고를 남기고 연속으로 보류되면 강제로 은퇴시킵니다.
- **조용히 사라질 수 있는 입력은 판정에 바로 쓰지 않음**: 이론상 비용을 결정하는 변수는 회차가 아니라 맥락 크기입니다. 그래도 처음에는 맥락 크기를 판정 입력에서 뺐습니다. 사용량 파싱은 실패해도 조용히 넘어가도록 만들어져 있어서, 그 값이 사라지면 판정이 소리 없이 「은퇴가 영원히 걸리지 않는」 상태로 퇴행합니다. 먼저 기록만 하고 데이터를 본 뒤에 판정에 넣기로 했습니다.

### 활발한 체인만 정확히 면제되는 빈틈

정책을 켜고 운영해 보니 빈틈이 드러났습니다. 맥락이 커지는 원인은 자주 트리거되는 것인데, 자주 트리거되면 유휴 시간이 생기지 않아 은퇴 조건을 만족하지 못합니다. 사람과 댓글을 활발히 주고받는 이슈 하나의 체인이 세션마다 컨텍스트 창을 꾸준히 더 채워 가며 창 한계 쪽으로 다가갔습니다. 창 한계에 닿으면 자동 압축이 걸리고, 그때 무엇이 버려지는지는 에이전트가 통제하지 못합니다.

여기에 세 겹을 더했습니다.

1. **맥락 사용률 탈출구**: 유휴 조건과 별도로, 직전 실행의 컨텍스트 창 사용률이 임계를 넘으면 은퇴시킵니다. 사용률 값이 없으면 기존 유휴 판정으로 돌아갑니다. 앞에서 판정에서 뺐던 입력을 되살리되, 값이 사라졌을 때의 동작을 명시하는 형태로 넣었습니다.
2. **인계 파일 구조 전환**: 활발한 이슈의 인계 파일을 열어 보니 시간순으로 쌓인 항해일지였습니다. 「지금 무엇이 참인가」를 알려면 수십 개 섹션을 훑어 스스로 재구성해야 했습니다. 현재 상태, 확정된 결정, 기각한 접근, 남은 일 순서로 다시 쓰는 양식으로 바꿨습니다. 인계 파일 자체는 맥락의 작은 일부였으므로 이 변경의 목적은 맥락 축소가 아니라 승계 품질입니다.
3. **은퇴 전 인계 파일 검증**: 은퇴 직전에 인계 파일이 새 양식을 따르는지 확인하고, 아니면 한 번 보류합니다.

은퇴가 처음 발동했을 때 턴당 맥락이 크게 줄어든 것을 확인했지만, 표본이 하나라 효과를 수치로 일반화하지는 않습니다. 은퇴는 수위를 영구히 낮추는 장치가 아니라 주기적으로 되돌리는 장치라는 점도 기억해야 합니다. 새 체인도 다시 자랍니다. 이 정책의 가치는 평균 절감보다 최악값을 유계로 만드는 데 있습니다.

### 맥락 바깥의 낭비

하루치 실행을 전수로 분류해 보니, 전진 없이 소모된 실행에는 맥락과 무관한 유형이 따로 있었습니다.

| 유형 | 구조 | 대응 |
|---|---|---|
| 동시 발사로 한도 소진 | 사용 한도가 계정 단위라 한 폴에서 여러 세션을 띄우면 처리량은 그대로이고 소진만 빨라집니다. 수십 턴을 돌다 한도에 걸린 세션은 산출물 없이 끝납니다 | 한 폴의 동시 발사 수를 제한하고, 한도가 회복될 때까지 발사를 보류합니다. 보류 판단 자체는 이미 있었고 발사 시점에 적용되지 않았을 뿐이었습니다 |
| 권한 거부의 늦은 발견 | 호스트 권한이 막는 작업을 세션이 한참 진행한 뒤에 발견하고 되돌립니다 | 발사 전에 요청된 작업의 종류를 허용 범위와 대조합니다 |
| 자기 재발사 | 에이전트가 건 상태 전이를 폴러가 새 이벤트로 보고 다시 발사합니다 | 전이 주체와 최신 댓글 작성자를 함께 보고 거릅니다 |
| 가짜 성공 | 1턴만 돌고 아무것도 하지 않은 실행이 완료로 기록됩니다 | 턴 수 임계가 아니라 「도구 호출 0건이고 Jira 쓰기 0건인가」로 판정합니다 |

가짜 성공의 판정 기준을 턴 수로 잡지 않은 이유가 있습니다. 턴 수 임계를 올리면 정당하게 짧게 끝난 실행, 예를 들어 「변경이 필요 없습니다」라고 판정하고 끝낸 실행을 실패로 오분류합니다. 증거 기반 조건이어야 합니다.

캐시 TTL을 5분으로 낮추는 안도 검토했습니다. 재발사 간격을 보면 1시간 TTL의 이득이 거의 없어 보였지만 권고를 보류했습니다. 헤드리스 CLI에서 TTL을 실제로 조작할 수 있는지 확인하지 못했고, 바꾼 뒤의 실측 대조도 없었기 때문입니다. 확인하지 못한 것을 근거로 설정을 바꾸지 않았습니다.

### 가장 큰 덩어리는 사람과 주고받는 구간이었습니다

실행을 트리거 종류별로 나눠 보니, 비용의 가장 큰 덩어리는 단계 게이트를 넘기는 실행이 아니라 게이트 사이에서 사람 댓글에 응답하는 실행이었습니다. 사람이 단계 중간에 짧은 지시를 여러 번 나눠 달면 그때마다 세션이 맥락 전체를 다시 읽고 다시 씁니다.

이 항은 코드로 줄이기 어렵습니다. 그래서 두 방향을 함께 둡니다.

- **사람 쪽**: 지시를 한 댓글에 모아 달라는 작성 가이드를 만들었습니다. 무엇을 바꿀지, 바꾸지 않을 것은 무엇인지, 완료를 어떻게 확인할지를 한 번에 적으면 왕복이 줄어듭니다.
- **코드 쪽**: 한 이슈의 왕복이 상한을 넘으면 에이전트가 더 진행하지 않고 사람에게 넘기는 안을 결정 항목으로 올렸습니다.

## 조용히 틀리는 지표

### 0은 두 가지를 뜻합니다

깨진 측정은 대개 예외를 던지지 않습니다. 찾는 문자열이 없으면 0건이고, 읽을 파일이 없으면 빈 집합입니다. 리포트에 찍힌 0은 「일이 없었다」와 「세는 장치가 망가졌다」를 동시에 뜻하는데, 사람은 그것을 앞의 뜻으로 읽습니다. 고장이 실적으로 보고되고, 아무도 놀라지 않으니 오래 갑니다.

이 에이전트에서 실제로 난 경우는 세 가지였습니다.

- 폴러가 세션 실행 방식을 동기에서 비동기로 바꾸면서 로그 문구도 바뀌었는데, 다이제스트 스크립트는 옛 문구를 세고 있었습니다. 주간 리포트는 오랫동안 「트리거 0회」를 보고했고, 일일 리포트는 「활동 0건이면 보내지 않는다」는 가드에 걸려 아예 발송되지 않았습니다.
- 원장 적재 누락으로 총액이 조용히 작아졌습니다(앞 절의 결함 1, 2).
- 집계 블록이 죽어도 스크립트의 종료 코드가 0이라 cron이 성공으로 봤습니다.

첫째와 셋째는 [실패했는데 성공으로 끝나는 시스템 — 종료 코드 0과 fail-open 게이트](/blog/2026/10/07/silent-failure-exit-code-fail-open.html)에서 로그 문구가 계약이 되는 문제와 종료 코드 판정을 자세히 다뤘으므로 여기서는 반복하지 않습니다. 이 글에서는 지표 쪽에 넣은 방어만 정리합니다.

세 경우 모두 관측 대상과 관측 장치가 따로 진화해서 생겼습니다. 폴러는 문구를 바꿨는데 다이제스트는 바꾸지 않았고, 폴러는 적재에 실패했는데 집계기는 원장만 믿었고, 집계기는 죽었는데 호출자는 종료 코드만 봤습니다. 그래서 방어의 방향도 「더 정확히 세자」가 아니라 「어긋났는지 스스로 묻자」로 잡았습니다.

### 정합성 배너: 조용한 0을 금지합니다

리포트가 스스로를 의심하고, 의심스러우면 본문 맨 위에 경고를 답니다.

```bash
banner=""
if [ "$log_lines_read" -eq 0 ]; then
  banner="지표 수집 이상: 로그를 읽지 못했습니다. 아래 수치는 모두 무효입니다."
elif [ "$launched" -gt 0 ] && [ $((completed + failed)) -eq 0 ]; then
  banner="지표 수집 이상: 발사 기록은 있는데 종료 기록이 없습니다. 종료 마커 불일치를 의심합니다."
elif [ "$ledger_rows" -gt 0 ] && [ "$completed" -eq 0 ]; then
  banner="지표 수집 이상: 원장에는 실행이 있는데 로그 완료가 0입니다. 마커 불일치를 의심합니다."
elif [ "$cost_main" != "$cost_check" ]; then
  banner="지표 수집 이상: 비용 집계 두 경로가 다릅니다. 비용 수치를 신뢰하지 마십시오."
fi
```

첫 조건이 가장 중요합니다. 로그를 한 줄도 읽지 못하면 나머지 조건이 모두 성립하지 않으므로, 이 조건이 없으면 「경고 없는 전부 0 리포트」가 나갑니다. 그것이 정확히 처음 사고의 모양입니다.

배너 문구에는 관측 사실만 씁니다. 원장 적재 결함을 고친 뒤 「적재 결함 재발 의심」이라는 이름으로 경고를 만들었는데, 이 경고가 매일 뜨기 시작했습니다. 조사해 보니 재발이 아니라 앞에서 말한 창 필터 누락과 격리 오염 때문이었습니다. 경고가 결함 이름을 직접 부르니 조사가 엉뚱한 곳에서 시작됐습니다. 원인 판정은 사람에게 넘기고 경고는 「무엇이 무엇과 어긋났는가」만 말하게 했습니다.

### 이중 경로 교차 검증

비용은 두 경로로 따로 계산해 대조합니다.

- **주 경로**: 원장, 실행 스크립트, 세션 로그를 대조해 미적재분까지 회수하는 분석기입니다. 읽는 파일이 많아 정확하지만 실패할 여지도 넓습니다.
- **대조 경로**: 원장 하나만 읽어 합산하는 짧은 코드입니다. 회수는 못 하지만 실패 경로가 짧습니다.

두 값이 어긋나면 배너가 뜹니다. 주 경로가 죽으면 대조 경로 단독으로 축소 집계하고, 그 사실도 배너와 집계 경로 표시로 알립니다. 짧은 쪽을 대조군으로 남겨 두는 것이 요점입니다.

### 실패는 막고, 저하는 알립니다

- 지표 집계 자체가 실패하면 리포트를 보내지 않고 cron 로그에 실패를 남깁니다.
- 비용 분석기만 실패하면 리포트는 보내고 배너를 답니다.

비용 하나 때문에 나머지 지표를 모두 버리면 「리포트가 오랫동안 발송되지 않았다」는 사고와 같은 종류의 손실이 생깁니다. 전부 막거나 전부 통과시키는 대신, 무엇을 잃었는지 말하면서 통과시킵니다.

마커 검사도 회귀 테스트로 넣었습니다. 집계가 세는 마커를 폴러 소스와 최근 며칠의 실제 로그 양쪽에 대조합니다. 한쪽만으로는 잡히지 않습니다. 소스만 보면 진단용 경로에 남아 있는 옛 문구 때문에 통과하고, 로그 전체를 보면 문구가 바뀌기 전의 기록에 속습니다. 마커 패턴에는 실제 이슈 키 형식의 앵커를 넣어서 테스트용 키로 남은 로그가 실적으로 세지지 않게 했습니다. 이슈 키 패턴은 정규식에 박지 않고 설정에서 읽습니다. 다른 프로젝트 키가 섞이는 순간 마커, 집계, 이슈 추출이 동시에 0이 되기 때문입니다.

## 자동 검증의 한계와 배포 경계

### 에이전트가 할 수 있는 검증은 환경이 정합니다

이 에이전트가 다루는 코드는 Java와 JSP로 된 레거시 웹 애플리케이션이었습니다. 운영 초기에는 Mac mini에 그 프로젝트가 요구하는 JDK가 없어 빌드가 되지 않았습니다. 그러면 「구현 및 자체 검증」 단계의 실행 근거는 매번 사람에게 넘어갑니다. 이것은 설계한 경계가 아니라 환경이 비어서 생긴 경계였습니다.

빌드가 되지 않는 동안에도 근거가 되는 정적 검증은 있었습니다.

| 검증 | 방법 | 잡는 것 |
|---|---|---|
| 의도 반영 | `git diff` 전체를 확정된 설계와 항목별로 대조 | 설계 이탈, 누락, 초과 구현 |
| 문법 | 바뀐 Java 파일만 단독 컴파일하고 오류를 종류별로 분류 | 문법 오류 |
| 템플릿 구조 | 바뀐 블록만 떼어 태그 짝과 XML 정형성을 검사 | 닫히지 않은 태그, 중첩 오류 |
| 메시지 키 | 쓴 메시지 키가 모든 언어 번들에 있는지 대조 | 빈 문구, 키가 그대로 노출되는 화면 |

단독 컴파일은 클래스패스가 없으니 반드시 오류를 많이 냅니다. 오류 개수로 판정하면 늘 실패로 읽히므로, 심볼을 찾지 못한다는 계열 외의 오류가 0건인지를 봐야 근거가 됩니다.

나중에 JDK를 맞추고 의존성 캐시를 갖춰 컴파일 검증은 에이전트가 직접 하게 됐습니다. 그래도 화면 검증은 여전히 못 합니다. 서버를 띄우려면 사내망 접속, 애플리케이션 서버, 메모리가 모두 필요하기 때문입니다. 빌드가 된다고 화면이 검증되는 것은 아닙니다.

### 권한은 세 층이 같은 문자열을 공유해야 열립니다

에이전트에게 개발 브랜치 반영을 맡기기로 한 뒤에도 반영은 여러 번 막혔습니다. 원인은 층마다 달랐습니다.

- 이전 사이클이 만든 임시 워크트리가 개발 브랜치를 체크아웃한 채 남아 있어, 다른 워크트리에서 그 브랜치를 쓸 수 없었습니다. 사이클 종료 시 임시 워크트리를 회수하도록 바꿨습니다.
- 호스트 `settings.json`의 deny 규칙이 프롬프트의 지시보다 우선했습니다.
- 허용 규칙에는 스크립트 실행 형태가 등록돼 있었는데, 계약 문서는 그 앞에 `cd 저장소루트 &&`를 붙여 실행하라고 지시했습니다. 확인해 보니 막은 것은 문자열 불일치가 아니라 세션 작업 디렉터리 바깥으로 나가는 `cd`였습니다. 허용 규칙에 `cd`를 넣는 방식으로는 풀리지 않아서, 스크립트가 저장소 루트를 스스로 찾게 고쳐 `cd`를 없앴습니다.

교훈은 계약 문서, 스크립트, 호스트 권한 세 층이 같은 명령 형태를 공유해야 한다는 것입니다. 계약만 고치면 호스트가 막고, 권한만 열면 형태가 어긋나서 다시 막힙니다. 그리고 막혔을 때 에이전트가 명령 형태를 바꿔 재시도하게 두면 안 됩니다. 가드를 무력화할 뿐 아니라 이런 층간 불일치를 드러나지 않게 덮습니다. 이 에이전트는 막히면 중단하고 보고합니다. 권한 규칙이 어떻게 매칭되는지는 [Claude Code 훅을 직접 써 보며 부딪힌 함정 6가지](/blog/2026/09/30/claude-code-hook-pitfalls.html)에서 다룬 훅 동작과 함께 보면 좋습니다.

### 경계를 어디에 둘 것인가

운영하며 정리된 경계는 다음과 같습니다.

| 단계 | 에이전트 | 사람 |
|---|---|---|
| 원인 분석, 계획, 설계 | 수행 | 승인 |
| 구현, 정적 검증, 컴파일, 설계 대조 | 수행 | 결과 확인 |
| 개발 브랜치 병합과 개발 서버 빌드 트리거(Jenkins API) | 수행 | 배포 결과 확인 |
| 개발 서버 화면 검증 | 못 함 | 요청자가 확인 |
| 검수 브랜치 PR, 운영 배포 | 하지 않음(정책) | 수행 |

기준은 「되돌리기 쉬운가」와 「에이전트가 판정 근거를 가질 수 있는가」 두 가지였습니다. 개발 서버는 여러 사람이 공유하지만 되돌리기 쉽고, 빌드 성공 여부를 에이전트가 API로 확인할 수 있습니다. 화면이 요구를 충족했는지는 에이전트가 근거를 가질 수 없습니다. 운영 반영은 되돌리기 어렵습니다.

이 경계에서 자주 헷갈린 것이 하나 있습니다. 개발자가 「개발 서버에 배포했습니다」라고 댓글을 달면 승인처럼 읽히지만, 그것은 배포 실행 보고이지 화면 검증 결과가 아닙니다. 이 댓글에 상태를 전이하면 아무도 화면을 보지 않은 채 다음 단계로 넘어갑니다. 에이전트는 상태를 유지하고 요청자에게 확인을 요청합니다. 같은 댓글에 판정과 무관한 유용한 정보(예를 들어 배포 일정)가 섞여 오면, 판정은 보류하되 그 정보는 바로 산출물에 반영합니다. 사람이 같은 말을 두 번 하지 않게 됩니다.

그리고 못 한 것을 못 했다고 쓰는 편이 빠릅니다. 빌드와 화면 확인을 하지 못했다고 그대로 알리자 개발자가 곧바로 개발 서버 배포를 지시해 다음 할 일이 한 번에 정해진 적이 있습니다. 추정으로 통과시켰다면 문제는 더 늦게 드러났을 것입니다.

## 이미 구현된 요구를 받았을 때

### 만들지 않는 것이 지시를 따르는 것입니다

요구를 분석해 보니 이미 코드에 들어가 있는 경우가 있었습니다. 에이전트의 기본 충동은 「요청을 받았으니 만든다」입니다. 그러면 같은 조건이 코드 두 곳에 생기고, 나중에 한쪽만 고쳐졌을 때 원인을 추적할 수 없습니다. 「일반 화면에서만 적용하고 특정 화면은 제외해 달라」는 요구를 그대로 받아 제외 분기를 넣었다면, 이미 있는 제외 조건 위에 같은 조건이 한 겹 더 얹혔을 것입니다.

그래서 무변경(no-op) 결론에도 규칙을 뒀습니다.

1. 요구 항목마다 그것을 충족하는 코드 위치를 줄 단위로 적습니다. 「이미 되어 있습니다」 한 줄로 끝내면 확인하지 않고 넘긴 것과 구별되지 않습니다.
2. 조건부 차단이라면 막아야 할 것만 막혔는지 경계값과 인접 기능을 회귀 항목으로 세웁니다.
3. 변경이 0이면 개발 브랜치로 승격하지 않습니다. 작업 브랜치의 기준 브랜치에는 다른 사람의 커밋이 쌓여 있어서, 변경 없이 승격하면 그 커밋들만 이 이슈 이름으로 개발 브랜치에 들어갑니다.
4. 변경 전후 화면이 같으면 화면 비교 검증은 통과 기록만 남는 껍데기입니다. 생략하고, 생략했다고 적습니다.
5. 마지막 단계는 PR 요청이 아니라 배포 일정 확인입니다. 열 PR이 없으므로, 남은 종결 조건은 코드가 아니라 그 변경이 언제 운영에 실리는가입니다.

### 「반영됐는가」에는 서버마다 다른 답이 있습니다

무변경 이슈에서 에이전트가 여러 사이클 동안 같은 오판을 반복한 적이 있습니다. 선행 구현이 릴리스 브랜치 어디에도 없다는 사실을 근거로 「어느 서버에도 반영되지 않았다」고 기록했습니다. 그 사실 자체는 맞았지만 적용 범위가 틀렸습니다. 서버마다 배포 소스 브랜치가 다르고, 개발 서버는 개발 브랜치를 빌드합니다. 선행 구현은 개발 브랜치에 이미 있었으므로 개발 서버에서는 처음부터 확인할 수 있었습니다.

이 오판은 문서 정확도 문제로 끝나지 않았습니다. 에이전트는 「올릴 코드가 없는데 개발 서버 확인을 요청하는 모양이 된다」며 이슈를 멈추고 사람을 부르는 쪽을 검토하고 있었습니다. 잘못된 배포 판정은 이슈를 멈추게 합니다.

규칙은 단순합니다. 「반영됐는가」를 물으면 「어느 서버에」를 먼저 정합니다. 확인은 명령 하나로 됩니다.

```bash
# 구현 커밋을 포함한 원격 브랜치 목록이 곧 서버별 답입니다
git branch -r --contains <구현 커밋>
```

결과를 서버와 브랜치의 표로 만들어 산출물에 남깁니다.

## 사람이 직접 처리한 것과 비교하기

### 자연 대조군

자동화의 효과를 재려면 같은 일을 사람이 했을 때와 비교해야 하는데, 처음 시도는 비교가 성립하지 않았습니다. 이유는 세 가지였습니다.

- 다른 개발자의 대화형 세션 기록은 각자의 노트북에만 있어서 사람 쪽 작업 시간을 모을 수 없었습니다.
- 에이전트가 사람 계정으로 Jira에 쓰고 있어서 사람과 기계의 활동을 가를 수 없었습니다.
- 사람이 처리했다고 고른 표본 중 일부가 실제로는 에이전트가 처리한 것이었습니다.

둘째는 에이전트가 전용 계정으로 쓰게 바꿔 해결했습니다. 그리고 비교에 좋은 표본이 우연히 생겼습니다. 같은 요구가 두 번 접수돼서 한 번은 사람이, 한 번은 에이전트가 처리한 경우입니다. 요구, 요청자, 담당자, 작업 성격이 모두 같고 처리 주체만 다릅니다. 같은 단계에 도달한 시점까지를 같은 규칙으로 쟀습니다.

### 무엇은 믿을 수 있고 무엇은 믿을 수 없는가

- **리드타임과 착수 지연은 왜곡이 적습니다.** 양쪽 모두 이벤트 타임스탬프로 직접 측정되기 때문입니다.
- **리드타임 단축의 대부분은 작업이 빨라진 것이 아니라 대기가 사라진 것입니다.** 사람 처리분은 접수 후 한참 동안 그 이슈를 위한 작업이 없다가 배포 일정에 맞춰 한꺼번에 처리됐습니다. 에이전트는 이슈가 처리 대상으로 올라오면 다음 폴에서 착수합니다. 그래서 「개발이 몇 배 빨라졌다」가 아니라 「대기가 사라져 같은 일이 훨씬 일찍 확인 대기 상태에 도달했다」고 써야 정확합니다.
- **사람 쪽 공수는 하한만 잴 수 있습니다.** 커밋 시각은 일이 끝난 시점만 남기므로 조사, 설계, 코딩 시간이 통째로 빠집니다. 커밋 간격이 유휴 임계를 넘으면 활동 구간이 0으로 잡히기도 합니다. 작업 시간 자기신고도 비어 있었습니다. 사람 쪽 분자가 과소 계상되므로 이 값으로 절감률을 말하면 안 됩니다.
- **기계 쪽 축은 폴러의 실행 기록만 씁니다.** 세션 기록 축에는 사람의 대화형 세션이 섞여 기계 시간이 부풀었습니다.
- **봇 계정 분리를 빼면 결론이 뒤집힙니다.** 에이전트가 남긴 댓글과 전이를 사람 활동으로 세면 「자동화했더니 사람 손이 더 많이 들었다」는 반대 결론이 나옵니다.

자동화에 유리한 편향도 함께 적어야 합니다. 대조 쌍 하나는 앞 절의 무변경 이슈였으므로 구현 시간이 자동화 쪽에 아예 계상되지 않았습니다. 다른 하나도 사람이 먼저 만든 구현을 넓히는 작업이라 대상 지점이 이미 특정돼 있었습니다. 그리고 자동화 쪽은 최종 확인 단계에서 사람을 기다리고 있었으므로, 사람 쪽에 온전히 들어 있는 검수 왕복이 아직 빠져 있었습니다.

### 쓰지 않기로 한 표현

보고서를 쓰면서 숫자보다 표현을 고르는 데 시간이 더 들었습니다. 이 에이전트에 대해서는 다음 표현을 쓰지 않기로 했습니다.

- 「사람보다 빠르다는 사실을 입증했다」: 대조 표본이 너무 적습니다.
- 「공수를 몇 퍼센트 절감했다」: 사람 쪽 값이 하한입니다.
- 「사람 개입 없이 완료했다」: 확인 지점과 운영 반영은 사람이 맡았습니다.
- 「토큰 비용을 몇 퍼센트 줄였다」: 절감 전후를 같은 조건으로 잰 표본이 없습니다.
- 「설계대로 구현했으므로 품질이 확보됐다」: 설계 대조율은 설계대로 만들었는지를 잰 값이고, 요구를 충족했는지는 별개입니다. 설계와 구현이 잘 맞았는데 검수에서 여러 번 되돌아간 이슈가 실제로 있었습니다.
- 비용 수치를 「지출」로 쓰기: 구독 세션의 사용량을 종량제 단가로 환산한 값이지 실제 청구액이 아닙니다.

대신 원자료를 그대로 씁니다. 백분율 하나보다 「기록된 단계 이동 중 몇 번을 시스템이 처리했는가」처럼 분자와 분모가 보이는 문장이 낫습니다.

## 정리

네 편에 걸쳐 Mac mini 한 대에 이슈 자동 처리 에이전트를 상주시킨 과정을 정리했습니다. 마지막으로 운영에서 남은 것을 모읍니다.

- **비용은 출력이 아니라 맥락에서 나옵니다.** 실행 한 번의 비용은 대부분 맥락을 다시 읽고 다시 쓰는 데 들어갑니다. 줄일 수 있는 항은 맥락 크기, 턴 수, 실행 횟수이고, 답을 짧게 하라는 지시로는 많이 줄지 않습니다.
- **`--resume`은 공짜가 아닙니다.** 맥락은 이어지지만 이 환경에서는 실행 경계마다 캐시를 다시 썼습니다. 체인을 끊는 정책을 두고, 승계물은 시간순 기록이 아니라 현재 상태로 씁니다.
- **원장은 실패도 적어야 원장입니다.** 성공 분기에만 적재하면 실패가 늘수록 총액이 줄어듭니다. 모든 집계 값에는 그 값의 창을 함께 싣습니다.
- **리포트는 스스로를 의심해야 합니다.** 로그를 못 읽었을 때 전부 0을 내지 말고 무효라고 말하게 합니다. 짧은 대조 경로를 남겨 두고, 경고에는 관측 사실만 씁니다.
- **검증의 경계는 환경이 정하고, 배포의 경계는 되돌릴 수 있는가와 판정 근거를 가질 수 있는가가 정합니다.** 하지 못한 검증은 하지 못했다고 씁니다.
- **만들지 않는 것도 결론입니다.** 이미 구현된 요구는 충족 위치를 줄 단위로 적고, 승격하지 않고, 배포 판정은 서버 단위로 냅니다.
- **사람과 비교할 때는 무엇이 왜곡 없이 재지는지부터 가립니다.** 이벤트 타임스탬프는 믿을 수 있고, 커밋 기반 공수는 하한입니다. 사람과 기계의 계정을 가르지 않으면 결론이 뒤집힙니다.

돌아보면 운영 중에 고친 결함 상당수는 기능이 아니라 측정에 있었습니다. 에이전트가 일을 잘하는지는 측정이 맞아야 알 수 있고, 측정이 틀리면 에이전트가 잘하는지 못하는지도 알 수 없습니다. 상주 에이전트를 만든다면 기능만큼 원장과 리포트도 공들여 설계하는 편이 좋습니다.

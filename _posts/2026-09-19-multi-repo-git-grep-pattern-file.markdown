## 문제와 배경

웹 서비스의 URL 경로 수십 건을 한꺼번에 바꾸거나 닫으려면, 먼저 **그 주소를 누가 참조하는지**를 알아야 합니다. 같은 저장소 안의 내부 링크는 함께 고치면 됩니다. 문제는 다른 저장소에 적힌 참조입니다. 모바일 앱의 웹뷰 주소, 배치가 보내는 알림 메일의 링크, 다른 서비스의 바로가기, 외부 개발자용 안내 페이지는 웹 서비스 배포에 따라오지 않습니다. 이런 참조를 놓친 채 경로를 바꾸면 메일 속 수신거부 링크가 죽거나 앱 화면이 404를 띄웁니다.

조사 대상은 여러 저장소를 서브모듈로 묶은 작업 공간이었습니다. `app-web`, `app-batch`, `shared-lib` 같은 저장소가 수십 개 들어 있고, 찾을 경로도 수십 건이었습니다.

가장 먼저 떠오르는 방법은 경로마다, 저장소마다 `grep -r`을 돌리는 것입니다.

```bash
# 느린 방법: 경로 수 × 저장소 수만큼 디렉터리를 순회합니다
while IFS= read -r path; do
  for repo in repos/*/; do
    grep -rn -- "$path" "$repo"
  done
done < paths.txt
```

경로 수십 건 × 저장소 수십 개면 디렉터리 전체 순회가 천 번을 넘습니다. 실제로 돌려 보니 데이터 파일이 큰 저장소 하나에서만 10분을 넘겨 중단해야 했습니다. 경로를 패턴 파일로 묶어 `grep -rF -f`로 저장소당 한 번만 순회하게 바꿔도 같은 저장소에서 다시 10분을 넘겼습니다. 순회 횟수보다 **무엇을 읽느냐**가 문제였습니다.

## 접근: 패턴 파일 하나, 저장소당 `git grep` 한 번

두 가지를 바꿨습니다.

1. **패턴을 파일 하나로 모읍니다.** `-f 파일`은 파일의 각 줄을 패턴으로 쓰므로, 한 번의 순회로 모든 경로를 동시에 찾습니다. 순회 횟수가 「경로 수 × 저장소 수」에서 「저장소 수」로 줄어듭니다.
2. **`grep -r` 대신 `git grep`을 씁니다.** `git grep`은 기본적으로 git이 추적하는 파일만 봅니다. `.gitignore`에 걸린 `node_modules`, 빌드 산출물, 내려받은 데이터 덤프는 처음부터 읽지 않습니다. 소스 참조를 찾는 목적이라면 이 파일들은 어차피 볼 필요가 없습니다.

같은 저장소 묶음에 이 방식을 적용하자 전체 저장소를 도는 데 약 2.5초가 걸렸습니다.

| 방식 | 디렉터리 순회 수 | 소요 시간 |
|---|---|---|
| 경로별 `grep -r` | 경로 수 × 저장소 수 | 첫 대형 저장소에서 10분 초과로 중단 |
| 저장소별 `grep -rF -f` + 제외 옵션 | 저장소 수 | 첫 대형 저장소에서 10분 초과로 중단 |
| 저장소별 `git grep -I -o -F -f` | 저장소 수 | 전체 약 2.5초 |

수치는 한 작업 공간에서 한 번 잰 값입니다. 차이의 대부분은 추적되지 않는 대용량 파일을 건너뛴 데서 나왔다고 보지만, 파일별로 시간을 나눠 재 보지는 않았습니다.

## 구현

### 1. 패턴 파일 만들기

한 줄에 패턴 하나씩 적습니다. 경로 중간에 `{id}` 같은 변수가 있으면 변수 앞까지의 고정 접두사만 남깁니다.

```bash
cat > patterns.txt <<'EOF'
/help/view
/notice/list
/legacy/unsubscribe.do
/member/reject
EOF

# 빈 줄과 앞뒤 공백을 지웁니다
sed -i.bak -e 's/^[[:space:]]*//' -e 's/[[:space:]]*$//' -e '/^$/d' patterns.txt
```

### 2. 저장소마다 한 번 훑기

```bash
#!/usr/bin/env bash
# scan-refs.sh: 패턴 파일로 여러 저장소를 훑어 "저장소<TAB>파일<TAB>패턴"을 출력합니다
set -euo pipefail
# git -C 는 작업 디렉터리를 옮기므로 패턴 파일은 절대 경로로 바꿔 둡니다
patterns=$(cd "$(dirname "$1")" && pwd)/$(basename "$1"); shift
tmp=$(mktemp); trap 'rm -f "$tmp"' EXIT

for repo in "$@"; do
  name=$(basename "$repo")
  rc=0
  git -C "$repo" grep -I -o -F -f "$patterns" -- . \
      ':!*.min.js' ':!*.map' ':!*.lock' ':!*.svg' > "$tmp" || rc=$?
  # 종료 코드 1은 "매치 없음"이고, 2 이상은 진짜 오류입니다
  if [ "$rc" -gt 1 ]; then
    echo "error: $repo (exit $rc)" >&2; exit "$rc"
  fi
  awk -v r="$name" '{
    i = index($0, ":")                  # 첫 콜론까지가 파일 경로
    print r "\t" substr($0, 1, i-1) "\t" substr($0, i+1)
  }' "$tmp"
done
```

```bash
bash scan-refs.sh patterns.txt repos/*/ > hits.tsv
```

옵션의 역할은 다음과 같습니다.

| 옵션 | 역할 |
|---|---|
| `-F` | 패턴을 정규식이 아니라 고정 문자열로 취급합니다. |
| `-f patterns.txt` | 파일의 각 줄을 패턴으로 씁니다. |
| `-o` | 줄 전체 대신 **매치된 부분만** 출력합니다. 패턴 문자열이 그대로 나오므로 어느 패턴이 걸렸는지 바로 압니다. |
| `-I` | 바이너리 파일을 건너뜁니다. |
| `':!*.min.js'` 등 | pathspec 제외 문법입니다. 압축된 번들, 소스맵, 잠금 파일, SVG처럼 사람이 쓴 참조가 아닌 파일을 뺍니다. |

두 군데는 처음 쓴 버전에서 실제로 틀렸던 부분입니다. 패턴 파일을 상대 경로로 넘기면 `git -C`가 디렉터리를 옮긴 뒤라 `fatal: cannot open 'patterns.txt'`가 납니다. 처음에는 「매치 없음」의 종료 코드 1을 넘기려고 파이프 끝에 `|| true`를 붙였는데, 그러면 이 치명 오류까지 삼켜서 결과가 빈 채로 정상 종료합니다. 「참조 0」이 판단 근거가 되는 작업이라 이 차이가 치명적입니다. 종료 코드 1과 2 이상을 나눠 처리해야 하는 이유는 [종료 코드 0으로 끝나는 조용한 실패](/blog/2026/10/07/silent-failure-exit-code-fail-open.html)에서 따로 다뤘습니다.

`git grep -o`는 `파일:매치` 형식으로 출력합니다. 패턴 쪽에 콜론이 들어갈 수 있으므로(`https:`로 시작하는 전체 URL 등) `awk -F:`로 마지막 필드를 자르지 않고, 첫 콜론에서 한 번만 나눕니다. 파일 이름에 콜론이 들어가는 저장소라면 `-z`로 구분자를 NUL로 바꾸는 편이 안전합니다.

### 3. 매치를 패턴 기준으로 되돌리기

결과를 패턴별로 묶으면 「이 경로를 누가 참조하는가」 표가 됩니다. 한 번도 안 걸린 패턴도 따로 뽑아야 합니다. 「참조 0」은 그 자체로 판단 근거이기 때문입니다.

```bash
# 패턴별로 어느 저장소가 몇 번 참조하는지
awk -F'\t' '{ n[$3 "\t" $1]++ } END { for (k in n) print k "\t" n[k] }' hits.tsv \
  | sort > by-pattern.tsv

# 어디서도 걸리지 않은 패턴
cut -f3 hits.tsv | sort -u > matched.txt
sort -u patterns.txt | comm -23 - matched.txt > unreferenced.txt
```

`by-pattern.tsv`의 한 줄은 `패턴  저장소  건수` 모양입니다. 이 표를 스프레드시트에 붙이거나, 경로 목록 표에 「참조 출처」 열로 합치면 됩니다.

## 함정과 트레이드오프

### 고정 문자열과 정규식

`-F`를 빼면 각 줄이 정규식이 됩니다. URL 경로에는 `.`, `?`, `+`, `[`처럼 정규식에서 뜻이 있는 문자가 자주 들어갑니다. 임시 저장소에서 확인해 보면 `-F` 없이 `/legacy/old.do`를 찾을 때 `/legacy/oldXdo`도 함께 걸립니다. 경로 목록을 찾는 용도라면 `-F`를 기본으로 두고, 정규식이 꼭 필요한 패턴만 별도 파일로 나눠 `-E -f`로 따로 돌리는 편이 낫습니다.

패턴 파일의 빈 줄도 지워 두는 것이 좋습니다. GNU grep은 빈 패턴을 모든 줄과 매치되는 패턴으로 취급한다고 문서에 적혀 있습니다. 제 환경의 `git grep`(2.54)과 macOS 기본 grep에서는 빈 줄이 모든 줄을 잡지 않았지만, 이것은 직접 관찰한 결과이지 보장된 동작이 아닙니다.

### `-o`와 겹치는 패턴

패턴 하나가 다른 패턴의 접두사이면 집계가 어긋납니다. 임시 저장소에서 `/help`와 `/help/view`를 함께 넣고 돌려 보니, `/help/view`가 들어 있는 줄은 `/help/view` 하나로만 출력되고 `/help`로는 세어지지 않았습니다. 또 `/help/viewer`가 들어 있는 줄은 `/help/view`로 잡혔습니다. 고정 문자열은 부분 문자열로 매치되기 때문입니다.

- 접두사 관계인 패턴은 따로 실행하거나, 결과를 해석할 때 긴 패턴의 매치를 짧은 패턴에도 더해 줍니다.
- 경계가 중요하면 패턴 끝에 경계 문자를 붙인 변형(`/help/view"`, `/help/view?`)을 함께 넣거나, 그 몇 건만 정규식으로 다시 확인합니다.

### 바이너리와 압축된 파일

`-I`는 git이 바이너리로 판단한 파일만 건너뜁니다. 한 줄짜리 압축 번들(`*.min.js`)이나 소스맵은 텍스트라서 그대로 검사되고, 매치가 걸리면 의미 없는 거대한 줄이 결과를 채웁니다. 위 스크립트처럼 pathspec으로 확장자를 빼 두면 결과가 깨끗해집니다. 다만 저장소가 빌드 산출물을 커밋해 두었다면, 그 산출물 속 참조가 실제 배포되는 유일한 사본일 수도 있습니다. 제외 목록은 저장소 성격을 보고 정합니다.

CSV나 JSON 같은 데이터 파일에 걸린 매치도 따로 읽어야 합니다. 데이터에 URL이 문자열로 들어 있을 뿐 그 저장소가 그 주소를 호출하는 것은 아닌 경우가 많습니다. 「외부 호출자 있음」으로 판정하기 전에 `파일:줄`을 한 번 열어 확인합니다.

### 서브모듈

작업 공간의 최상위 저장소에서 그냥 `git grep`을 실행하면 서브모듈 안의 내용은 보지 않습니다. 서브모듈은 상위 저장소 입장에서 커밋 포인터 하나일 뿐이기 때문입니다. 방법은 두 가지입니다.

```bash
# 1) 상위 저장소에서 서브모듈까지 재귀
git grep --recurse-submodules -I -o -F -f patterns.txt

# 2) 서브모듈마다 따로 (저장소 이름을 붙이기 쉽습니다)
git submodule foreach --quiet \
  'git grep -I -o -F -f "$toplevel/patterns.txt" | sed "s|^|$name:|" || true'
```

`--recurse-submodules`는 활성화되어 체크아웃된 서브모듈만 검색하고, `--untracked`와 함께 쓸 수 없습니다. 초기화하지 않은 서브모듈은 조용히 빠지므로, 결과에 저장소가 하나도 안 보이면 체크아웃 여부부터 확인합니다.

또 서브모듈마다 지금 체크아웃된 브랜치가 다를 수 있습니다. 검색 결과는 「각 저장소의 현재 작업 트리」 기준입니다. 운영 배포 기준으로 보려면 저장소마다 원격 기준 브랜치를 지정해 트리를 검색합니다.

```bash
git -C repos/app-batch fetch -q origin
git -C repos/app-batch grep -I -o -F -f "$PWD/patterns.txt" origin/main -- .
```

트리를 지정하면 출력이 `origin/main:파일:매치` 형식이 되므로, 앞의 `awk` 분리 위치도 하나 늘려야 합니다.

### 추적 파일만 본다는 것

`git grep`이 빠른 이유가 곧 한계입니다. 커밋되지 않은 로컬 설정 파일이나 무시된 파일은 보지 않습니다. 필요하면 `--untracked`(무시 파일까지 보려면 `--no-exclude-standard`)를 붙이되, 속도 이점이 줄어듭니다.

더 근본적으로, 이 방법이 찾는 것은 **저장소에 적힌 참조**뿐입니다. 이미 발송된 메일 본문, 사용자 기기에 깔린 앱 구버전, 검색엔진 색인, 외부 사이트의 링크는 저장소 밖에 있습니다. 「참조 0」은 「저장소 안에서는 아무도 링크하지 않는다」는 뜻이지 「아무도 그 주소로 들어오지 않는다」는 뜻이 아닙니다. 실제 유입은 접근 로그나 분석 도구의 리퍼러로 따로 확인해야 합니다.

### 셸 함수로 감싼 명령

이 스크립트를 파이썬 같은 다른 언어로 감쌀 때 겪은 함정도 있습니다. 대화형 셸에서 잘 되던 `rg`를 `subprocess`로 부르니 `FileNotFoundError`가 났습니다. 그 셸에서 `rg`는 실행 파일이 아니라 셸 함수로 정의되어 있었고, 셸 함수와 alias는 자식 프로세스에 보이지 않습니다. `type rg`나 `which rg`가 경로 대신 함수 정의를 출력하면 이 경우입니다. 자식 프로세스에서 쓸 도구는 실제 실행 파일 경로를 확인하고 부르거나, 어디에나 있는 `git grep`을 쓰는 편이 안전합니다.

## 결과를 판단에 쓰기

참조 출처를 뽑았으면 경로마다 네 단계로 나누면 변경 위험이 바로 보입니다.

| 판정 | 뜻 | 대응 |
|---|---|---|
| 외부 호출자 있음 | 앱, 다른 서비스, 외부 안내 문서 등 따로 배포되는 저장소가 참조 | 영구 리다이렉트(301)를 유지하거나 상대 쪽 수정을 먼저 받습니다. |
| 함께 배포되는 저장소만 | 같은 배포 일정에 묶인 배치나 관리 도구만 참조 | 같은 배포에 함께 고칩니다. |
| 내부만 | 바꾸려는 저장소 안에서만 링크 | 내부 링크를 바꾸고 리다이렉트를 겁니다. |
| 참조 0 | 어느 저장소도 링크하지 않음 | 닫기(410) 후보입니다. 다만 유입 로그로 한 번 더 확인합니다. |

## 정리

- 여러 패턴을 여러 저장소에서 찾을 때는 패턴을 파일 하나로 모아 `-F -f`로 넘기고, 저장소당 한 번만 순회합니다.
- `grep -r` 대신 `git grep`을 쓰면 추적 파일만 읽어서, 무시된 대용량 파일이 많은 저장소일수록 차이가 커집니다. 한 작업 공간에서는 10분을 넘기던 검색이 2.5초로 줄었습니다.
- `-o`로 매치된 패턴 문자열을 받아 `저장소·파일·패턴`으로 집계하고, 한 번도 걸리지 않은 패턴을 따로 뽑습니다.
- 정규식 문자, 접두사가 겹치는 패턴, 압축 파일과 데이터 파일의 매치, 서브모듈과 체크아웃 브랜치, 저장소 밖의 참조는 결과를 해석할 때 따로 챙깁니다.

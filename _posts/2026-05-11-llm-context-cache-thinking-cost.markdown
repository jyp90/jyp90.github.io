## 문제와 배경

여러 언어로 문서를 바꿔 보여주는 기능에서, 요청마다 같은 시스템 프롬프트와 소수의 가이드 예시를 통째로 다시 보내고 있었습니다. 문서 내용은 요청마다 다르지만 지시문과 예시는 거의 고정이었는데도, 모델은 그 부분까지 매번 새 입력 토큰으로 계산했습니다. 호출이 늘자 비용 증가 폭이 실제로 처리한 문서 수의 증가 폭보다 가팔라졌습니다.

같은 요청에는 또 다른 낭비가 섞여 있었습니다. 모델 쪽에 사고(thinking) 단계가 켜져 있어, 번역처럼 정해진 형식을 그대로 따르면 되는 작업에서도 매번 사고 과정에 해당하는 출력 토큰이 추가로 붙었습니다. [이전 글](/blog/2026/05/06/fastapi-sse-production-stability.html)에서 스트리밍 응답을 안정화한 뒤, 이번에는 같은 기능의 비용 구조 쪽을 들여다봤습니다. 모델 과금 체계와 단가는 공급자가 수시로 바꾸므로, 아래에서는 금액 대신 토큰 절감 비율과 구조만 다룹니다.

## 접근

요청 하나가 서로 독립적인 두 개의 게이트를 거치도록 구조를 나눴습니다.

```mermaid
flowchart TD
  req["요청 도착"] --> pages{"페이지 수"}
  pages -->|"3 이상"| cache["캐시 적용"]
  pages -->|"미만"| fresh["새 프롬프트"]
  cache --> call["모델 호출"]
  fresh --> call
  call --> think{"사고 필요?"}
  think -->|"아니오"| off["budget 0"]
  think -->|"예"| on["budget 유지"]
```

첫 번째 게이트는 캐시 적용 여부를 문서의 페이지 수만으로 정합니다. 처음에는 환경변수 플래그로 켜고 끄는 안도 검토했지만, 개발·운영 환경에서 서로 다른 값이 들어가 결과가 갈릴 위험이 있어 버렸습니다. 페이지 수 하나로만 정하면 환경에 상관없이 같은 입력이면 항상 같은 경로를 탑니다.

두 번째 게이트는 작업 성격에 따라 사고 단계를 아예 끄는 것입니다. 번역은 입력 구조를 그대로 따라가는 템플릿형 작업이라, 사고 단계를 거치지 않아도 결과 형식이 크게 달라지지 않을 것으로 보고 기본값을 0으로 뒀습니다. 복잡한 수식이나 코드가 섞인 입력까지 품질이 보장된다고 확인한 것은 아니고, 운영하면서 지켜봐야 할 가정입니다.

| 게이트 | 기준 | 이유 |
|---|---|---|
| 프롬프트 캐시 | 페이지 수 ≥ 3 | 손익분기점 자체는 더 낮은 페이지 수지만, 운영에서 캐시가 자주 맞도록 여유를 둠 |
| thinking budget | 기본값 0 | 템플릿형 작업이라 사고 단계가 결과에 거의 기여하지 않는다고 판단 |

## 구현

### 핵심 코드

캐시 적용 여부를 판단하는 함수는 페이지 수와 모델의 캐싱 지원 여부만 봅니다. 환경변수를 넣지 않은 이유를 주석으로 남겨, 나중에 "편의상 플래그 하나 추가하자"는 유혹을 막았습니다.

```python
CACHE_MIN_PAGES = 3

def should_use_cache(pages: int, model: str) -> bool:
    """캐시 적용 여부를 페이지 수만으로 결정한다.
    환경변수 플래그를 두지 않아 개발/운영 환경이 서로 다르게 동작하는 일을 막는다."""
    return pages >= CACHE_MIN_PAGES and supports_prompt_cache(model)
```

캐시 키는 요청을 처리한 서버 인스턴스가 아니라 언어와 콘텐츠 유형, 프롬프트 버전으로만 만듭니다. 같은 언어·유형이면 어느 인스턴스가 받든 같은 캐시를 보게 하려는 목적입니다.

```python
def cache_key(language: str, content_type: str, prompt_version: str) -> str:
    raw = f"{language}:{content_type}:{prompt_version}"
    return hashlib.sha256(raw.encode()).hexdigest()
```

모델 호출부는 두 게이트의 결과를 그대로 반영합니다. 캐시를 쓸 때는 캐시된 프롬프트 참조를, 쓰지 않을 때는 새로 만든 프롬프트를 넘기고, thinking budget은 작업 유형에 따라 결정한 값을 넘깁니다.

```python
def translate_document(doc: Document, model: str) -> str:
    use_cache = should_use_cache(doc.pages, model)
    prompt = cached_prompt_ref(doc.language, doc.content_type) if use_cache else build_prompt(doc)
    response = client.generate_content(
        prompt=prompt,
        generation_config={"thinking_budget": 0},
    )
    return response.text
```

이 조합으로 입력 토큰은 캐시가 맞을 때 약 3분의 2 가량 줄었고, 출력 토큰은 사고 단계를 끄자 약 4분의 3 가량 줄었습니다. 둘은 서로 다른 지점(입력 vs 출력)을 줄이는 독립적인 조치라서, 하나만 적용했을 때보다 같이 적용했을 때 전체 토큰 사용량 감소 폭이 커졌습니다.

분당 요청 한도와 분당 토큰 한도는 따로 관리되는 값이라, 평소 트래픽은 요청 한도에는 여유가 있어도 토큰 한도에는 그렇지 않을 수 있습니다. 둘을 같은 것으로 보고 한쪽만 확인하면, 실제로는 토큰 한도에 먼저 걸리는 상황을 놓칠 수 있습니다.

## 함정과 트레이드오프

| 선택 | 얻는 것 | 잃거나 주의할 것 |
|---|---|---|
| 캐시 적용 하한을 손익분기점보다 높게 둠 | 캐시 적중률이 올라가 짧은 문서가 캐시를 자주 비우지 않음 | 손익분기점은 넘겼지만 하한에는 못 미치는 문서는 캐시를 못 씀 |
| 캐시 키에 프롬프트 버전을 포함 | 프롬프트 문구를 바꿔도 옛 캐시를 잘못 재사용하지 않음 | 버전을 올리는 걸 잊으면 바뀐 프롬프트가 옛 캐시로 응답할 수 있음 |
| thinking budget 기본값 0 | 출력 토큰이 크게 줄어듦 | 복잡한 입력에서 품질이 떨어질 가능성은 운영 데이터로 계속 확인해야 함 |
| 캐시 생성·보관에 드는 비용은 계산에서 제외 | 당장 확인된 절감 효과에 집중 | 캐시 쪽 과금 정책이 바뀌면 손익분기점도 다시 계산해야 함 |

캐시 적용 하한을 손익분기점보다 높게 둔 선택은 "이득이 나는 지점부터 바로 켠다"는 직관과는 반대입니다. 손익분기점 바로 위 구간까지 캐시를 켜면, 그 구간의 문서가 캐시를 자주 새로 만들고 지우는 쪽으로 움직여 다른 문서의 캐시 적중률을 떨어뜨리는 경우가 있었습니다. 캐시는 개별 요청 단위가 아니라 공유 자원으로 보고 하한을 정해야 했습니다.

## 정리

- 같은 프롬프트를 매번 새 입력으로 보내는 비용과, 불필요한 사고 단계가 만드는 출력 비용은 서로 다른 지점에서 생기므로 따로 줄여야 합니다.
- 프롬프트 캐시 적용 여부는 환경변수가 아니라 요청 자체의 속성(페이지 수)으로만 정해, 환경마다 다르게 동작할 여지를 없앴습니다.
- 캐시 키에 프롬프트 버전을 넣지 않으면, 프롬프트를 고친 뒤에도 옛 캐시가 계속 재사용될 수 있습니다.
- thinking budget을 끄는 선택은 템플릿형 작업이라는 전제 위에 있고, 그 전제가 맞는지는 운영 데이터로 계속 확인해야 합니다.
- 분당 요청 한도와 분당 토큰 한도는 다른 값이라, 한쪽만 보고 여유가 있다고 판단하면 안 됩니다.

## 문제와 배경

앞의 네 편에서 폴러가 Jira 이슈를 감지하고 헤드리스 `claude -p` 세션을 띄워 작업을 맡기는 구조까지 다뤘습니다. 이 편은 그 뒤에 오는 두 단계 중 첫 번째, 즉 에이전트가 한 일을 사람에게 알리는 경로입니다. 트래커 코멘트, Slack 메시지, 멘션, 배포 결과 알림, 정기 요약이 여기에 속합니다. 그 경로가 사고를 내지 않게 받쳐 주는 안전장치와 게이트 오판 사례는 다음 편에서 다룹니다.

두 단계 모두 출발점은 같은 전제입니다. **에이전트에게 「하지 마라」를 프롬프트로만 말하면 언젠가 어깁니다.** 그래서 지켜야 하는 규칙은 가능한 한 프롬프트 바깥, 즉 실행 인자·훅·권한 설정·폴러 코드에 둡니다. 아래 내용은 대부분 이 원칙을 각 경로에 적용한 결과입니다.

## 통지 1: 트래커 코멘트는 MCP 도구가 아니라 REST 호출로

### 프롬프트 금지는 지켜지지 않았습니다

Claude Code에는 Atlassian MCP 서버를 붙일 수 있고, 거기에는 코멘트 작성이나 상태 전이 같은 쓰기 도구가 들어 있습니다. 대화형 세션에서는 편리하지만 무인 에이전트에는 문제가 있었습니다. 에이전트가 이 도구로 코멘트를 쓰면 자동화 계정이 아니라 운영자 **개인 명의**로 글이 올라갔습니다. 그 장비의 MCP 연결이 사람 계정으로 인증돼 있었기 때문으로 봅니다.

처음에는 프롬프트에 「트래커 쓰기에 MCP 도구를 쓰지 마십시오」라고 적었습니다. 대부분은 지켜졌지만 항상은 아니었고, 실제로 개인 명의 코멘트가 나간 일이 있었습니다. 누가 쓴 글인지가 틀리면 나중에 사람과 기계의 작업량을 가르는 것도 불가능해집니다.

### 도구 자체를 세션에서 빼 버립니다

해결은 지시가 아니라 제거였습니다. 폴러가 세션을 띄울 때 `--disallowedTools`로 MCP 쓰기 도구를 서브프로세스 단위에서 막습니다. MCP 서버가 여러 이름공간으로 붙어 있을 수 있으니 이름공간마다 같은 도구 목록을 펼쳐서 넘깁니다.

```python
WRITE_TOOLS = ["addCommentToJiraIssue", "transitionJiraIssue",
               "editJiraIssue", "createJiraIssue"]
MCP_PREFIXES = ["mcp__atlassian__", "mcp__plugin_atlassian__"]  # 연결 방식마다 접두어가 다릅니다

def disallowed_tools():
    return [p + t for p in MCP_PREFIXES for t in WRITE_TOOLS]

cmd = ["claude", "-p", prompt,
       "--disallowedTools", ",".join(disallowed_tools())]
```

읽기 도구(이슈 조회, 전이 목록 조회, JQL 검색)는 그대로 둡니다. 세션은 MCP로 읽고, 쓰기는 자동화 계정의 API 토큰으로 REST를 직접 호출합니다. 코멘트 본문 앞에는 고정 접두어를 붙여 사람이 한눈에 기계가 쓴 글임을 알 수 있게 했습니다.

다만 「REST로 쓰라」고 하는 순간 다른 문제가 생깁니다. 세션이 `curl`을 실행해야 하는데, 그 `curl`이 권한 규칙을 실제로 통과하는지가 생각보다 까다롭습니다. 이 부분은 6편의 「쓰기 권한 게이트」에서 이어서 다룹니다.

## 통지 2: Slack은 봇 한 경로로

Slack 발송은 처음에 Incoming Webhook과 봇 토큰(`chat.postMessage`)이 섞여 있었는데, 봇 한 경로로 통일했습니다. 이유는 두 가지입니다.

- **스레드가 필요합니다.** 봇으로 보낸 메시지는 스레드의 기준 타임스탬프를 돌려받을 수 있어서, 같은 이슈의 후속 알림을 한 스레드에 모으고 사람이 그 스레드에 단 답장을 이슈 세션으로 다시 이어 붙일 수 있습니다. 이 대화형 리스너는 Slack Socket Mode로 상시 연결된 launchd 서비스로 따로 돕니다.
- **경로가 둘이면 정책도 둘이 됩니다.** 채널, 서식, 실패 처리 규칙을 바꿀 때 한쪽만 고치는 일이 생깁니다.

경로를 하나로 줄여도 구현이 하나가 되지는 않았습니다. 보조 셸 스크립트들이 쓰는 공용 발송 함수와, 폴러가 자체로 가진 Python 발송 함수가 같은 정책을 두 벌로 구현하고 있습니다. 기능 결함은 아니지만, 정책을 바꿀 때 두 곳을 함께 고쳐야 한다는 사실은 설정 파일 주석에 적어 두었습니다.

```json
{
  "slack": {
    "method": "bot",
    "channel_id": "C0XXXXXXX",
    "_note": "발송 정책은 셸 공용 함수와 폴러 내장 함수 두 곳에 있습니다. 함께 고치십시오."
  }
}
```

## 통지 3: 멘션은 담당자와 보고자만

초기 구현은 사람을 부르는 경로가 여러 갈래였고, 그중 상당수가 **이슈와 무관한 고정 명단**을 불렀습니다. 배포가 끝나면 검수 담당자를, 헬스 경고가 나면 운영자를, 담당자가 개발팀 밖이면 개발팀 전원을 부르는 식입니다. 이벤트가 생길 때마다 같은 사람이 호출되니, 그 사람 입장에서는 자기 일이 아닌 알림이 계속 쌓입니다.

원칙을 하나로 줄였습니다.

- 이슈 단위 이벤트의 멘션 대상은 **그 이슈의 담당자(assignee)와 보고자(reporter)뿐**입니다.
- 담당자가 없으면 보고자만 부르고 「담당자 지정이 필요합니다」를 함께 적습니다.
- 둘 다 없으면 멘션 없이 안내만 남깁니다. 다른 사람을 찾아서 부르지 않습니다.
- 폴러 헬스 경고나 트리거 실패처럼 이슈와 무관한 시스템 알림은 멘션 없이 채널 메시지만 보냅니다.

이 원칙을 지키게 만든 장치는 역시 프롬프트 문장이 아니라 **데이터를 빼는 것**이었습니다. 예전에는 「담당자가 개발팀이 아니면 전원을 멘션하라」는 판단을 위해 개발팀 전원의 계정 ID를 프롬프트에 넣었습니다. 이제 프롬프트에는 담당자와 보고자의 계정 ID만 들어갑니다. 세션이 다른 사람의 ID를 모르면 그 사람을 멘션할 방법도 없습니다. 개발팀 명단은 폴러 안에서 「담당자를 개발자로 재지정해 달라는 안내를 붙일지」를 판정하는 데만 씁니다.

```python
def mention_targets(issue):
    people = [p for p in (issue.assignee, issue.reporter) if p]
    # 중복 제거(담당자와 보고자가 같은 사람일 수 있음), 순서 유지
    seen, result = set(), []
    for p in people:
        if p.account_id not in seen:
            seen.add(p.account_id)
            result.append(p)
    return result  # 비어 있으면 멘션 없이 안내만 남깁니다
```

설정 파일의 이벤트별 멘션 명단은 전부 빈 배열로 비우고, 「여기에 이름을 다시 넣으면 그 사람이 해당 이벤트마다 습관적으로 호출됩니다」라는 경고를 주석으로 남겼습니다.

대가도 있습니다. 시스템 알림에서 멘션이 사라졌으므로 폴러가 죽어도 실시간으로 호명되는 사람이 없습니다. 채널 메시지와 매시 헬스체크는 남아 있으니 탐지는 유지되지만, 알아차리는 속도는 사람이 채널을 얼마나 자주 보느냐에 달렸습니다. 또 담당자 필드의 품질에 더 기대게 됩니다. 담당자가 잘못 지정돼 있으면 엉뚱한 사람이 불리는데, 예전에는 전원 멘션이 그 오류를 덮었다면 이제는 드러냅니다. 저는 덮는 쪽보다 드러내는 쪽이 낫다고 판단했습니다.

## 통지 4: 배포 성공 알림과 상태 자동 전이

에이전트가 코드를 개발 브랜치에 올린 뒤의 흐름은 책임을 둘로 나눴습니다.

- **세션**: 구현, 자체 검증, 개발 브랜치 승격, 결과 코멘트까지 합니다. Jenkins는 만지지 않습니다.
- **폴러**: 다음 폴링 주기에 Jenkins 개발 빌드를 API로 실행하고, 결과를 감시해 알림과 상태 전이를 합니다.

세션에서 Jenkins를 떼어 낸 이유는, 세션이 실행하는 명령은 권한 판정이 매번 같다는 보장이 없기 때문입니다(아래 「쓰기 권한 게이트」 참고). 폴러는 일반 Python 프로세스라 권한 시스템을 거치지 않고 결정적으로 동작합니다.

### 빌드를 거는 조건

폴러는 아래 조건이 **모두** 참일 때만 빌드를 요청합니다.

1. 빌드 잡이 추종하는 브랜치가 개발 브랜치이고, 그 값을 **잡 설정에서 직접 읽었다.**
2. 아직 빌드되지 않은 커밋 구간에 에이전트가 승격한 커밋이 들어 있다.
3. 개발 브랜치의 최신 커밋이 Jenkins가 마지막으로 빌드한 리비전과 다르다.
4. 진행 중인 빌드가 없고 대기열도 비어 있다.

1번의 「잡 설정에서 직접 읽었다」가 중요합니다. 잡 설정을 못 읽었을 때 마지막 빌드의 리비전으로 브랜치를 대신 추정하는 경로가 있었는데, 그것은 「다음에 무엇을 빌드할지」가 아니라 「지난번에 무엇을 빌드했는지」입니다. 누군가 잡의 추종 브랜치를 자기 기능 브랜치로 바꾼 직후라면, 그 추정을 믿는 순간 남의 브랜치를 공용 개발 서버에 배포하게 됩니다.

2번은 공용 브랜치라는 성질 때문에 넣었습니다. 다른 개발자가 개발 브랜치에 머지만 해 둔 상태에서 에이전트가 빌드를 걸면, 에이전트와 무관한 변경만 배포됩니다. 에이전트의 커밋이 구간에 있을 때만 빌드하고, 그때 함께 나가는 다른 변경이 있으면 결과 코멘트에 그 사실을 적습니다.

판정에 필요한 값을 하나라도 모르면(응답 없음, 필드 누락, 예외) 빌드를 걸지 않습니다. 「모르는 것은 거짓이 아니라 모르는 것」이라는 원칙인데, 이 판정이 왜 기본값 하나로 뒤집히는지는 [실패했는데 성공으로 끝나는 시스템 — 종료 코드 0과 fail-open 게이트](/blog/2026/10/07/silent-failure-exit-code-fail-open.html)에서 따로 다뤘습니다.

```python
def should_trigger(job, dev_tip, agent_commits_in_range):
    # None은 "모름"입니다. 모르면 걸지 않습니다.
    if job is None or job.branch_source != "config" or job.branch != "dev":
        return False, "branch"           # 이 사유만 사람에게 한 번 알립니다
    if not agent_commits_in_range:
        return False, None               # 정상: 조용히 넘깁니다
    if job.last_built_rev is None or dev_tip == job.last_built_rev:
        return False, None
    if job.building is not False or job.in_queue is not False:
        return False, None               # True/False가 명시돼야 통과합니다
    return True, None
```

사람에게 알리는 것은 1번이 깨진 경우뿐입니다. 2~4번은 정상 상태이므로 알리면 소음이 됩니다.

### 결과 알림과 상태 전이

빌드가 성공하면 이슈를 정해 둔 다음 상태(개발 서버 검증 단계)로 옮기고, 담당자와 보고자를 멘션한 코멘트와 Slack 메시지를 보냅니다. 이미 그 상태라면 아무것도 하지 않습니다.

실패도 알립니다. 자동화가 빌드를 걸기 시작하면 「자동화가 실패를 만들었는데 아무도 모르는」 구간이 새로 생기기 때문입니다. 실패 알림에는 빌드 번호, 콘솔 링크, 실패한 리비전을 담되 **원인은 단정하지 않습니다.** 알림을 이슈 스레드로 보내므로 사람이 그 스레드에서 조사를 요청하면 이슈 세션으로 이어집니다. 자동 수정 루프는 의도적으로 만들지 않았습니다. `ABORTED`, `UNSTABLE`, 진행 중 상태를 실패로 읽지 않도록 결과 값도 구분합니다.

이 흐름에서 두 가지 결함이 나왔습니다.

- **결과가 아직 없는 빌드를 지나쳐 버렸습니다.** 결과 값이 비어 있는 순간 감시 포인터만 앞으로 옮겨서, 그 빌드의 알림을 영영 잃었습니다. 결과가 확정될 때까지 포인터를 붙잡아 두도록 고쳤습니다.
- **「한 번만 알린다」가 매 주기 초기화됐습니다.** 차단 사유 통보를 억제하는 기록을, 조건 1을 통과할 때마다 사유를 가리지 않고 지워서 같은 통보가 폴링 주기마다 반복될 수 있었습니다. 지울 때는 해소된 그 사유만 지우도록 바꿨습니다.

## 통지 5: 일간·주간 요약

실시간 알림과 별개로, 정해진 시각에 로그를 집계해 보내는 요약 보고가 둘 있습니다. 둘 다 cron으로 돌고 같은 봇 경로로 나갑니다.

- **일간 요약**: 평일 퇴근 무렵, 그날의 폴링, 세션 실행, 처리 결과를 집계합니다.
- **주간 요약**: 주말 직전, 한 주 동안 사람이 개입한 정도와 리드타임 같은 추이를 봅니다.

요약에는 한계가 하나 있습니다. 폴러를 멈춰 둔 기간에는 새 로그가 쌓이지 않으니 집계 값이 0에 가까워질 것으로 예상되는데, 0이 「한가했다」인지 「멈춰 있었다」인지는 요약만으로 구분되지 않습니다. 이 문제는 8편에서 다시 다룹니다.


## 알림 경로를 줄이면 생기는 대가

멘션을 담당자와 보고자로 좁히고 시스템 알림에서 멘션을 뺀 결과, 폴러 장애는 채널을 보는 사람만 압니다. 소음과 탐지 속도 사이에서 소음을 줄이는 쪽을 골랐고, 그 대가를 알고 쓰는 것이 중요합니다.

## 정리

- 트래커 쓰기는 MCP 쓰기 도구를 `--disallowedTools`로 빼고, 자동화 계정의 REST 호출로 옮겼습니다. 코멘트 본문에 고정 접두어를 붙여 기계가 쓴 글임을 드러냅니다.
- Slack은 스레드를 쓸 수 있는 봇 한 경로로 보내고, 멘션은 그 이슈의 담당자와 보고자로만 한정했습니다. 다른 사람의 ID를 프롬프트에 넣지 않는 것이 가장 확실한 차단이었습니다.
- 배포 실행과 결과 알림은 세션이 아니라 폴러가 맡고, 판정에 필요한 값을 모르면 빌드를 걸지 않습니다. 알리는 것은 이상이 있을 때뿐입니다.

## 다음 편 예고

6편에서는 이 통지 경로들이 사고 없이 돌게 받쳐 주는 안전장치, 즉 에이전트의 자기 수정 차단, 연속 3회 기준 헬스체크, 쓰기 권한 게이트, 중복·재알림·정체 가드, 로그 보존을 다룹니다. 그리고 게이트가 「사람에게 해 달라는 요청」을 「승인」으로 잘못 읽어 되돌릴 수 없는 전이를 한 사례와, 그 뒤 바꾼 판정 규칙을 정리합니다.

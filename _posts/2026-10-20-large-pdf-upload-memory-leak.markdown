## 문제와 배경

[지난 글](/blog/2026/01/17/retry-backoff-strategy-worker-monitoring.html)에서는 워커를 감시하고 타임아웃을 거는 구조를 다뤘습니다. 이번 글은 그 워커들이 실제로 대용량 PDF를 처리할 때 메모리를 어떻게 쓰는지, 그리고 그 메모리가 어디서 새는지를 다룹니다.

운영 서버 한 대가 특정 시점에 응답 불능 상태가 되어 재부팅한 적이 있습니다. 조사해 보니 두 가지가 겹쳐 있었습니다.

1. 업로드·파싱 워커들이 대용량 PDF를 처리하는 동안 메모리를 평소보다 뚜렷하게 많이 썼습니다.
2. 짧은 시간에 대용량 파일 I/O가 몰리자, 원격 저장소를 로컬 경로처럼 마운트해 주는 FUSE(Filesystem in Userspace) 기반 프로세스가 D-state(uninterruptible sleep)에 들어갔습니다. 이 상태는 커널이 응답을 기다리며 걸어 둔 잠금이라 `kill -9`로도 끊을 수 없고, 그 프로세스에 발이 묶인 다른 프로세스까지 연쇄로 멈춰 서버 전체가 응답 불능에 빠졌습니다.

| 겉으로 보이는 증상 | 실제 원인 |
|---|---|
| 서버 메모리 사용량이 평소보다 뚜렷하게 높음 | 업로드 워커가 파일 전체를 메모리에 올린 채 처리 |
| 특정 프로세스가 `D` 상태로 멈춰 `kill`도 안 먹힘 | FUSE 마운트가 동시 I/O를 감당하지 못해 블로킹 |
| 장애 복구 후에도 메모리가 서서히 다시 올라감 | 워커 쪽에 별도의 장기 메모리 누수가 존재 |

이 장애를 계기로 업로드 경로를 먼저 고쳤고, 같은 코드베이스의 워커를 더 들여다보면서 장애와는 별개로 운영 중 서서히 쌓이는 누수 패턴도 여럿 찾아 정리했습니다. 둘은 증상이 비슷해 보이지만 원인은 다르므로 나눠서 씁니다.

## 접근

업로드 경로부터 추적했습니다. 요청으로 들어온 파일을 검증하고 저장하는 코드가 파일 내용을 통째로 bytes로 읽어 변수에 들고 있다가, 해시를 계산하고, 그 bytes를 다시 디스크에 썼습니다. 큰 파일일수록 그 bytes가 고스란히 메모리에 남아 있는 구조였습니다. 게다가 업로드 검증과 저장을 서로 다른 함수가 각각 처리하면서, 같은 파일을 한 번 읽어 크기를 확인하고 처음으로 되돌아가 다시 읽어 저장하는 흐름도 섞여 있어 읽기 자체가 두 번 일어났습니다.

FUSE 마운트 쪽은 애플리케이션 로직이 아니라 I/O 패턴이 문제였습니다. 여러 워커가 동시에 원격 저장소에서 대용량 파일을 직접 읽으면, FUSE는 그 요청들을 처리할 스레드 수에 한계가 있어 큐가 밀리고, 밀린 상태가 길어지면 D-state로 넘어갑니다. 마운트 자체를 없애는 선택지는 없었으므로(상시 마운트가 필요한 구조였습니다), 동시에 몰리는 I/O 양을 줄이는 쪽으로 방향을 잡았습니다.

이 두 가지를 고치고 나서, 같은 워커 군을 메모리 추이 관점에서 다시 훑었습니다. 장애와 무관하게도 파이프라인 단계 사이에 넘겨주는 중간 데이터가 다음 단계가 끝날 때까지 불필요하게 살아 있거나, DB 세션을 여러 단계에 걸쳐 하나로 유지하거나, 무거운 객체를 매 작업마다 새로 만드는 패턴이 여럿 있었습니다. 장애를 일으킨 「한 번에 몰리는 메모리」 문제와, 「시간이 지나며 서서히 쌓이는」 누수 문제는 따로 다뤄야 한다고 판단했습니다.

## 구현

### 업로드를 스트리밍으로 바꾸기

업로드 처리를 청크 단위 스트리밍으로 바꿔, 파일 전체를 메모리에 올리지 않고 받은 만큼 바로 디스크에 쓰도록 고쳤습니다. 첫 청크에서 매직 바이트를 확인해 PDF가 아닌 파일을 조기에 거르고, 해시도 전체를 들고 있지 않고 청크가 들어올 때마다 갱신합니다.

```python
import hashlib
import os
import time

async def save_upload_streaming(upload_file, max_size: int, temp_dir: str) -> tuple[str, str, int]:
    """청크 단위로 받아 바로 디스크에 쓴다. 전체 bytes를 메모리에 들고 있지 않는다."""
    hasher = hashlib.sha256()
    total_size = 0
    is_first_chunk = True
    tmp_path = os.path.join(temp_dir, f"upload_{int(time.time() * 1000)}.tmp")

    with open(tmp_path, "wb") as out:
        async for chunk in upload_file:
            if is_first_chunk:
                if not chunk.startswith(b"%PDF-"):
                    raise ValueError("PDF 형식이 아닙니다")
                is_first_chunk = False
            hasher.update(chunk)
            out.write(chunk)
            total_size += len(chunk)
            if total_size > max_size:
                os.remove(tmp_path)
                raise ValueError("허용 크기를 초과했습니다")

    return hasher.hexdigest(), tmp_path, total_size
```

이 함수가 끝나면 호출부는 임시 파일 핸들을 곧바로 닫습니다. 업로드 라이브러리가 내부적으로 스풀 파일을 쓰는 경우, 핸들을 닫지 않으면 응답을 반환할 때까지 그 스풀 파일이 메모리 또는 임시 디스크를 계속 점유합니다.

```python
try:
    file_hash, local_path, size = await save_upload_streaming(upload_file, MAX_PDF_SIZE, TEMP_DIR)
finally:
    try:
        await upload_file.close()  # 스풀 파일 즉시 정리
    except Exception:
        pass
```

검증과 저장을 분리해 두 번 읽던 기존 흐름은 이 한 번의 스트리밍 패스로 합쳤습니다. 크기 제한 값도 설정 모듈과 엔드포인트 코드에 각각 다르게 박혀 있던 것을 설정 한 곳으로 모아, 환경별로만 값을 바꿀 수 있게 정리했습니다.

### 원격 파일 접근을 한 번으로 압축하기

파싱 단계에서 같은 원격 경로(FUSE 마운트 아래)를 여러 번 오가며 읽는 대신, 처리를 시작할 때 로컬 임시 경로로 한 번만 복사해 두고 그 뒤로는 로컬 파일만 건드리도록 바꿨습니다. 여러 워커가 같은 원격 경로를 동시에 반복해서 두드리는 빈도를 줄이는 것이 목적이라, 복사 한 번의 비용은 감수할 만했습니다.

```python
import asyncio
import shutil

async def to_local_cache(remote_path: str, cache_dir: str, job_id: str) -> str:
    local_path = f"{cache_dir}/cache_{job_id}.pdf"
    await asyncio.to_thread(shutil.copy2, remote_path, local_path)
    return local_path
```

복사해 둔 로컬 파일은 해당 작업이 끝나는 `finally` 블록에서 예외 여부와 상관없이 지웁니다. 워커가 중간에 재시작되는 경우까지 고려해, 시작 시점에 이전 작업이 남긴 캐시 파일이 있으면 먼저 정리하는 루틴도 같이 넣었습니다.

### 파이프라인 단계 사이의 중간 데이터 정리

업로드 문제와 별도로 찾은 누수 중 비중이 큰 것은, 파싱 단계에서 만든 페이지 텍스트·청크 목록 같은 큰 데이터가 색인 단계까지 끝날 때까지 그대로 들고 있던 부분이었습니다. 다음 단계에 실제로 필요하지 않은 값은 넘기기 전에 지우도록 했습니다.

```python
def drop_unused_context(context: dict, keep_keys: set[str]) -> None:
    for key in list(context.keys()):
        if key not in keep_keys:
            context.pop(key, None)
```

DB 세션도 파싱부터 색인까지 하나로 묶어 들고 있던 것을, 단계별로 열고 닫도록 나눴습니다. 세션을 쪼개면 연결을 더 자주 맺고 끊지만, 그 대신 커넥션 풀을 오래 점유하지 않습니다.

```python
async def run_pipeline(job, session_factory):
    async with session_factory() as db:
        parsed = await run_parse(db, job)

    async with session_factory() as db:
        await run_index(db, job, parsed)
```

그 밖에, 매 작업마다 새로 만들던 무거운 파싱 객체를 워커 생성 시 한 번만 만들어 재사용하도록 바꿨고, 검색 엔진에 대량으로 색인 요청을 보낼 때 반환되는 대형 응답 객체를 배치 처리 직후 명시적으로 비우도록 했습니다.

## 함정과 트레이드오프

- **D-state는 애플리케이션 레벨에서 손쓸 수 없습니다.** `kill -9`도 듣지 않고, 그 프로세스를 기다리는 다른 프로세스까지 멈춥니다. 재발을 막는 방법은 결국 그 프로세스에 몰리는 동시 I/O 양을 애초에 줄이는 것뿐이었습니다. 사후 대응이 아니라 사전에 I/O 패턴을 설계에 반영해야 하는 종류의 문제입니다.
- **도달하지 않는 코드도 정리 대상입니다.** 설정값이 비어 있어 운영에서는 실행되지 않던 OCR 코드 경로가 무거운 의존성과 함께 남아 있었습니다. 당장 실행되지 않는다고 안전한 것은 아니므로, 쓰지 않기로 확정된 경로는 설정으로 꺼 두기보다 코드째 지웠습니다.
- **세션을 단계별로 쪼개는 것은 공짜가 아닙니다.** 커넥션을 더 자주 맺고 끊으므로, 풀 설정에 따라서는 쪼개기 전보다 연결 생성 비용이 늘 수 있습니다. 오래 점유하는 비용과 자주 맺고 끊는 비용 중 무엇이 더 아픈지는 트래픽 패턴에 따라 다릅니다.
- **네이티브 확장 라이브러리는 파이썬 GC가 보는 메모리와 다르게 움직입니다.** 비슷한 시기에 텍스트 추출 품질을 개선하려고 C로 작성된 파싱 엔진을 일부 경로에 도입하는 검토가 있었는데, 이런 라이브러리는 자체적으로 메모리를 관리하는 경우가 많아 파이썬 쪽 객체 참조 카운트만 보고는 실제 메모리 사용량을 다 설명할 수 없습니다. 메모리 문제를 조사할 때는 애플리케이션 코드뿐 아니라 쓰고 있는 네이티브 확장의 메모리 특성도 확인 대상에 넣어야 합니다. 라이선스나 운영 적용 여부가 불확실한 라이브러리는 범위를 제한한 시험 기간을 정해 두고 검증한 뒤 정식 도입을 결정하는 편이 안전합니다.

## 정리

- 대용량 파일을 다루는 업로드 경로는 전체를 메모리에 올리지 않는 스트리밍 처리가 기본이어야 하고, 검증과 저장을 분리하다 같은 파일을 두 번 읽는 구조가 생기지 않았는지 따로 확인해야 합니다.
- 원격 파일시스템에 여러 워커가 동시에 반복 접근하는 구조는 메모리 문제와 별개로, 마운트 프로세스 자체를 끊어낼 수 없는 블로킹 상태(D-state)로 몰아갈 수 있습니다. 동시 접근 횟수를 줄이는 설계가 필요합니다.
- 장애를 일으키는 「한 번에 몰리는」 메모리 문제와, 운영 중 서서히 쌓이는 누수 문제는 원인과 해법이 다르므로 나눠서 조사하는 편이 효율적입니다.
- 파이프라인 단계 사이에 넘기는 중간 데이터는 다음 단계에 필요한 만큼만 남기고 정리하고, 여러 단계를 아우르는 DB 세션은 단계별로 쪼개는 쪽이 커넥션 점유 측면에서 안전합니다.

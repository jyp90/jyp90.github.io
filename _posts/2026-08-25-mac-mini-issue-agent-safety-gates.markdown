5편에서는 에이전트가 사람에게 알리는 다섯 가지 통지 경로를 다뤘습니다. 이 편에서는 그 경로들이 사람이 보지 않는 시간에도 사고 없이 돌게 받쳐 주는 안전장치, 그리고 게이트에서 실제로 일어난 오판 사례를 다룹니다. 전제는 5편과 같습니다. **에이전트에게 「하지 마라」를 프롬프트로만 말하면 언젠가 어깁니다.** 그래서 지켜야 하는 규칙은 가능한 한 프롬프트 바깥, 즉 훅·권한 설정·폴러 코드에 둡니다.

## 안전장치 1: 에이전트가 전역 설정과 자기 자신을 고치지 못하게

무인 세션이 고치면 안 되는 파일이 있습니다. 하나는 서비스 전체에 영향을 주는 설정·빌드 파일(`.env`, `*.properties`, `application*.yml`, `web.xml`, `pom.xml`, `build.gradle`, `package.json` 등)이고, 다른 하나는 **에이전트 자신**(자동화 런타임 디렉터리, `~/.claude/settings.json`, 훅, 플러그인, LaunchAgents, 상태·자격 파일)입니다.

뒤쪽이 더 중요합니다. 에이전트가 자기 코드를 고칠 수 있으면, 다음 실행의 규칙을 스스로 바꾸고 그 변경을 막는 장치까지 함께 바꿀 수 있습니다.

이 차단은 `Edit`·`Write`에 거는 `PreToolUse` 훅으로 구현했습니다. 대상 경로가 금지 목록에 걸리면 종료 코드 2로 도구 호출을 거부합니다. 훅의 동작 방식과 함정은 [Claude Code 훅을 직접 써 보며 부딪힌 함정 6가지](/blog/2026/09/30/claude-code-hook-pitfalls.html)에 정리해 두었습니다.

```python
#!/usr/bin/env python3
import json, os, sys, fnmatch
from pathlib import Path

if os.environ.get("ISSUE_AGENT") != "1":
    sys.exit(0)  # 사람이 연 일반 세션은 건드리지 않습니다

HOME = Path.home()
SELF_PATHS = [HOME / "issue-agent", HOME / ".claude" / "settings.json",
              HOME / ".claude" / "hooks", HOME / "Library" / "LaunchAgents"]
SENSITIVE = ["*.env", ".env*", "*.properties", "application*.yml",
             "web.xml", "pom.xml", "build.gradle", "package.json"]

def is_self(p: Path):
    return any(p == s or s in p.parents for s in SELF_PATHS)

def scoped_allow(p: Path):
    # 폴러가 주입한 범위만 인정합니다. 세션은 이 값을 세울 수 없습니다.
    scope = json.loads(os.environ.get("ISSUE_AGENT_EDIT_SCOPE", "{}"))
    root = scope.get("worktree")
    if not root or Path(root).resolve() not in p.parents:
        return False
    rel = str(p.relative_to(Path(root).resolve()))
    return any(fnmatch.fnmatch(rel, g) for g in scope.get("allow_globs", []))

event = json.load(sys.stdin)
target = Path(event["tool_input"].get("file_path", "")).resolve()

if is_self(target):
    print("자동화 런타임과 권한 설정은 수정할 수 없습니다.", file=sys.stderr)
    sys.exit(2)
if any(fnmatch.fnmatch(target.name, g) for g in SENSITIVE) and not scoped_allow(target):
    print("전역 설정·빌드 파일은 수정할 수 없습니다.", file=sys.stderr)
    sys.exit(2)
sys.exit(0)
```

설계에서 신경 쓴 점은 다음과 같습니다.

- **자동화 세션에서만 켭니다.** 폴러가 세션을 띄울 때 환경변수를 넣고, 훅은 그 값이 있을 때만 판정합니다. 사람이 직접 여는 세션은 영향을 받지 않습니다.
- **좁게 여는 통로는 폴러만 엽니다.** 화면 문구 리소스처럼 서버 동작을 바꾸지 않는 파일은 열어 줄 필요가 있었습니다. 이때 세 조건(대상이 그 이슈의 작업 디렉터리 안, 허용 글로브와 일치, 자기 수정 대상 아님)이 모두 참일 때만 통과시키고, 그 범위 값은 폴러가 주입합니다. 세션이 스스로 범위를 넓히는 것은 자기 수정 차단이 막습니다.
- **글로브는 경로를 앵커해서 씁니다.** 파일명 패턴 한 줄만 적으면 테스트 리소스나 루트의 같은 이름 파일까지 함께 열립니다. 위 예시처럼 작업 디렉터리 기준 상대경로로 매칭하고, 허용 글로브도 `*/src/main/resources/messages/*.properties`처럼 위치를 고정해서 적습니다.
- **분류 기준은 한 곳에 둡니다.** 훅과 폴러가 「어떤 경로가 민감한가」를 각자 따로 적으면 목록이 어긋나고, 그 어긋남은 오류 없이 오작동합니다. 실제로 문서는 자동 처리 대상이라고 안내한 파일을 훅은 막고 있던 상태가 발견됐습니다. 지금은 경로 분류 모듈 하나를 둘이 함께 가져다 씁니다.

한 가지 함정이 있었습니다. 사람이 수동으로 쓰려고 만든 「전체 예외 플래그」가 훅 맨 앞에서 무조건 통과시키도록 돼 있어서, 그 플래그를 세우면 문구 파일뿐 아니라 자기 수정 차단까지 함께 풀렸습니다. 같은 훅을 `Bash`에도 걸어 둔 상태에서 이 플래그로 crontab 삭제 명령까지 통과하는 것을 직접 확인했습니다. 폴러는 이 플래그를 절대 넣지 않지만, 「간편한 예외」로 보이는 장치가 가장 넓은 구멍이 될 수 있다는 점은 주석과 문서에 경고로 남겼습니다.

### 「못 고쳤다」의 원인은 훅만이 아닙니다

에이전트가 파일을 고치지 못했다는 보고를 받으면 원인이 세 층 중 어디인지 먼저 가립니다.

| 층 | 무엇이 막는가 | 여는 방법 |
|---|---|---|
| 직접 만든 훅 | 위 경로 차단 | 허용 범위 설정 |
| Claude Code 자동 모드 분류기 | 명령 형태나 의도에 대한 하네스 판단 | 설정으로 열리지 않습니다. 같은 일을 전용 도구나 단순한 명령 형태로 하면 통과하는 경우가 많습니다 |
| 세션 자신의 판단 | 모델의 자기검열 | 세션이 이어 읽는 이슈 메모를 사람이 정정합니다 |

훅은 열려 있었는데(첫 수정이 실제로 통과한 것까지 확인) 세션이 성공한 수정을 스스로 되돌리고 인계 메모에 「재시도 금지」를 남긴 경우가 있었습니다. 다음 실행들은 그 메모를 읽고 시도 자체를 하지 않았습니다. 이때 훅을 더 넓히는 것은 아무 효과가 없습니다. 또 상시 프롬프트에 「이 파일은 안전장치 대상이 아니다」라고 적으려는 시도 자체가 분류기에 막혔습니다. 가드를 여는 일과 세션이 그것을 실제로 쓰게 하는 일은 별개로 다뤄야 합니다.

## 안전장치 2: 헬스체크와 연속 3회 실패 기준

헬스체크는 부팅 직후 한 번, 그리고 매시 정각에 cron으로 돌고, **이상이 있을 때만** Slack에 경고를 보냅니다. 보는 항목은 다음과 같습니다.

- 폴러의 생존 신호 파일이나 로그가 일정 시간 이상 조용한가
- 「처리 중」 상태가 일정 시간 이상 바뀌지 않았는가
- crontab에 폴러 줄이 실제로 있는가
- 자격 증명 파일 권한이 소유자 전용(`600`)인가
- `claude` 실행 파일이 동작하는가
- 보조 디스패처의 생존 신호와 연속 실패 횟수

실패 기준은 「한 번 실패」가 아니라 **「연속 3회 실패」**입니다. 트래커 검색 실패나 세션 실행 실패가 한두 번 나는 것은 네트워크나 일시 오류로 흔한 일이라, 그때마다 알리면 경고가 무시되기 시작합니다. 연속 횟수가 기준을 넘으면 경고를 보내고, 같은 경고는 정해 둔 시간(예: 30분) 안에 다시 보내지 않습니다.

```json
{
  "health_alert": {
    "consecutive_tracker_failures": 3,
    "consecutive_session_failures": 3,
    "stale_processing_repeats": 2,
    "renotify_after_minutes": 30
  }
}
```

운영하면서 알게 된 점이 하나 있습니다. 폴러를 일부러 멈출 때는 헬스체크도 같이 멈춰야 합니다. 폴러만 멈추면 헬스체크가 「폴러가 조용하다」는 경고를 매시 보냅니다. 반대로 둘 다 멈춰 두고 잊으면, 시스템 전체가 조용히 서 있어도 아무도 모릅니다. 이 문제도 8편에서 이어서 다룹니다.

## 안전장치 3: 쓰기 권한 게이트

앞에서 트래커 쓰기를 REST 호출로 옮겼다고 했습니다. 세션이 `curl`을 실행하려면 `settings.json`의 `permissions.allow` 규칙에 걸려야 합니다. 여기서 다음 사실들을 확인했습니다. 일부는 공식 문서에 근거가 있고, 일부는 `--permission-mode dontAsk`(분류기 없이 규칙만 적용하는 모드)로 격리 실험해 관찰한 결과입니다.

- **규칙은 서브커맨드마다 따로 매칭됩니다.** 공식 문서에 「규칙은 각 서브커맨드와 독립적으로 일치해야 한다」고 나옵니다. 그래서 `source ~/.creds && curl ...`을 통째로 allow에 적어 두면 어느 서브커맨드와도 맞지 않습니다.
- **`source`는 정확히 일치하는 규칙을 줘도 통과하지 않았습니다.** 임의 코드를 실행하는 명령이라 허용 대상이 아닌 것으로 보입니다. 공식 문서의 계약이 아니라 직접 관찰한 결과입니다.
- **명령에 `$변수`가 있으면 매칭되지 않았습니다.** 리터럴 URL 대신 `$BASE/rest/...`처럼 쓰면 규칙과 맞지 않습니다. 「분석할 수 없는 명령은 승인을 요청한다」는 공식 설명과 맞아떨어집니다.

자격 증명 파일을 `source`하고 `-u "$USER:$TOKEN"`으로 호출하는 흔한 형태는 이 셋에 모두 걸립니다. 즉 규칙이 처음부터 죽어 있었습니다. 그런데도 코멘트가 대체로 올라갔던 것은 자동 모드 분류기가 매번 재량으로 통과시켜 줬기 때문이고, 같은 명령이 어떤 실행에서는 통과하고 어떤 실행에서는 막힌 이유도 그것이었습니다. 한 번 막힌 뒤 형태를 바꿔 다시 시도하면 분류기가 그것을 「차단 우회 시도」로 보고 더 강하게 막는 것도 관찰했습니다.

해결은 규칙을 되살리는 것이 아니라 **래퍼 스크립트 하나로 쓰기 경로를 모으는 것**이었습니다.

```bash
#!/usr/bin/env bash
# tracker-write.sh comment|transition <ISSUE-KEY> <payload.json>
set -euo pipefail
readonly BASE="https://tracker.example.com/rest/api/3/issue"
readonly CRED="$HOME/issue-agent/secrets/tracker.netrc"   # 600 권한

verb="$1"; key="$2"; payload="$3"
[[ "$key" =~ ^[[:upper:]][[:upper:][:digit:]]*-[[:digit:]]+$ ]] || { echo "잘못된 이슈 키" >&2; exit 2; }
[[ -f "$payload" ]] || { echo "페이로드 파일 없음" >&2; exit 2; }

case "$verb" in
  comment)    url="$BASE/$key/comment" ;;
  transition) url="$BASE/$key/transitions" ;;
  *) echo "지원하지 않는 동작" >&2; exit 2 ;;
esac

code=$(curl -sS -o /dev/null -w '%{http_code}' --netrc-file "$CRED" \
  -H 'Content-Type: application/json' -X POST --data @"$payload" "$url")
[[ "$code" == 2* ]] || { echo "HTTP $code" >&2; exit 1; }
```

```json
{
  "permissions": {
    "allow": [
      "Bash(/Users/agent/issue-agent/bin/tracker-write.sh comment *)",
      "Bash(/Users/agent/issue-agent/bin/tracker-write.sh transition *)"
    ]
  }
}
```

설계의 핵심은 **URL을 인자로 받지 않는다**는 점입니다. URL, 자격 증명, HTTP 메서드는 스크립트가 고정하고, 와일드카드가 덮는 것은 이슈 키와 페이로드 파일 경로뿐입니다. 세션은 페이로드를 `Write` 도구로 파일에 쓰고 경로만 넘기므로 셸 따옴표 문제도 사라집니다.

`curl` 자체를 허용하되 자격 증명만 설정 파일로 빼는 더 작은 수정도 가능했습니다. 채택하지 않은 이유는 규칙 중간의 `*`가 임의의 `curl` 플래그를 허용하기 때문입니다. `-o`로 홈 디렉터리의 셸 설정 파일을 덮어쓰는 명령도 그 규칙에 매칭됩니다. 죽은 규칙을 그대로 살리면 의도한 적 없는 권한을 새로 여는 셈입니다.

규칙을 교체할 때는 새 규칙을 먼저 넣고 매칭을 확인한 뒤 옛 규칙을 지웠습니다. 그리고 「폴러가 만드는 명령 문자열이 실제 `settings.json`의 allow 규칙과 매칭되는가」를 확인하는 회귀 테스트를 두었습니다. 규칙이 죽어 있어도 자동 모드에서는 분류기가 대신 통과시켜 주므로 겉으로는 동작하는 것처럼 보입니다. **allow 규칙은 「적었다」가 아니라 「매칭된다」를 확인해야 합니다.**

## 안전장치 4: 중복 실행, 재알림, 정체

무인 자동화가 겪기 쉬운 실패 세 가지에 각각 가드를 둡니다.

- **중복 실행**: 폴링 주기는 시작하자마자 잠금 파일을 잡습니다. 직전 주기가 긴 세션 때문에 아직 끝나지 않았다면 이번 주기는 조용히 끝냅니다. 같은 이슈에 세션 두 개가 동시에 뜨는 일을 막습니다.
- **완료 이슈 재알림**: 배포 감시는 빌드에 포함된 커밋 메시지에서 이슈 키를 뽑아 알림을 보냅니다. 그런데 이미 종결된 이슈의 커밋도 새 빌드에 계속 포함되므로, 빌드가 돌 때마다 끝난 이슈에 알림이 다시 나갔습니다. 종결 상태인 이슈는 건너뛰는 가드를 추가했고, 필요하면 배포 감시 전체를 설정 스위치 하나로 끌 수 있게 했습니다.
- **처리 정체**: 「처리 중」 상태가 일정 시간 이상 바뀌지 않거나, 같은 정체가 연속으로 관측되면 경고합니다. 세션이 오류 없이 멈춰 있는 경우를 잡기 위한 것입니다.

중복 쪽에서는 별개로 남은 위험도 있습니다. HTTP 세션의 재시도 설정이 POST까지 재시도하도록 돼 있어서, 응답만 늦게 온 경우 같은 코멘트가 여러 번 게시될 수 있습니다. 읽기용 세션과 쓰기용 세션의 재시도 정책을 나누는 것이 맞습니다.

같은 맥락에서 상태 파일을 `write_text` 한 번으로 덮어쓰면, 쓰는 도중 프로세스가 죽었을 때 상태 전체가 사라집니다. 임시 파일에 쓰고 `os.replace`로 바꿔치기하는 원자적 쓰기가 필요합니다.

## 안전장치 5: 로그 정리

로그는 매일 새벽 cron으로 정리하고 30일만 보존합니다. 활성 로그 파일은 줄 앞의 날짜를 보고 오래된 줄을 잘라내고, 순환된 백업 파일은 통째로 지웁니다.

```bash
# 매일 04:30
30 4 * * * /Users/agent/issue-agent/bin/log-cleanup.sh >> /Users/agent/issue-agent/logs/cleanup.log 2>&1
```

이 잡은 폴러를 멈춘 기간에도 계속 돌게 둡니다. 멈춘 기간의 로그가 남아 있어야 나중에 「왜 멈췄고 언제 다시 돌았는지」를 따라갈 수 있습니다.

## 게이트 오판: 「사람에게 해 달라는 요청」을 「승인」으로 읽은 경우

에이전트의 워크플로에는 사람의 판단을 기다리는 게이트가 여러 개 있습니다. 게이트에서 에이전트는 사람이 남긴 코멘트를 읽고 통과인지 아닌지를 판정한 뒤 상태를 옮깁니다. 여기서 가장 비싼 오판이 나왔습니다.

### 무슨 일이 있었나

개발 서버 배포가 끝난 이슈에 보고자가 이렇게 남겼습니다. 「개발 서버에서 수정 확인했습니다. 테스트 서버로 넘겨 주세요.」

보고자의 뜻은 「담당 개발자가 테스트 서버에 배포해 주면 거기서 다시 보겠다」였습니다. 에이전트는 이것을 「이 단계 검증이 끝났으니 다음 단계로 가자」로 읽고, 이슈를 검수 서버 단계로 옮긴 뒤 검수 반영 요청까지 올렸습니다.

### 원인은 세 겹이었습니다

1. **게이트에서 앞으로 갈 수 있는 곳이 하나뿐이었습니다.** 그 상태는 개발 서버와 테스트 서버 검증을 한 상태로 묶고 있었고, 통과 조건은 「보고자 검증 완료」 하나, 전진 전이도 검수 서버 단계 하나뿐이었습니다. 통과로 읽는 순간 갈 곳이 정해져 있었습니다. 게이트는 사람이 원한 곳이 아니라 **워크플로가 갈 수 있는 곳**으로 움직입니다.
2. **문장의 목적어를 잘못 잡았습니다.** 「테스트 서버로 넘겨 주세요」에서 옮길 대상은 작업물이고 목적지는 환경입니다. 에이전트는 이를 단계 이동 요청으로 읽었습니다. 문장에는 검수 서버나 머지에 대한 언급이 전혀 없었습니다.
3. **자기모순을 걸러내지 못했습니다.** 같은 실행에서 에이전트는 코멘트에 「테스트 서버 반영은 담당 개발자가 직접 해야 합니다」라고 써 놓고, 그 일이 끝나기 전에 상태를 올렸습니다. 남은 사람 조치를 스스로 적어 놓고도 전이한 것입니다.

그리고 이 워크플로에는 검수 서버 단계에서 이전 단계로 돌아가는 전이가 없었습니다. 오판이 곧 되돌릴 수 없는 결과가 됐고, 사람이 트래커 화면에서 직접 옮겨야 했습니다.

### 바꾼 규칙

에이전트의 게이트 계약에 다음을 넣었습니다.

- 게이트 코멘트가 **승인**인지 **사람에게 하는 요청**인지 먼저 가릅니다.
- 요청이면 통과가 아니라 「사람 조치 대기」입니다. 상태를 그대로 두고, 그 일을 할 사람을 멘션해 요청을 전달만 합니다.
- 판별 기준은 **행위 주체**입니다. 그 일을 하는 주체가 에이전트가 아니면 전이하지 않습니다. 에이전트가 구조적으로 할 수 없는 일(테스트 서버 배포, 검수 브랜치 PR 생성과 머지, 운영 반영, 인프라 변경)은 무조건 여기에 해당합니다.
- 이 게이트는 「다음 단계로 올려도 된다」는 **명시적 승인일 때만** 전이합니다.
- **애매하면 전이하지 않습니다.** 전이는 되돌리기 어렵고, 전이하지 않으면 사람이 한 마디 더 하면 그만입니다.

남은 개선점도 적어 두었습니다. 지금 판정은 「넘겨 달라」, 「배포해 달라」 같은 요청 어휘를 걸러내는 방식이라, 새 표현이 나오면 다시 뚫립니다. 방향을 뒤집어 **명시적 승인이 있을 때만 통과, 나머지는 전부 사람 조치 대기**로 바꾸는 편이 안전합니다. 전이 직전에 「이 코멘트에 사람이 해야 할 남은 일을 적었는가, 그렇다면 전이하지 않는다」는 자기 점검 한 줄을 두는 것도 비용 대비 효과가 큽니다.

```text
[전이 직전 점검]
1. 이 판정의 근거 문장은 "다음 단계로 가도 된다"는 승인인가?
2. 그 문장이 요구하는 행위의 주체는 누구인가? 에이전트가 아니면 → 전이하지 않음
3. 내가 이번에 쓴 코멘트에 사람이 해야 할 남은 일이 적혀 있는가? 있으면 → 전이하지 않음
4. 위 셋 중 하나라도 확신이 없으면 → 전이하지 않고 확인을 요청
```

### 비슷한 오판이 다른 모양으로도 나옵니다

이후에도 같은 계열의 판단 문제가 두 번 더 나왔습니다.

- **배포 실행 보고는 검증 판정이 아닙니다.** 개발 서버 검증 단계에서 담당 개발자가 「개발 서버에 배포했습니다」라고 남겼습니다. 승인처럼 읽히지만 배포했다는 보고일 뿐, 누구도 화면을 확인하지 않았습니다. 이 단계는 개발자가 배포하고 보고자가 화면을 확인하는 릴레이이고, 게이트 판정 신호는 보고자의 확인입니다. 에이전트는 상태를 유지한 채 보고자에게 확인을 요청했고, 보고자가 확인 항목을 하나씩 회신한 뒤에 통과했습니다.
- **「반영됐나」에는 「어느 서버에」가 먼저입니다.** 요구 사항이 이미 구현돼 있던 이슈에서, 에이전트는 「어느 서버에도 반영되지 않아 확인할 수 없다」는 판단을 여러 번의 실행 동안 반복했습니다. 검수와 운영 서버는 릴리스 브랜치에서 배포되지만 개발 서버는 개발 브랜치에서 배포됩니다. 서버별로 다시 보니 개발 서버에는 처음부터 들어 있었습니다. 판정은 서버마다 따로 내야 하고, 확인은 `git branch -r --contains <커밋>` 한 줄이면 충분합니다. 잘못된 배포 판정은 멀쩡한 이슈를 게이트에 세워 멈추게 합니다.

같은 이슈에서 나온 규칙이 하나 더 있습니다. 요구가 이미 구현돼 있으면 새로 만들지 않는 것이 지시를 따르는 것이고, 변경이 없으면 개발 브랜치 승격도 하지 않습니다. 변경 없이 승격하면 그 이슈 명의로 다른 작업자의 커밋만 공용 브랜치에 올라갑니다. 대신 요구 항목마다 어디서 충족되는지를 근거와 함께 적어서, 「확인하지 않고 넘긴 것」과 구별되게 합니다.

## 함정과 트레이드오프

- **안전장치가 두 벌이면 언젠가 어긋납니다.** Slack 발송 함수, 경로 분류, 배포 감시가 각각 두 곳에 구현돼 있던 시기가 있었습니다. 어긋남은 오류를 내지 않고 조용히 오작동합니다. 판정 기준은 한 곳에 두고 양쪽이 가져다 쓰게 합니다.
- **권한 규칙은 「적었다」가 아니라 「매칭된다」로 확인합니다.** 자동 모드의 분류기는 죽은 규칙을 대신 메워 주므로, 규칙이 동작하는지는 분류기를 빼고 실행해 봐야 알 수 있습니다.
- **게이트 판정은 어휘가 아니라 목적지로 합니다.** 「이 사람이 지금 다음 단계로 올리자고 말했는가」를 묻습니다. 요청 어휘 목록으로 막는 방식은 새 표현 앞에서 다시 뚫립니다.
- **예외 플래그가 가장 넓은 구멍이 될 수 있습니다.** 사람용 우회 수단은 기본 차단보다 앞에서 평가되기 쉽고, 그러면 자기 수정 차단까지 함께 풀립니다.

## 정리

- 안전장치는 자기 수정 차단, 연속 3회 기준 헬스체크, 쓰기 권한 게이트, 중복·재알림·정체 가드, 로그 보존으로 이뤄집니다.
- 쓰기 권한 게이트는 URL과 자격 증명을 고정한 래퍼 스크립트로 모으고, allow 규칙은 「적었다」가 아니라 실제로 매칭되는지 분류기 없이 확인해야 합니다.
- 게이트에서는 승인과 요청을 먼저 가르고, 행위 주체가 에이전트가 아니면 전이하지 않으며, 애매하면 멈춥니다.

## 멱등성(Idempotency)이란?

**멱등성(Idempotency)**은 동일한 연산을 여러 번 수행해도 시스템 상태가 처음 한 번 실행한 것과 같은 결과를 갖는 성질입니다.

RabbitMQ 등 메시지 브로커는 기본적으로 메시지를 *중복해서 전달*할 수 있기 때문에,  
소비자 측에서 **중복 메시지를 안전하게 처리할 수 있는 구조**를 설계해 두는 것이 필요합니다.

---

## RabbitMQ + DB 기반 멱등성 처리 전략

### 메시지에 고유 ID 부여

메시지에는 **유니크한 식별자(ID)**를 포함해야 합니다.  
이 ID를 통해 중복된 메시지를 구별하고, 동일 메시지인지 아닌지를 판단할 수 있습니다.

보통 메시지 헤더 또는 본문에 UUID, 또는 조합 키(JobID + Step 등)를 포함합니다.

---

### 멱등성 체크 저장소

DB에 **idempotency_log** 또는 **job_step**과 같은 테이블을 두고,  
이미 처리된 메시지 ID를 저장합니다.

처리 중복이 의심되는 메시지는 이 테이블에서 먼저 찾아보고,  
이미 존재할 경우 **비즈니스 로직을 스킵하고 ACK**만 보내 처리합니다.

---

### 트랜잭션 일관성

RabbitMQ 메시지 처리 로직은 다음 순서로 수행하는 것이 안전합니다:

1. **DB 트랜잭션 시작**  
2. **멱등성 확인 (중복 여부 체크)**  
3. **비즈니스 로직 수행**  
4. **처리 완료 로그/상태 저장**  
5. **트랜잭션 커밋**  
6. **RabbitMQ ACK 전송**

트랜잭션 커밋 이전에 ACK를 보내지 않음으로써,  
실패 시 메시지 재전달과 중복 처리 방지를 보장합니다.

---

## job / job_step 테이블 기반 멱등성 설계

AI 파이프라인을 **단계별로 나누어 처리**한다고 가정합니다.

Job 테이블

- job_id (PK)
- user_id
- status
- created_at

Job_Step 테이블

- job_id (FK)
- step_name
- status
- processed_at


- `(job_id, step_name)` 조합은 유니크해야 합니다.
- 메시지 소비 시 해당 조합으로 DB에서 insert 또는 select 처리를 수행하여 멱등성을 확인합니다.

**예시 흐름:**

1. Consumer에서 메시지를 받는다.
2. `(job_id, step_name)`로 insert 시도
3. insert 성공 → 비즈니스 로직 수행
4. insert 실패(중복) → 기존 기록이므로 작업 스킵하고 ACK

이 설계는 DB의 **유니크 제약조건**과 **트랜잭션**을 활용한 멱등성 보장입니다.

---

## 왜 멱등성이 필요한가?

중복 메시지 처리 문제는 분산 시스템에서 흔히 발생합니다:

- 네트워크 장애
- Consumer crash
- RabbitMQ 재시도
- 중복 퍼블리시

멱등성 설계가 없다면 결과가 중복 생성되거나 **상태 불일치**가 발생할 수 있습니다.  
예를 들어 요약 결과가 이중으로 저장되거나, 채팅이 중복 생성되는 문제 등입니다.

## 마치며

멱등성은 안정적인 메시지 기반 서비스 설계를 위해 **필수적인 요소**입니다.  
RabbitMQ의 *at-least-once* 전송 특성과 DB 트랜잭션을 이해하고 적절하게 설계하면,  
중복 메시지로부터 안전한 서비스를 만들 수 있습니다.

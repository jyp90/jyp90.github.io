## 문제와 배경

학술 논문 서비스에, 논문 상세 화면 안에서 본문을 바로 읽을 수 있는 뷰어를 붙이는 작업을 했습니다. 서버 사이드 렌더링을 쓰는 기존 웹 애플리케이션(Spring MVC + JSP) 위에, 같은 화면 한 곳에서 본문을 그려야 했습니다. 다만 본문은 한 가지 형태로만 오지 않았습니다. 출판사가 넘겨준 구조화 XML(JATS 계열 학술 마크업)로 오는 논문도 있고, 스캔한 PDF를 OCR로 추출한 일반 텍스트로만 오는 논문도 있었습니다. 같은 화면이 두 소스를 모두 다룰 수 있어야 했습니다.

운영하면서 드러난 문제는 두 가지였습니다.

- OCR로 추출한 본문 안의 수식(LaTeX) 중 일부가 KaTeX 렌더에서 예외를 던졌고, 그 자리에는 수식 대신 LaTeX 원문 코드가 그대로 노출됐습니다.
- 본문을 보유하고 있다고 알리는 칩은 떴는데 정작 본문 영역이 비어 있거나, 칩은 한 종류로 표기됐는데 실제로 그려진 본문은 다른 종류인 경우가 있었습니다.

두 문제를 따로 보면 원인이 달라 보이지만, 좁혀 보면 공통점이 있었습니다. 「본문이 실제로 무엇을 그리는가」와 「그 사실을 알리는 신호」가 서로 다른 곳에서 각자 판정되고 있었다는 점입니다. 이 글은 그 판정을 한 곳으로 모은 과정과, 수식처럼 입력 품질이 들쭉날쭉한 영역을 다루는 방법을 정리합니다.

## 접근

한 화면 안에서 XML과 OCR이라는 두 소스를 다루는 원칙은 간단하게 잡았습니다.

1. **소스가 둘 다 있으면 구조화 XML을 우선합니다.** 출판사가 정제한 마크업이라 문단·표·각주 위치의 정확도가 OCR보다 높기 때문입니다. 두 소스를 동시에 보여 주면 문단 구조나 표 레이아웃이 서로 달라 혼란만 커집니다.
2. **본문이 실제로 렌더되는지 여부로 모든 노출 신호(칩, 노출 영역)를 판정합니다.** 서버가 미리 내려준 플래그를 각 화면이 따로 해석하게 두지 않고, 브라우저가 실제로 그린 결과를 판정 기준으로 삼았습니다.
3. **수식처럼 입력 품질을 보장할 수 없는 영역은 단계적으로 복구하되, 정상 입력은 복구 로직을 아예 거치지 않게 합니다.** 복구 시도 자체가 정상 수식을 건드릴 위험이기 때문입니다.
4. **DOM에 의존하지 않는 계산과, DOM을 직접 조작하는 코드를 분리합니다.** 계산 로직만 떼어 두면 전체 화면을 띄우지 않고도 단위 테스트로 검증할 수 있습니다.

## 구현

### 소스 판별과 우선순위

본문 영역을 초기화할 때, 화면에 구조화 XML 컨테이너가 실제로 존재하는지를 먼저 봅니다. 있으면 XML 경로로 렌더하고 OCR 뷰어는 자동으로 숨깁니다. 없으면 OCR 경로로 넘어갑니다.

```javascript
function pickBodySource(root) {
  // 서버가 내려준 플래그가 아니라, 브라우저에 실제로 도착한 DOM을 봅니다.
  // 같은 요청이라도 권한·캐시 조건에 따라 XML 영역 자체가 생략될 수 있기 때문입니다.
  if (root.querySelector('.article-body--structured')) {
    return 'structured';
  }
  return root.querySelector('.article-body--ocr') ? 'ocr' : 'none';
}
```

서버 플래그 대신 DOM을 직접 보는 이유는, 플래그와 실제 렌더 결과가 어긋나는 경우를 이미 겪었기 때문입니다. XML 영역은 로그인 상태나 캐시 조건에 따라 아예 생략되고 비는 경우가 있었는데, 그런 상황에서도 「DOM에 지금 무엇이 그려져 있는가」는 항상 정확한 답이 됩니다.

### 노출 신호를 하나로 묶기

본문을 보유했다고 알리는 칩은 검색 결과, 논문 상세 상단, 목차 세 곳에서 따로 그려지고 있었습니다. 처음에는 세 곳의 판정 기준이 통일되어 있지 않았고, 일부는 본문 색인 적재 여부 대신 원문 파일 존재 여부까지 신호로 썼습니다. 그래서 같은 논문인데 칩은 한 종류, 실제 렌더는 다른 종류로 나오는 경우가 생겼습니다. 스캔 이미지로만 존재하고 아직 OCR 처리가 끝나지 않은 논문에서는 더 심했습니다. 「원문 파일은 있다」는 신호만 보고 칩을 띄우면, 본문 영역은 실제로 그릴 것이 없어 비어 있었습니다.

고친 방향은 판정 함수를 하나로 만들고, 칩과 본문 렌더 모두 그 함수를 호출하게 하는 것이었습니다.

```javascript
function deriveBodyType(hasStructuredBody, hasIndexedOcrBody) {
  if (hasStructuredBody) return 'STRUCTURED';
  if (hasIndexedOcrBody) return 'OCR';
  return 'NONE'; // 원문 파일만 있고 실제로 그릴 본문이 없는 경우도 여기로 떨어집니다
}
```

핵심은 「원문 파일이 있다」와 「본문을 그릴 수 있다」를 같은 신호로 섞지 않는 것입니다. 전자는 자료 보유 여부고, 후자는 실제로 렌더 가능한 텍스트가 있는지입니다. 칩은 반드시 후자를 기준으로 떠야 하고, 세 화면이 모두 같은 함수 호출 결과를 쓰게 만들면 화면마다 판정이 어긋나는 일을 막을 수 있습니다.

### 수식 복구: 엄격 렌더를 먼저, 복구는 실패했을 때만

OCR로 뽑아낸 수식의 LaTeX에는 불필요한 구분자(`$$`, `$`, `\[ \]`)가 겹쳐 들어오거나, 괄호 그룹이 중복되거나, 닫는 구문이 깨진 채로 섞여 들어오는 경우가 있었습니다. KaTeX를 엄격 모드(`throwOnError: true`)로 쓰면 이런 입력에서 예외가 나고, 그 결과 수식 전체가 LaTeX 원문 그대로 화면에 노출됐습니다. 반대로 관대 모드(`throwOnError: false`)로 바꾸면 예외 대신 파싱 불가 토큰을 빨간 오류색으로 표시하는데, 이쪽이 오히려 가독성이 더 나빴습니다.

복구는 3단계로 나눴습니다.

1. 구분자를 정리합니다(겹친 `$`, `$$`, `\[ \]`, 끝에 남은 처리되지 않은 역슬래시 제거).
2. 엄격 렌더를 시도합니다. 정상 수식은 대부분 여기서 끝나므로, 다음 단계의 복구 휴리스틱이 정상 수식을 건드릴 일이 없습니다.
3. 실패한 경우에만 구조 손상 패턴(중복된 괄호 그룹, 깨진 닫는 구문)을 복구하는 휴리스틱을 적용해 한 번 더 엄격 렌더를 시도합니다. 그래도 실패하면 LaTeX 원문 텍스트로 강등합니다.

### 핵심 코드

```javascript
function renderFormula(el, rawLatex) {
  const latex = stripFormulaDelimiters(rawLatex);

  if (tryStrictRender(el, latex)) return;                    // 정상 수식은 여기서 끝납니다
  if (tryStrictRender(el, repairBrokenStructure(latex))) return; // 손상 패턴만 복구 시도
  el.textContent = rawLatex;                                  // 복구 실패 시 원문 텍스트로 강등
}

function tryStrictRender(el, latex) {
  try {
    katex.render(latex, el, { throwOnError: true });
    return true;
  } catch {
    return false;
  }
}
```

`katex.render`는 전달받은 요소에 직접 DOM을 조립하는 API라, `renderToString` 결과를 `innerHTML`로 밀어 넣는 방식보다 안전합니다. 복구가 끝까지 실패하면 빨간 오류 토큰 대신 LaTeX 원문 텍스트를 그대로 보여 주는 쪽을 택했습니다. 독자 입장에서는 깨진 기호 나열보다 원문이 더 읽기 쉽기 때문입니다.

### 계산 로직과 DOM 로직 나누기

표 열 너비 계산, 캡션·각주 분류, 목차 항목 추출처럼 「입력을 받아 값을 돌려주는」 로직과, 그 결과를 실제 DOM에 반영하는 로직을 서로 다른 파일로 나눴습니다. 계산 로직은 DOM이나 브라우저 API에 의존하지 않으므로, 화면을 띄우지 않고도 단위 테스트로 검증할 수 있습니다.

```javascript
// body-metrics.js — DOM에 의존하지 않는 순수 계산
export function computeColumnWidths(cellTextLengths, minWidthPercent) {
  const total = cellTextLengths.reduce((a, b) => a + b, 0) || 1;
  return cellTextLengths.map(len =>
    Math.max(minWidthPercent, Math.round((len / total) * 100))
  );
}
```

```javascript
// body-render.js — DOM 조립, body-metrics의 계산 결과만 가져다 씁니다
import { computeColumnWidths } from './body-metrics.js';

function enhanceTable(table) {
  const lengths = [...table.querySelectorAll('th')].map(th => th.textContent.length);
  const widths = computeColumnWidths(lengths, 8);
  widths.forEach((w, i) => table.style.setProperty(`--col-${i}`, `${w}%`));
}
```

이렇게 나누고 나면, 표 열 너비를 글자 수 비례로 계산하는 규칙이 맞는지는 다양한 입력값으로 단위 테스트를 돌려 확인하고, DOM 조립이 맞는지는 실제 화면에서 눈으로 확인하는 식으로 역할을 나눌 수 있었습니다.

## 함정과 트레이드오프

- **서버 플래그와 실제 렌더 결과는 다를 수 있습니다.** 노출 신호를 여러 화면이 각자 판단하게 두면, 어느 한쪽만 바뀌어도 드리프트가 생깁니다. 판정은 한 함수로 모으고 모든 화면이 그 결과를 공유해야 합니다.
- **복구 휴리스틱의 적용 순서가 바뀌면 정상 입력까지 건드릴 위험이 있습니다.** 엄격 렌더를 항상 먼저 시도하고, 복구는 실패했을 때만 적용해야 정상 수식이 복구 로직을 아예 거치지 않는다는 것을 보장할 수 있습니다.
- **관대 렌더는 해법이 아닙니다.** 파싱 불가 토큰을 오류색으로 표시하는 쪽이 오히려 가독성을 더 떨어뜨렸습니다.
- **프런트에서 복구할 수 있는 손상에는 한계가 있습니다.** 원천 OCR 구조 자체가 심하게 깨진 경우(배열이나 그룹 스코프가 뒤섞인 경우)는 프런트 휴리스틱으로 안전하게 복원할 수 없습니다. 근본적인 해결은 OCR 파이프라인이 애초에 유효한 LaTeX를 산출하는 쪽입니다.

## 정리

- 두 본문 소스를 한 화면에서 다룰 때는, 어느 소스가 우선인지와 그 판정 방법(이번 경우는 실제 DOM 존재 여부)을 먼저 정해야 합니다.
- 본문 보유를 알리는 신호와 실제 렌더 가능 여부는 다른 개념입니다. 모든 노출 지점이 같은 판정 함수를 공유하게 하면 드리프트를 구조적으로 막을 수 있습니다.
- 품질이 들쭉날쭉한 입력(OCR 수식)은 정상 입력을 건드리지 않는 순서로 복구 단계를 설계해야 합니다. 엄격 렌더 우선, 복구는 실패했을 때만, 최종 실패는 원문 노출로.
- DOM에 의존하지 않는 계산 로직을 분리해 두면, 화면 전체를 띄우는 무거운 검증 없이도 단위 테스트로 많은 부분을 검증할 수 있습니다.

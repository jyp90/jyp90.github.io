인테리어 공사를 앞두고 가장 답답했던 건 **"이 냉장고가 이 자리에 들어가나? 들어가면 문은 열리나?"** 같은 질문에 답할 도구가 마땅치 않다는 점이었다. Planner 5D 같은 서비스도 써 봤지만, 실제 판매 중인 가전의 정확한 치수, 업체에 그대로 들고 갈 도면, 콘센트 위치까지 한 번에 다루기는 어려웠다.

그래서 우리 가족만 쓸 인테리어 플래너를 직접 만들었다. 이름은 `sn-house-interior`. 2026-10-08에 설계 문서를 쓰기 시작해 10-10까지 3일 동안 **커밋 260여 개, PR 40여 개, 스펙 라운드 50여 개, 단위 테스트 630여 개**까지 왔다. 코드는 거의 전부 Claude Code가 썼고, 나는 요구사항을 말하고 결정하고 검증하는 역할을 맡았다.

- 앱: https://jyp90.github.io/sn-house-interior/ (가족용이라 입장 PIN이 걸려 있습니다)

## 무엇을 하는 앱인가

평면도 이미지를 깔고 축척을 맞춘 뒤 벽·문·창을 그리면 집이 3D로 세워진다. 그 위에 실제 크기의 가구·가전을 끌어다 놓고, 겹치거나 문이 안 열리는 곳을 확인한 다음, 시공업체에 넘길 PDF를 뽑는다.

| 탭 | 하는 일 |
|---|---|
| 체크리스트 | 시공 단계별 현장 확인 항목. 배치 내용에서 자동으로 생기는 항목 포함 |
| 구조 | 평면도 트레이싱, 벽·문·창·중문, 방 영역·바닥재·벽지 |
| 전기 | 콘센트·스위치·조명 배치, 스위치 그룹, 전용 회로가 필요한 가전 경고 |
| 배치 | 카탈로그 가구·가전 드래그 배치(2D/3D), 배치안 A/B 비교 |
| 내보내기 | 평면 PNG, 업체용 PDF(치수도·배치도·전기·방 마감표·창호 일람·견적 요청서) |

자동으로 잡아 주는 것:
- 가구끼리 겹침(높이까지 고려 — 상부장과 하부장은 겹치지 않는다)
- 벽에 너무 붙거나 떨어짐, 문·서랍이 열릴 공간 부족
- 방 면적, 바닥재·벽지 적용 모습(3D)

## 설계 원칙: 백엔드 없이, 정수 cm로

**스택**: Vite + TypeScript + React 19 + react-three-fiber(three.js) + zustand + zod. PDF는 jsPDF + svg2pdf.js. 런타임 의존성은 10개뿐이다.

몇 가지 원칙을 초기에 박아 두었고, 이게 나중에 큰 도움이 됐다.

1. **백엔드 없음.** 저장은 localStorage 자동 저장 + IndexedDB(배경 이미지) + JSON 파일. 가족 몇 명이 쓰는 도구에 서버는 과하다. GitHub Pages에 정적으로 배포한다.
2. **모든 치수는 정수 cm.** 평면 데이터는 cm, 3D 씬은 1 unit = 1 m. 변환은 `cmToM`/`mToCm` 한 곳에서만 한다. 부동소수점 오차로 "1cm 차이로 겹침" 같은 판정이 흔들리지 않게 하려는 것.
3. **하나의 `Plan` 객체, zod 스키마로 정의하고 타입은 거기서 뽑는다.** 스키마가 바뀌면 버전을 올리고 마이그레이션 단계와 테스트를 같이 추가한다. 3일 만에 v1 → v9까지 갔는데, 예전에 저장한 JSON이 한 번도 깨지지 않았다.
4. **순수 함수 계층 분리.** `geometry/`, `validation/`, `checklist/`, `persistence/`, `export/pages.ts`는 React를 import하지 않는 순수 함수이고 옆에 `*.test.ts`가 붙는다. 단위 테스트 대부분이 여기 있다.
5. **편집 한 번 = undo 한 단계.** 모든 평면 변경은 store 액션을 통해서만 일어난다. 모드·도구·드래그 중 상태 같은 화면 전용 상태는 별도 store로 분리해 평면에 섞이지 않게 했다.

## 기술적으로 재미있었던 부분

### 1. 충돌 판정: OBB + 분리축 정리

가구는 회전할 수 있으니 축 정렬 박스(AABB)로는 부족하다. 모든 가구·벽·문 열림 영역을 OBB(oriented bounding box)로 표현하고 분리축 정리(SAT)로 겹침을 판정한다.

```ts
export type OBB = { cx: number; cy: number; hw: number; hd: number; angle: number };
```

여기에 **설치 높이**를 더해 수직 구간이 겹칠 때만 충돌로 본다. 그래서 벽걸이 TV 아래 TV장, 하부장 위 상부장은 경고가 나지 않는다. 문 열림은 문짝이 그리는 사분원 영역을 OBB 묶음으로 근사하고, 문이 벽 끝을 넘어가면 벽 범위로 잘라 낸다.

### 2. 닫힌 벽에서 방 영역 자동 인식

방마다 바닥재·벽지를 입히려면 방의 다각형이 필요한데, 벽을 다 그린 뒤 방 윤곽을 또 그리는 건 귀찮다. 그래서 방 이름 라벨을 씨앗으로 삼아 영역을 자동으로 찾는다.

1. 벽 전체 바운딩 박스를 한 칸씩 넓힌 5cm 격자를 만들고, 칸 중심이 벽 OBB 안이면 막힌 칸으로 표시
2. 씨앗 칸에서 4방향 flood fill. 바깥 테두리 칸에 닿으면 벽이 닫히지 않은 것이므로 실패
3. 채운 칸들의 경계 변을 이어 가장 긴 고리(외곽)만 취하고 공선 꼭짓점 제거
4. 각 꼭짓점을 벽 **마감면 모서리**에 스냅해 격자 계단을 정확한 정수 cm 좌표로 되돌림

문이 있어도 벽은 경계로 본다. 격자 근사 + 기하 스냅 조합이라 구현이 단순하면서도 결과 좌표가 깔끔하다.

### 3. 외부 3D 모델 없이 절차적 모델링

냉장고, 세탁기, 싱크대, 코너 하부장, 레인지후드 같은 제품은 GLB 파일을 쓰지 않고 **실제 치수를 받아 코드로 형상을 만드는 builder** 19종으로 그린다. 치수만 바꾸면 모델이 따라오니 "공식 사양 치수"로 교체하기 쉽고, 번들도 가볍다. 문짝 손잡이, 유리, 콘센트 구멍과 핀, 스위치 로커까지 같은 방식이다.

### 4. 한글 PDF의 함정들

업체용 PDF는 `export/pages.ts`(페이지 데이터·줄바꿈·쪽 나눔, 순수 함수) → `export/pdf.ts`(jsPDF + svg2pdf.js, lazy load) 두 단계로 나눴다. 만나 본 함정:

- svg2pdf는 `font-family="Pretendard"`를 명시해야 한글 폰트가 적용된다.
- `paint-order`를 지원하지 않는다. 그래서 흰 외곽선이 있는 라벨은 같은 `<text>`를 두 겹(외곽선 층 + 글자 층)으로 그린다.
- 이모지가 들어가면 깨진다. PDF용 텍스트는 이모지를 걸러 낸다.

### 5. 기타 작은 것들

- **react-three-fiber 첫 프레임 깜빡임**: 캔버스가 컨테이너 크기를 알기 전에 기본값 300×150으로 한 프레임 그려졌다. CSS로 캔버스를 100%로 고정해 해결.
- **2D와 3D 뷰는 항상 마운트**: 탭을 오갈 때 조건부 렌더링 대신 숨김 클래스로만 전환한다. 3D 씬을 다시 만드는 비용과 카메라 상태 유실을 피한다.
- **2D 핀치 줌**: 터치 포인터를 id별로 추적하다 두 개가 되면 핀치를 시작한다. 매 이동마다 누적하지 않고 **시작 시점의 viewBox·중점·거리 기준**으로 다시 계산해서 흔들림이 쌓이지 않는다.

## 공개 배포에서 우리 집 정보 지키기

앱이 GitHub Pages로 공개 배포되기 때문에 개인정보 관리가 꽤 신경 쓰였다. 주소·단지명·매물 링크·원본 평면도는 gitignore된 `private/`에만 두고, 여러 겹으로 막는다.

- **스캔 스크립트**: 금지어 목록을 `private/`에 두고, 스테이징된 변경·추적 파일·커밋 로그·빌드 결과물을 각각 검사한다.
- **CI**: PR과 `main` push마다 같은 스캔을 돌린다. 금지어는 저장소 secret으로 넣어서 금지어 목록 자체가 공개되지 않는다. secret이 없으면 잡이 실패한다(조용히 통과하지 않게).
- **번들 가드**: 빌드 후 `check:dist`가 허용된 평면도 외의 이미지, `private/` 흔적, 잘못된 base path를 검사한다. 하나라도 걸리면 배포가 막힌다.
- 커밋 메시지, 문서, PDF/PNG 내보내기 배경에도 원본 평면도를 넣지 않는 것이 규칙이다.

처음에는 소스 저장소 자체를 공개하고 Pages를 돌렸는데, 결국 **소스는 비공개 저장소로, 배포는 빌드 결과만 담은 공개 저장소로** 나눴다. GitHub Free에서는 비공개 저장소의 Pages를 쓸 수 없기 때문이다. 비공개 저장소의 Actions가 테스트·빌드·번들 검사를 통과하면 `dist/`를 커밋 하나로 만들어 공개 저장소에 deploy key로 강제 push한다. 공개 쪽에는 소스도 이력도 남지 않는다.

## Claude Code로 개발한 방식

이 프로젝트의 진짜 실험은 사실 여기였다. 3일 동안 40여 개의 PR을 만들고 머지했는데, 흐름은 이렇다.

### 스펙 라운드

요청 하나가 들어오면 바로 코드를 짜지 않고, 설계 문서에 날짜가 붙은 **새 절(§N)**을 추가한다. 예전 절을 고치지 않고 덧붙이며, 뒤 절이 앞 절을 덮는다. 그래서 "왜 이렇게 됐지?"를 언제든 추적할 수 있다. 설계 문서가 §50을 넘었다.

### 워크트리 + 서브에이전트

- 요청마다 `git worktree`로 별도 작업 디렉터리와 브랜치를 만든다. 여러 Claude Code 세션이 같은 저장소를 동시에 만져도 서로 밟지 않는다.
- 메인 세션은 나와 브레인스토밍하고 스펙·계획을 쓴다. 승인되면 구현은 서브에이전트에게 맡기고, 리뷰는 "스펙과 다른 것"을 결함으로 취급한다.
- 끝나는 방식도 고정해 두었다: typecheck → 단위 → e2e → **실제 브라우저 탐색 QA** → 문서 동기화 → 개인정보 스캔 → PR → 머지 → 워크트리·브랜치 정리. 사람이 중간에 끼지 않아도 한 라운드가 끝까지 간다.

### 프로젝트 스킬

반복되는 절차는 `CLAUDE.md`에 길게 쓰지 않고 `.claude/skills/`에 스킬로 뺐다.

| 스킬 | 언제 |
|---|---|
| `committing-safely` | 커밋·PR 전. 워크트리 확인, 명시적 경로로만 `git add` |
| `checking-privacy` | 커밋·문서·내보내기·배포 근처 |
| `syncing-docs` | 라운드 마무리. 어떤 문서의 어느 절을 갱신할지 표로 |
| `migrating-plan-schema` | 스키마 변경. 버전 증가 + 마이그레이션 + 테스트 |
| `adding-catalog-product` | 제품 추가·공식 치수 교체 |
| `exploratory-qa` | 테스트가 다 통과한 뒤 실제 브라우저 확인 |

`CLAUDE.md`는 규칙과 포인터만 남기고 짧게 유지한다. 세부 절차는 필요할 때 스킬이 불러온다.

### 배운 것

- **리뷰만으로는 런타임 버그를 못 잡는다.** 코드 리뷰를 통과한 변경이 실제 브라우저에서 3D가 안 뜨거나 드래그가 안 되는 일이 있었다. 그 뒤로 "테스트 통과 후 실제 브라우저 QA"를 완료 조건에 넣었다.
- **테스트를 초록으로 만드는 꼼수를 명시적으로 금지해야 한다.** 기대값 수정, 테스트 skip, e2e에서 실제 사용자 조작 대신 store를 직접 호출하기 — 이걸 규칙으로 막아 두었다.
- **문서도 완료의 일부.** 매 라운드 `HANDOFF.md`(현재 상태·다음 할 일), 기능 → 코드 → 스펙 지도, 모듈 메모를 같이 갱신한다. 새 세션이 컨텍스트 없이 시작해도 몇 개 문서만 읽고 바로 이어 갈 수 있다.

### 결정을 번복한 이야기: 모바일

모바일 대응은 세 번 바뀌었다.

1. **§33 보기 전용**: 폰에서는 편집 도구를 숨기고 보기만. → 써 보니 폰에서도 고치고 싶었다.
2. **§44 PC 화면 그대로 축소**: viewport를 `width=1200`으로 고정하고 핀치로 확대. → 글자가 너무 작고 불편했다.
3. **§48 1열 배치**: viewport는 `device-width`, 같은 도구·패널을 캔버스 → 속성 → 도구 순으로 세로로 쌓는다. 기능 제한 없음.

스펙을 덮어쓰지 않고 라운드를 쌓았기 때문에, 각 결정이 왜 철회됐는지 문서에 그대로 남아 있다. 직접 써 보기 전에는 정답을 알 수 없는 문제라서, 빨리 만들고 바로 써 보는 짧은 루프가 효과적이었다.

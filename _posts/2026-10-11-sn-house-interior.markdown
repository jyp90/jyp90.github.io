인테리어 공사를 앞두고 가장 답하기 어려웠던 질문은 「이 냉장고가 이 자리에 들어가나, 들어가면 문은 열리나」였습니다. Planner 5D 같은 서비스도 써 봤지만 실제 판매 중인 가전의 치수, 업체에 그대로 들고 갈 도면, 콘센트 위치를 한 번에 다루기는 어려웠습니다.

그래서 가족만 쓸 인테리어 플래너 `sn-house-interior`를 직접 만들었습니다. 2026-10-08에 설계 문서를 쓰기 시작해 핵심 기능은 사흘 안에 들어갔고, 10-11의 배포 정리까지 커밋 281개(머지 커밋 포함), `main`에 머지된 PR 56개가 쌓였습니다. 코드는 거의 전부 Claude Code가 썼고, 저는 요구사항을 말하고 결정하고 실제로 써 보며 검증하는 역할을 맡았습니다.

이 시리즈는 그 과정을 단계별 화면과 함께 네 편으로 나눠 정리합니다. 1편은 설계 문서와 첫 3D 배치, 2편은 2D 평면 편집기와 배치안 비교, 3편은 업체용 PDF와 방 영역 자동 인식, 4편은 모바일 대응과 공개 배포입니다.

- 앱: https://jyp90.github.io/sn-house-interior/ (가족용이라 입장 PIN이 걸려 있습니다)

글의 모든 화면은 각 시점의 커밋을 체크아웃해 익명 예시 평면(방 두 개짜리 가상의 집)을 띄우고 찍은 것입니다. 실제 집 평면은 넣지 않았습니다.

## 설계 문서부터 쓰게 한 이유

첫 커밋은 코드가 아니라 설계 문서입니다. Claude Code와 브레인스토밍으로 요구사항을 정리한 뒤 「목적, 확정된 결정, 데이터 모델, 화면, 검증 규칙, 테스트, 범위 제외」를 담은 스펙을 쓰게 했고, 그다음 커밋이 그 스펙을 과제 단위로 쪼갠 구현 계획 1(기반 + 3D 배치)입니다.

스펙의 「확정된 결정」 표에는 나중에 바꾸기 어려운 것만 넣었습니다.

| 항목 | 결정 |
|---|---|
| 구조 입력 | 평면도 이미지 트레이싱 + 축척 보정 |
| 제품 형상 | 실제 치수를 받아 코드로 만드는 절차적 모델링(외부 GLB 없음) |
| 저장 | localStorage 자동 저장 + JSON 내보내기/불러오기, 백엔드 없음 |
| 검증 | 충돌(OBB) + 벽까지 거리 + 문 열림 반경 |
| 스택 | Vite + TypeScript + React + react-three-fiber + drei + zustand + zod |

구현은 계획의 과제를 하나씩 서브에이전트에게 맡기는 방식으로 진행했습니다. 커밋 이력을 보면 `feat: plan schema and anonymous sample plan`, `feat: OBB collision and wall geometry`, `feat: clearance sectors, wall distances and wall snapping`처럼 과제 하나가 커밋 하나로 3–5분 간격으로 쌓여 있습니다. 순수 함수 계층(스키마, 기하, 검증, 저장)이 먼저 테스트와 함께 들어가고, 화면은 그 뒤에 붙었습니다.

## 초기에 고정한 설계 원칙

1. **모든 치수는 정수 cm.** 평면 데이터는 cm, 3D 씬은 1 unit = 1 m이고 변환은 한 모듈에서만 합니다. 부동소수점 오차로 「1cm 차이로 겹침」 판정이 흔들리지 않게 하려는 것입니다.
2. **`Plan` 객체 하나를 zod 스키마로 정의하고 타입은 스키마에서 뽑습니다.** 스키마가 바뀌면 버전을 올리고 마이그레이션 단계와 테스트를 같이 추가합니다. 이 규칙 덕분에 v1에서 v11까지 가는 동안 예전에 저장한 JSON을 계속 읽을 수 있었습니다.
3. **React를 import하지 않는 순수 함수 계층.** `geometry/`, `validation/`, `persistence/` 같은 디렉터리는 옆에 `*.test.ts`가 붙고, 단위 테스트 대부분이 여기 있습니다.
4. **편집 한 번 = 실행 취소 한 단계.** 모든 평면 변경은 store 액션을 거치고, 모드·도구·드래그 중 상태처럼 화면에만 필요한 상태는 별도 store에 둡니다.

## 충돌 판정: OBB와 분리축 정리

가구는 회전할 수 있으니 축 정렬 박스(AABB)로는 부족합니다. 가구·벽·문 열림 영역을 모두 OBB(oriented bounding box)로 표현하고 분리축 정리(SAT, separating axis theorem)로 겹침을 판정합니다. 두 직사각형의 변 방향 네 축 중 하나라도 투영 구간이 떨어져 있으면 겹치지 않은 것입니다. 아래는 원리만 보이도록 새로 쓴 최소 예시입니다.

```ts
type OBB = { cx: number; cy: number; hw: number; hd: number; angle: number };

function axes(b: OBB): [number, number][] {
  const c = Math.cos(b.angle), s = Math.sin(b.angle);
  return [[c, s], [-s, c]];
}

function project(b: OBB, [ax, ay]: [number, number]): [number, number] {
  const [[ux, uy], [vx, vy]] = axes(b);
  const center = b.cx * ax + b.cy * ay;
  const r = b.hw * Math.abs(ux * ax + uy * ay) + b.hd * Math.abs(vx * ax + vy * ay);
  return [center - r, center + r];
}

export function overlaps(a: OBB, b: OBB): boolean {
  for (const axis of [...axes(a), ...axes(b)]) {
    const [aMin, aMax] = project(a, axis);
    const [bMin, bMax] = project(b, axis);
    if (aMax <= bMin || bMax <= aMin) return false; // 닿기만 한 것은 겹침이 아님
  }
  return true;
}
```

문 열림은 문짝이 그리는 사분원을 OBB 여러 개로 근사합니다. 나중에(3편) 설치 높이가 들어오면서 평면 OBB가 겹치고 세로 구간도 겹칠 때만 충돌로 보도록 바뀝니다. 그래야 벽걸이 TV 아래 TV장, 하부장 위 상부장이 경고 없이 놓입니다.

## 외부 3D 모델 없이 절차적 모델링

냉장고, 세탁기, TV, 침대 같은 제품은 GLB 파일을 쓰지 않고 **실제 치수를 받아 코드로 형상을 만드는 builder**로 그립니다. 치수만 바꾸면 모델이 따라오니 샘플 치수를 공식 사양으로 교체하기 쉽고 번들도 가볍습니다. 계획 1 시점에는 builder가 몇 개뿐이었고, 지금은 싱크대 하부장, 코너장, 붙박이 가전, 욕실 설비까지 builder 종류가 17개입니다.

builder는 형상의 바운딩 박스가 제품 치수와 정확히 같아야 한다는 조건을 테스트로 묶었습니다(`feat: procedural product builders with exact bounding boxes`). 화면에 보이는 모양과 충돌 판정에 쓰는 박스가 어긋나면 「겹쳐 보이는데 경고가 없다」는 혼란이 생기기 때문입니다.

## 첫 단계에서 잘못된 것들

계획 1의 기능 커밋 뒤에는 리뷰에서 나온 수정이 바로 붙어 있습니다. 같은 유형의 문제가 이후에도 반복돼서 여기 정리해 둡니다.

| 증상 | 원인 | 수정 |
|---|---|---|
| 드래그 중 실행 취소를 누르면 사라진 아이템을 계속 끌고 있음 | 드래그 상태가 undo와 따로 놀았음 | undo 시 진행 중인 드래그를 취소 |
| 드래그 도중 회전·삭제·복제를 하면 undo 항목이 둘로 쪼개짐 | 드래그 트랜잭션이 열려 있는데도 이력이 쌓였음 | 드래그가 열려 있는 동안은 이력을 쌓지 않음 |
| 포인터가 끊기면 드래그가 끝나지 않음 | `pointercancel` 미처리 | `pointercancel`에서도 드래그 종료 |
| 벽 끝점·방 라벨·설비 좌표에 소수가 들어갈 수 있었음 | 좌표 스키마가 정수를 강제하지 않았음 | 좌표 스키마에 정수 조건 추가 |
| 읽지 못한 저장본을 다음 자동 저장이 덮어쓸 수 있었음 | 깨진 저장본을 「저장본 없음」과 같게 취급 | 원본 문자열을 시각이 붙은 키로 백업하고 오류 배너 표시, 페이지를 떠날 때(`pagehide`) 대기 중인 자동 저장을 바로 기록 |

정수 cm는 원칙으로만 정해 두고 스키마에는 빠져 있었습니다. 원칙을 문서에만 두지 않고 스키마·테스트로 강제해야 한다는 점을 이 단계에서 확인했습니다.

## 정리

- 설계 문서와 구현 계획을 먼저 쓰게 하고, 과제 단위로 구현을 맡기면 커밋이 작고 추적하기 쉬워집니다.
- 정수 cm, 스키마 하나, 순수 함수 계층, 편집 한 번 = undo 한 단계라는 원칙은 이후 마흔 번 넘는 스펙 라운드 동안 바뀌지 않았습니다.
- 다음 편에서는 같은 날 이어서 만든 2D 평면 편집기와 배치안 A/B 비교, 그리고 스펙을 덮어쓰지 않고 「라운드」로 쌓는 방식을 다룹니다.

## 문제와 배경

1~2편에서는 Mac mini 한 대에 폴러와 보조 프로세스를 상주시키고 설정·상태 파일을 분리하는 구성을 다뤘습니다. 이번 편은 그 폴러가 실제로 하는 일, 즉 「지금 Claude를 깨워야 하는 이슈가 있는가」를 판정하고 깨워야 한다면 헤드리스 Claude Code 세션을 어떻게 띄우는지를 다룹니다.

이 부분에서 풀어야 할 문제는 네 가지였습니다. 이 편에서는 앞의 두 질문(언제·어떻게 깨울 것인가)을, 다음 편에서는 나머지 두 질문(어떻게 이어 가고 무엇을 남길 것인가)을 다룹니다.

- **언제 깨울 것인가**: 사람이 아직 승인하지 않은 이슈를 Claude가 먼저 진행해 버리면 안 되고, 반대로 사람이 답을 달았는데 아무도 반응하지 않아도 안 됩니다.
- **어떻게 띄울 것인가**: 대화형 터미널이 없는 상태에서 Claude Code를 돌려야 합니다. 권한 확인 창에 답해 줄 사람도 없습니다.
- **어떻게 이어 갈 것인가**: 이슈 하나는 계획, 설계, 구현, 검수를 거치며 며칠에 걸쳐 여러 번 깨어납니다. 매번 처음부터 다시 읽게 하면 비싸고, 앞 단계에서 내린 결정을 잊어버립니다.
- **무엇을 남길 것인가**: 무인으로 도는 세션이 무엇을 받았고 무엇을 했고 얼마를 썼는지 나중에 확인할 수 있어야 합니다.

## 접근: 가벼운 폴러, 무거운 세션

전체 구조는 한 문장으로 요약됩니다. **폴러는 판정만 하고 바로 끝나고, 실제 작업은 따로 떨어져 나간 Claude 세션이 합니다.**

```text
[launchd / cron, 1분 주기]
   └─ poll()            Jira 조회 → 트리거 판정 → 세션 발사 → 즉시 종료
         │
         └─ claude -p   독립 프로세스로 분석·구현·댓글 작성 (수십 분~수 시간)
                │
   다음 poll() ◀┘       PID와 완료 표지 파일로 끝났는지 확인 → 결과 회수
```

폴러 자체는 Jira REST 호출과 조건 분기만 하므로 토큰을 쓰지 않습니다. 토큰을 쓰는 것은 트리거가 실제로 성립해 세션이 뜰 때뿐입니다. 그래서 폴링 주기를 10분에서 1분으로 줄여도 비용은 늘지 않고 반응 지연만 짧아졌습니다. 비용을 정하는 것은 폴링 횟수가 아니라 트리거 횟수입니다.

처음에는 폴러가 `claude -p`를 동기로 호출하고 끝날 때까지 기다렸습니다. 세션이 길어지면 폴러의 잠금이 그동안 풀리지 않아 다음 주기가 전부 건너뛰어졌습니다. 발사와 회수를 분리한 뒤로는 폴러가 매분 몇 초 안에 끝납니다.

## 구현

### 1. 이슈 수집: 세 갈래 조회를 합칩니다

한 번의 폴링에서 서로 목적이 다른 조회 세 개를 돌리고, 이슈 키로 중복을 지워 하나의 목록으로 합칩니다.

| 조회 | 조건 | 왜 필요한가 |
|---|---|---|
| 최근 변경분 | 감시 대상 상태 + 최근 N분 안에 갱신 | 평상시 신호 대부분을 잡습니다 |
| 미처리 전수 | 「AI 수정 요청」 상태 전체, 시간 조건 없음 | 최근 변경 창 밖으로 밀려난 이슈를 구제합니다 |
| AI 레인 | 자동화 전용 이슈 유형의 상태들 | 단계형 워크플로를 따르는 이슈를 따로 봅니다 |

예시 JQL은 이런 모양입니다. 상태 이름과 이슈 유형은 직접 만든 일반 예시입니다.

```sql
-- 최근 변경분: 폴링 주기보다 조금 긴 창으로 겹치게 봅니다
status in ("AI 수정 요청", "사람 확인") AND updated >= -3m

-- 미처리 전수: 시간 조건 없이 오래된 것부터
status = "AI 수정 요청" ORDER BY updated ASC

-- AI 레인
issuetype = "AI Task" AND status in ("분석", "계획 확인", "설계", "설계 확인", "구현", "검수")
```

최근 변경 창(lookback)을 주기보다 조금 길게 잡는 이유는 폴러 한 번이 늦게 뜨거나 실패했을 때 그 사이의 변경을 놓치지 않기 위해서입니다. 1분 주기에 3분 창을 쓰면 같은 변경을 두세 번 보게 되지만, 아래의 중복 방지가 그것을 흡수합니다. 세 조회는 서로 독립적으로 실패하게 두었습니다. 하나가 Jira 쪽 타임아웃으로 실패해도 나머지 두 조회의 결과로 그 주기를 진행합니다.

### 2. 레인 상태 머신: 상태가 곧 신호입니다

AI 레인의 상태는 세 부류로 나눴고, 부류마다 트리거 규칙이 다릅니다.

| 부류 | 예시 상태 | 트리거 규칙 |
|---|---|---|
| 진입 | 할 일 → 분석 | 사람이 담당자를 지정하고 직접 옮겨야 합니다. 폴러는 진입을 만들지 않습니다 |
| AI 차례 | 분석, 설계, 구현 | 상태에 **들어온 순간** 한 번 트리거합니다(on_enter). 댓글이 없어도 됩니다 |
| 게이트 | 계획 확인, 설계 확인, 검수 | 자동화 계정이 아닌 사람이 **새 댓글**을 달 때만 트리거합니다(on_comment) |

요약하면 「AI 차례면 스스로 시작하고, 게이트면 사람의 말을 기다린다」입니다. 별도 알림 시스템 없이 Jira 워크플로의 상태만으로 자동 구간과 사람 구간이 갈립니다. 상태 목록은 코드가 아니라 설정 파일에 두어서, 워크플로에 상태가 하나 늘어도 폴러를 고치지 않고 설정만 바꿉니다.

```json
{
  "poll": { "interval_minutes": 1, "lookback_minutes": 3 },
  "ai_lane": {
    "entry":   ["분석"],
    "ai_turn": ["분석", "설계", "구현"],
    "gate":    ["계획 확인", "설계 확인", "검수"]
  }
}
```

### 3. 트리거 판정과 중복 방지

판정 순서는 단순합니다. 종결된 이슈는 건너뛰고, AI 차례 상태에서 아직 한 번도 트리거하지 않았으면 발사하고, 게이트 상태에서 처리하지 않은 사람 댓글이 있으면 발사합니다.

어려운 부분은 「같은 일을 두 번 하지 않기」입니다. 1분마다 같은 이슈를 다시 보므로 중복 방지 장치가 여러 겹 필요했습니다.

- **폴러 전체 잠금**: 이전 폴링이 아직 돌고 있으면 이번 폴링은 조용히 끝납니다.
- **이슈별 처리 중 표시**: 세션이 떠 있는 이슈는 `processing`으로 표시하고 건너뜁니다. 한 이슈에 세션은 동시에 하나만 돕니다. 표시가 너무 오래 남으면(세션이 죽었는데 회수되지 못한 경우) 일정 시간 뒤 자동으로 풀어 줍니다.
- **AI 차례 트리거 횟수**: 상태별로 몇 번 발사했는지 세어 두고, 0일 때만 on_enter로 발사합니다.
- **처리한 댓글 ID 목록**: 이미 반응한 댓글 ID를 이슈별로 쌓아 두고, 상한(예: 200개)을 넘으면 오래된 것부터 버립니다.
- **자기 댓글 제외**: 자동화 계정이 단 댓글은 트리거 대상에서 뺍니다. 이것을 빠뜨리면 에이전트가 자기 댓글에 반응해 끝없이 다시 깨어납니다.

```python
def should_trigger(issue, state, lane, bot_account_id):
    st = state.setdefault(issue.key, {"triggers": {}, "seen_comments": [], "status": "active"})
    if issue.status_category == "done" or st["status"] == "processing":
        return None

    if issue.status in lane["ai_turn"] and st["triggers"].get(issue.status, 0) == 0:
        return {"kind": "on_enter"}

    if issue.status in lane["gate"]:
        fresh = [c for c in issue.comments
                 if c.author_id != bot_account_id and c.id not in st["seen_comments"]]
        if fresh:
            return {"kind": "on_comment", "comments": fresh}
    return None
```

상태 파일 하나(`~/issue-agent/state.json`)에 이 값들과 폴러의 마지막 성공 시각을 함께 둡니다. 폴러가 살아 있는지는 로그 꼬리가 아니라 이 성공 시각과 heartbeat 파일의 수정 시각으로 판정합니다. 정상 폴링은 로그를 거의 남기지 않으므로 로그가 조용하다는 사실만으로는 아무것도 알 수 없습니다.

### 4. 프롬프트 조립

트리거가 성립하면 폴러가 프롬프트를 만듭니다. 들어가는 내용은 다음과 같습니다.

- **현재 상태와 이번 회차의 계약**: 「이번 실행은 설계 단계만 수행하고, 설계안을 게시한 뒤 확인 게이트로 옮기고 멈춘다」처럼 한 회차에 한 단계만 하도록 못 박습니다. 세션이 다음 단계까지 내달리지 않게 하는 가장 강한 장치가 이 문장이었습니다.
- **이슈 본문과 트리거 댓글**: 무엇을 해야 하는지, 사람이 무엇이라고 답했는지를 넣습니다.
- **이슈 메모리 문서**: 앞 회차들이 남긴 요약(아래 6절)을 길이 상한을 두고 넣습니다.
- **쓰기 규칙**: Jira 댓글과 상태 전이를 어떤 명령으로만 하라는 지시입니다. 이 규칙이 왜 필요한지는 5편에서 다룹니다.

조립한 프롬프트는 명령줄 인자로 직접 넘기지 않고 파일에 쓴 뒤 실행 스크립트가 그 파일을 읽어 넘깁니다. 프롬프트에는 사람이 쓴 댓글이 그대로 들어가므로 셸 인자로 이어 붙이면 따옴표 처리에서 사고가 납니다. 명령줄에 붙는 나머지 값은 고정 리터럴이나 UUID뿐이라 인용 처리를 해서 붙입니다.

### 5. `claude -p` 발사

발사 함수는 회차마다 파일 네 개를 만들고, 실행 스크립트를 새 세션 그룹으로 띄웁니다.

```python
import shlex, subprocess
from datetime import datetime
from pathlib import Path

RUNS = Path.home() / "issue-agent" / "runs"
DENY_WRITE = ["mcp__jira__addComment", "mcp__jira__transitionIssue"]

def spawn_session(issue_key, prompt, cwd, resume_id=None, model=None):
    run_dir = RUNS / issue_key
    run_dir.mkdir(parents=True, exist_ok=True)
    base = run_dir / datetime.now().strftime("%Y%m%d-%H%M%S")
    prompt_f, log_f, done_f, sh_f = (base.with_suffix(s) for s in (".prompt", ".log", ".done", ".sh"))
    prompt_f.write_text(prompt, encoding="utf-8")

    args = ["--output-format", "json", "--disallowedTools", *DENY_WRITE]
    if model:
        args += ["--model", model]
    if resume_id:
        args += ["--resume", resume_id]

    sh_f.write_text(
        "#!/usr/bin/env bash\n"
        f"cd {shlex.quote(str(cwd))}\n"
        f'claude -p "$(cat {shlex.quote(str(prompt_f))})" {" ".join(map(shlex.quote, args))} '
        f"> {shlex.quote(str(log_f))} 2>&1\n"
        f'echo "$?" > {shlex.quote(str(done_f))}\n'
    )
    sh_f.chmod(0o755)
    p = subprocess.Popen(["bash", str(sh_f)], cwd=cwd, start_new_session=True,
                         stdin=subprocess.DEVNULL, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
    return {"pid": p.pid, "log": str(log_f), "done": str(done_f)}
```

플래그마다 고른 이유가 있습니다.

- `-p`(`--print`): 비대화형 실행입니다. 프롬프트를 받아 한 번 돌고 결과를 표준 출력에 쓴 뒤 끝납니다. 스크립트와 CI에서 쓰라고 공식 문서가 제공하는 진입점입니다.
- `--output-format json`: 결과를 JSON 하나로 받습니다. 처음에는 사용량을 기록할 때만 켰는데, 세션 ID를 회수하려면 이 출력이 필요해서 지금은 항상 켭니다.
- `--disallowedTools`: Jira MCP 서버의 쓰기 도구를 프로세스 단위로 막습니다. 프롬프트에 「MCP로 쓰지 말라」고만 적었을 때 세션이 사람 계정으로 연결된 MCP를 써서 댓글을 단 일이 있었습니다. 지시와 차단을 이중으로 겁니다.
- `--model`: 단계 성격에 따라 모델을 바꿀 수 있게 열어 두었습니다. 같은 이유로 `--effort`도 설정값이 있을 때만 붙입니다.
- `--resume`: 이슈별 세션을 이어 갈 때 붙입니다(6절).
- `start_new_session=True`: 폴러가 끝나도 세션 프로세스가 함께 죽지 않게 합니다.

다음 폴링은 기록해 둔 PID에 `os.kill(pid, 0)`을 보내 살아 있는지 보고, 죽었으면 `.done` 파일의 종료 코드와 `.log`의 JSON을 읽어 결과를 회수합니다. 실행 중이면 그냥 건너뜁니다.

권한 모드에 대해서는 한 가지만 먼저 적어 둡니다. 무인 세션에서 권한 확인 창은 아무도 답하지 않으므로, 허용 규칙(allow)에 걸리지 않은 명령은 설정된 권한 모드에 따라 거부되거나 분류기의 판단에 맡겨집니다. 서브에이전트를 부르는 세션이라면 `Agent` 도구를 허용 목록에 넣어야 무인에서도 위임이 됩니다. 그리고 허용 규칙이 실제로 매칭되는지는 `--permission-mode dontAsk`로 분류기를 빼고 돌려 봐야 알 수 있었습니다. 규칙을 적어 둔 것과 규칙이 맞는 것은 다른 문제였고, 그 이야기는 6편의 「쓰기 권한 게이트」에서 이어 갑니다.


## 정리

- 폴러는 판정하고 발사한 뒤 바로 끝나고, 작업은 떨어져 나간 `claude -p` 세션이 합니다. 비용은 폴링 주기가 아니라 트리거 횟수에 비례합니다.
- 트리거는 Jira 상태로 정합니다. AI 차례 상태는 진입할 때 한 번, 게이트 상태는 사람의 새 댓글에만 반응합니다. 잠금, 처리 중 표시, 트리거 횟수, 처리한 댓글 ID, 자기 댓글 제외를 겹쳐 중복을 막습니다.
- 발사는 프롬프트를 파일로 넘기고, `--output-format json`으로 결과를 받고, `--disallowedTools`로 쓰기 도구를 막고, 새 세션 그룹으로 띄웁니다.

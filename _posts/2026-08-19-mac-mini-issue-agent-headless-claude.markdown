## 문제와 배경

1편에서는 Mac mini 한 대에 폴러와 보조 프로세스를 상주시키는 구성을 다뤘습니다. 이번 편은 그 폴러가 실제로 하는 일, 즉 「지금 Claude를 깨워야 하는 이슈가 있는가」를 판정하고 깨워야 한다면 헤드리스 Claude Code 세션을 어떻게 띄우는지를 다룹니다.

이 부분에서 풀어야 할 문제는 네 가지였습니다.

- **언제 깨울 것인가**: 사람이 아직 승인하지 않은 이슈를 Claude가 먼저 진행해 버리면 안 되고, 반대로 사람이 답을 달았는데 아무도 반응하지 않아도 안 됩니다.
- **어떻게 띄울 것인가**: 대화형 터미널이 없는 상태에서 Claude Code를 돌려야 합니다. 권한 확인 창에 답해 줄 사람도 없습니다.
- **어떻게 이어 갈 것인가**: 이슈 하나는 계획, 설계, 구현, 검수를 거치며 며칠에 걸쳐 여러 번 깨어납니다. 매번 처음부터 다시 읽게 하면 비싸고, 앞 단계에서 내린 결정을 잊어버립니다.
- **무엇을 남길 것인가**: 무인으로 도는 세션이 무엇을 받았고 무엇을 했고 얼마를 썼는지 나중에 확인할 수 있어야 합니다.

## 접근: 가벼운 폴러, 무거운 세션

전체 구조는 한 문장으로 요약됩니다. **폴러는 판정만 하고 바로 끝나고, 실제 작업은 따로 떨어져 나간 Claude 세션이 합니다.**

```text
[launchd / cron, 1분 주기]
   └─ poll()            Jira 조회 → 트리거 판정 → 세션 발사 → 즉시 종료
         │
         └─ claude -p   독립 프로세스로 분석·구현·댓글 작성 (수십 분~수 시간)
                │
   다음 poll() ◀┘       PID와 완료 표지 파일로 끝났는지 확인 → 결과 회수
```

폴러 자체는 Jira REST 호출과 조건 분기만 하므로 토큰을 쓰지 않습니다. 토큰을 쓰는 것은 트리거가 실제로 성립해 세션이 뜰 때뿐입니다. 그래서 폴링 주기를 10분에서 1분으로 줄여도 비용은 늘지 않고 반응 지연만 짧아졌습니다. 비용을 정하는 것은 폴링 횟수가 아니라 트리거 횟수입니다.

처음에는 폴러가 `claude -p`를 동기로 호출하고 끝날 때까지 기다렸습니다. 세션이 길어지면 폴러의 잠금이 그동안 풀리지 않아 다음 주기가 전부 건너뛰어졌습니다. 발사와 회수를 분리한 뒤로는 폴러가 매분 몇 초 안에 끝납니다.

## 구현

### 1. 이슈 수집: 세 갈래 조회를 합칩니다

한 번의 폴링에서 서로 목적이 다른 조회 세 개를 돌리고, 이슈 키로 중복을 지워 하나의 목록으로 합칩니다.

| 조회 | 조건 | 왜 필요한가 |
|---|---|---|
| 최근 변경분 | 감시 대상 상태 + 최근 N분 안에 갱신 | 평상시 신호 대부분을 잡습니다 |
| 미처리 전수 | 「AI 수정 요청」 상태 전체, 시간 조건 없음 | 최근 변경 창 밖으로 밀려난 이슈를 구제합니다 |
| AI 레인 | 자동화 전용 이슈 유형의 상태들 | 단계형 워크플로를 따르는 이슈를 따로 봅니다 |

예시 JQL은 이런 모양입니다. 상태 이름과 이슈 유형은 직접 만든 일반 예시입니다.

```sql
-- 최근 변경분: 폴링 주기보다 조금 긴 창으로 겹치게 봅니다
status in ("AI 수정 요청", "사람 확인") AND updated >= -3m

-- 미처리 전수: 시간 조건 없이 오래된 것부터
status = "AI 수정 요청" ORDER BY updated ASC

-- AI 레인
issuetype = "AI Task" AND status in ("분석", "계획 확인", "설계", "설계 확인", "구현", "검수")
```

최근 변경 창(lookback)을 주기보다 조금 길게 잡는 이유는 폴러 한 번이 늦게 뜨거나 실패했을 때 그 사이의 변경을 놓치지 않기 위해서입니다. 1분 주기에 3분 창을 쓰면 같은 변경을 두세 번 보게 되지만, 아래의 중복 방지가 그것을 흡수합니다. 세 조회는 서로 독립적으로 실패하게 두었습니다. 하나가 Jira 쪽 타임아웃으로 실패해도 나머지 두 조회의 결과로 그 주기를 진행합니다.

### 2. 레인 상태 머신: 상태가 곧 신호입니다

AI 레인의 상태는 세 부류로 나눴고, 부류마다 트리거 규칙이 다릅니다.

| 부류 | 예시 상태 | 트리거 규칙 |
|---|---|---|
| 진입 | 할 일 → 분석 | 사람이 담당자를 지정하고 직접 옮겨야 합니다. 폴러는 진입을 만들지 않습니다 |
| AI 차례 | 분석, 설계, 구현 | 상태에 **들어온 순간** 한 번 트리거합니다(on_enter). 댓글이 없어도 됩니다 |
| 게이트 | 계획 확인, 설계 확인, 검수 | 자동화 계정이 아닌 사람이 **새 댓글**을 달 때만 트리거합니다(on_comment) |

요약하면 「AI 차례면 스스로 시작하고, 게이트면 사람의 말을 기다린다」입니다. 별도 알림 시스템 없이 Jira 워크플로의 상태만으로 자동 구간과 사람 구간이 갈립니다. 상태 목록은 코드가 아니라 설정 파일에 두어서, 워크플로에 상태가 하나 늘어도 폴러를 고치지 않고 설정만 바꿉니다.

```json
{
  "poll": { "interval_minutes": 1, "lookback_minutes": 3 },
  "ai_lane": {
    "entry":   ["분석"],
    "ai_turn": ["분석", "설계", "구현"],
    "gate":    ["계획 확인", "설계 확인", "검수"]
  }
}
```

### 3. 트리거 판정과 중복 방지

판정 순서는 단순합니다. 종결된 이슈는 건너뛰고, AI 차례 상태에서 아직 한 번도 트리거하지 않았으면 발사하고, 게이트 상태에서 처리하지 않은 사람 댓글이 있으면 발사합니다.

어려운 부분은 「같은 일을 두 번 하지 않기」입니다. 1분마다 같은 이슈를 다시 보므로 중복 방지 장치가 여러 겹 필요했습니다.

- **폴러 전체 잠금**: 이전 폴링이 아직 돌고 있으면 이번 폴링은 조용히 끝납니다.
- **이슈별 처리 중 표시**: 세션이 떠 있는 이슈는 `processing`으로 표시하고 건너뜁니다. 한 이슈에 세션은 동시에 하나만 돕니다. 표시가 너무 오래 남으면(세션이 죽었는데 회수되지 못한 경우) 일정 시간 뒤 자동으로 풀어 줍니다.
- **AI 차례 트리거 횟수**: 상태별로 몇 번 발사했는지 세어 두고, 0일 때만 on_enter로 발사합니다.
- **처리한 댓글 ID 목록**: 이미 반응한 댓글 ID를 이슈별로 쌓아 두고, 상한(예: 200개)을 넘으면 오래된 것부터 버립니다.
- **자기 댓글 제외**: 자동화 계정이 단 댓글은 트리거 대상에서 뺍니다. 이것을 빠뜨리면 에이전트가 자기 댓글에 반응해 끝없이 다시 깨어납니다.

```python
def should_trigger(issue, state, lane, bot_account_id):
    st = state.setdefault(issue.key, {"triggers": {}, "seen_comments": [], "status": "active"})
    if issue.status_category == "done" or st["status"] == "processing":
        return None

    if issue.status in lane["ai_turn"] and st["triggers"].get(issue.status, 0) == 0:
        return {"kind": "on_enter"}

    if issue.status in lane["gate"]:
        fresh = [c for c in issue.comments
                 if c.author_id != bot_account_id and c.id not in st["seen_comments"]]
        if fresh:
            return {"kind": "on_comment", "comments": fresh}
    return None
```

상태 파일 하나(`~/issue-agent/state.json`)에 이 값들과 폴러의 마지막 성공 시각을 함께 둡니다. 폴러가 살아 있는지는 로그 꼬리가 아니라 이 성공 시각과 heartbeat 파일의 수정 시각으로 판정합니다. 정상 폴링은 로그를 거의 남기지 않으므로 로그가 조용하다는 사실만으로는 아무것도 알 수 없습니다.

### 4. 프롬프트 조립

트리거가 성립하면 폴러가 프롬프트를 만듭니다. 들어가는 내용은 다음과 같습니다.

- **현재 상태와 이번 회차의 계약**: 「이번 실행은 설계 단계만 수행하고, 설계안을 게시한 뒤 확인 게이트로 옮기고 멈춘다」처럼 한 회차에 한 단계만 하도록 못 박습니다. 세션이 다음 단계까지 내달리지 않게 하는 가장 강한 장치가 이 문장이었습니다.
- **이슈 본문과 트리거 댓글**: 무엇을 해야 하는지, 사람이 무엇이라고 답했는지를 넣습니다.
- **이슈 메모리 문서**: 앞 회차들이 남긴 요약(아래 6절)을 길이 상한을 두고 넣습니다.
- **쓰기 규칙**: Jira 댓글과 상태 전이를 어떤 명령으로만 하라는 지시입니다. 이 규칙이 왜 필요한지는 3편에서 다룹니다.

조립한 프롬프트는 명령줄 인자로 직접 넘기지 않고 파일에 쓴 뒤 실행 스크립트가 그 파일을 읽어 넘깁니다. 프롬프트에는 사람이 쓴 댓글이 그대로 들어가므로 셸 인자로 이어 붙이면 따옴표 처리에서 사고가 납니다. 명령줄에 붙는 나머지 값은 고정 리터럴이나 UUID뿐이라 인용 처리를 해서 붙입니다.

### 5. `claude -p` 발사

발사 함수는 회차마다 파일 네 개를 만들고, 실행 스크립트를 새 세션 그룹으로 띄웁니다.

```python
import shlex, subprocess
from datetime import datetime
from pathlib import Path

RUNS = Path.home() / "issue-agent" / "runs"
DENY_WRITE = ["mcp__jira__addComment", "mcp__jira__transitionIssue"]

def spawn_session(issue_key, prompt, cwd, resume_id=None, model=None):
    run_dir = RUNS / issue_key
    run_dir.mkdir(parents=True, exist_ok=True)
    base = run_dir / datetime.now().strftime("%Y%m%d-%H%M%S")
    prompt_f, log_f, done_f, sh_f = (base.with_suffix(s) for s in (".prompt", ".log", ".done", ".sh"))
    prompt_f.write_text(prompt, encoding="utf-8")

    args = ["--output-format", "json", "--disallowedTools", *DENY_WRITE]
    if model:
        args += ["--model", model]
    if resume_id:
        args += ["--resume", resume_id]

    sh_f.write_text(
        "#!/usr/bin/env bash\n"
        f"cd {shlex.quote(str(cwd))}\n"
        f'claude -p "$(cat {shlex.quote(str(prompt_f))})" {" ".join(map(shlex.quote, args))} '
        f"> {shlex.quote(str(log_f))} 2>&1\n"
        f'echo "$?" > {shlex.quote(str(done_f))}\n'
    )
    sh_f.chmod(0o755)
    p = subprocess.Popen(["bash", str(sh_f)], cwd=cwd, start_new_session=True,
                         stdin=subprocess.DEVNULL, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
    return {"pid": p.pid, "log": str(log_f), "done": str(done_f)}
```

플래그마다 고른 이유가 있습니다.

- `-p`(`--print`): 비대화형 실행입니다. 프롬프트를 받아 한 번 돌고 결과를 표준 출력에 쓴 뒤 끝납니다. 스크립트와 CI에서 쓰라고 공식 문서가 제공하는 진입점입니다.
- `--output-format json`: 결과를 JSON 하나로 받습니다. 처음에는 사용량을 기록할 때만 켰는데, 세션 ID를 회수하려면 이 출력이 필요해서 지금은 항상 켭니다.
- `--disallowedTools`: Jira MCP 서버의 쓰기 도구를 프로세스 단위로 막습니다. 프롬프트에 「MCP로 쓰지 말라」고만 적었을 때 세션이 사람 계정으로 연결된 MCP를 써서 댓글을 단 일이 있었습니다. 지시와 차단을 이중으로 겁니다.
- `--model`: 단계 성격에 따라 모델을 바꿀 수 있게 열어 두었습니다. 같은 이유로 `--effort`도 설정값이 있을 때만 붙입니다.
- `--resume`: 이슈별 세션을 이어 갈 때 붙입니다(6절).
- `start_new_session=True`: 폴러가 끝나도 세션 프로세스가 함께 죽지 않게 합니다.

다음 폴링은 기록해 둔 PID에 `os.kill(pid, 0)`을 보내 살아 있는지 보고, 죽었으면 `.done` 파일의 종료 코드와 `.log`의 JSON을 읽어 결과를 회수합니다. 실행 중이면 그냥 건너뜁니다.

권한 모드에 대해서는 한 가지만 먼저 적어 둡니다. 무인 세션에서 권한 확인 창은 아무도 답하지 않으므로, 허용 규칙(allow)에 걸리지 않은 명령은 설정된 권한 모드에 따라 거부되거나 분류기의 판단에 맡겨집니다. 서브에이전트를 부르는 세션이라면 `Agent` 도구를 허용 목록에 넣어야 무인에서도 위임이 됩니다. 그리고 허용 규칙이 실제로 매칭되는지는 `--permission-mode dontAsk`로 분류기를 빼고 돌려 봐야 알 수 있었습니다. 규칙을 적어 둔 것과 규칙이 맞는 것은 다른 문제였고, 그 이야기는 3편의 안전장치에서 이어 갑니다.

### 6. 이슈별 세션 이어 가기: `session_id`와 `--resume`

초기 폴러는 트리거마다 완전히 새 대화로 세션을 띄웠습니다. 작업 디렉터리(이슈별 git worktree)는 이어졌지만, 앞 단계에서 Claude가 왜 그렇게 계획했는지, 설계에서 무엇을 버렸는지, 검수에서 무엇이 실패했는지는 대화에 남지 않았습니다.

그래서 이슈 키를 대화의 정체성으로 삼았습니다. Slack 봇이 스레드 ID로 세션을 이어 가는 것과 같은 방식입니다.

1. 첫 발사는 새 세션으로 띄우고, 끝나면 JSON 출력의 `session_id`를 꺼내 상태 파일의 그 이슈 항목에 저장합니다.
2. 다음 트리거부터는 그 값을 `--resume <session_id>`로 넘깁니다.
3. 재개가 실패하면(로그에 세션을 찾지 못했다는 오류가 남거나, 회수한 ID가 요청한 ID와 다르면) 저장해 둔 ID를 지웁니다. 즉시 다시 띄우지 않고 다음 트리거가 새 세션으로 시작하게 둡니다.

```python
import json

def harvest(proc, issue_state):
    try:
        out = json.loads(Path(proc["log"]).read_text(encoding="utf-8").strip().splitlines()[-1])
    except (ValueError, IndexError, OSError):
        issue_state.pop("session_id", None)   # 결과를 못 읽으면 다음 회차는 새 세션
        return None
    sid = out.get("session_id")
    if proc.get("resumed_from") and sid != proc["resumed_from"]:
        issue_state.pop("session_id", None)   # 재개가 조용히 새 대화가 된 경우
    elif sid:
        issue_state["session_id"] = sid
    return out
```

`--resume`만으로는 부족했습니다. 세션 기록에는 보존 기한이 있고, 기한이 지나거나 기록이 정리되면 재개가 실패합니다. 그래서 대화와 별개로 **이슈 메모리 문서**를 하나 둡니다. 세션이 단계를 마칠 때마다 요청 요약, 판정한 작업 유형, 계획, 설계 결정, 구현 요지, 되돌림 이력을 이 문서에 갱신하고, 폴러는 매 발사마다 이 문서를 프롬프트에 넣습니다. 이 문서는 git worktree 바깥(`~/issue-agent/runs/<이슈키>/memory.md`)에 둡니다. 저장소 안에 두면 작업 브랜치의 변경 목록이 지저분해집니다.

운영하면서 이 두 장치의 역할을 다시 정했습니다. 근거는 비용입니다.

- 세션을 이어 갈 수 있는 기한과 프롬프트 캐시가 따뜻한 기한은 다릅니다. 메모에 남은 관찰로는 구독 로그인에서 캐시 기한이 대략 1시간, 세션 재개 기한은 그보다 훨씬 깁니다. 공식 문서의 보장이 아니라 직접 관찰한 값입니다.
- 게이트 사이에는 사람의 승인이 끼어 있어 간격이 몇 시간에서 며칠입니다. 그 구간에서 `--resume`을 하면 세션은 살아 있지만 캐시는 식어 있어서, 쌓인 대화 전체를 할인 없이 다시 보내게 됩니다. 이슈가 길어질수록 이 값이 커집니다.
- 반면 메모리 문서는 길이 상한이 있어 비용이 일정합니다.

그래서 단계 사이의 맥락 복원은 **메모리 문서가 정본**이고, `--resume`은 직전 회차가 끝난 지 캐시 기한 안에 다시 깨어날 때만 쓰는 최적화로 내렸습니다. 인증을 API 키로 바꾸면 캐시 기한이 더 짧아지므로(관찰상 몇 분) `--resume`의 이점은 더 줄어듭니다. 한 이슈를 한 세션으로 끝까지 끌고 가는 그림은 매력적이지만, 사람이 끼는 워크플로에서는 짧고 독립적인 회차와 구조화된 인수인계 문서가 더 싸고 더 튼튼했습니다.

### 7. 회차별 산출물

이슈마다 디렉터리 하나를 두고, 회차마다 같은 이름 접두로 파일 네 개를 남깁니다.

```text
~/issue-agent/runs/<이슈키>/
├─ 20260818-101500.prompt   이번 회차에 실제로 넘긴 프롬프트 전문
├─ 20260818-101500.sh       그 프롬프트로 claude를 실행한 스크립트(플래그 포함)
├─ 20260818-101500.log      세션 출력(JSON)
├─ 20260818-101500.done     claude 프로세스의 종료 코드
├─ memory.md                이슈 메모리 문서
└─ session.json             session_id와 회차 이력
```

`.prompt`와 `.sh`가 있으면 어떤 회차든 같은 조건으로 다시 돌려 볼 수 있습니다. 무인 세션이 이상하게 행동했을 때 가장 먼저 여는 파일이 `.prompt`입니다. 에이전트 정의 파일을 고쳤는데 행동이 바뀌지 않는다면, 대개 프롬프트에 박힌 문장이 정의 파일보다 강하게 작용하고 있기 때문입니다(9절).

`.done`의 값이 0이라고 해서 일이 된 것은 아닙니다. 프롬프트 첫 줄이 등록되지 않은 명령이어서 세션이 아무 일도 하지 않고 끝났는데도 종료 코드는 0이었던 사례가 있습니다. 종료 코드만 보고 성공을 기록하면 안 된다는 점은 [종료 코드 0으로 끝나는 조용한 실패](/blog/2026/10/07/silent-failure-exit-code-fail-open.html)에서 따로 정리했습니다. 회수 단계에서는 최소한 JSON의 `is_error`와 `num_turns`까지 함께 봅니다.

### 8. 인증 모드와 사용량 계측

헤드리스 `claude -p`를 인증하는 방법은 두 가지를 놓고 비교했습니다.

| 방식 | 장점 | 주의할 점 |
|---|---|---|
| Console API 키(`ANTHROPIC_API_KEY`) | 자동화 용도가 약관상 명확하고, 쓴 만큼 과금됩니다 | 비용이 바로 청구됩니다. 프롬프트 캐시 기한이 짧습니다 |
| 구독 로그인(OAuth) | 사람 좌석과 같은 한도 안에서 돕니다 | 상시 자동화가 「개인의 통상 사용」 전제에 맞는지 회색지대가 남습니다 |

공식 문서에서 확인한 함정이 세 가지 있습니다.

- 비대화형(`-p`) 모드에서는 환경에 `ANTHROPIC_API_KEY`가 있으면 항상 그 키를 씁니다. 구독으로 돌리려던 스크립트가 남아 있던 키 때문에 API로 과금될 수 있으므로, 폴러는 발사할 때 어느 모드인지 로그에 한 줄 남깁니다.
- 브라우저 로그인이 불가능한 환경을 위해 `claude setup-token`으로 장기 OAuth 토큰(`CLAUDE_CODE_OAUTH_TOKEN`)을 발급할 수 있습니다. 구독 플랜이 전제입니다.
- CI용 `--bare` 모드는 OAuth와 키체인을 읽지 않습니다. API 키 방식과는 잘 맞지만, 구독 로그인에 기대는 스크립트에는 맞지 않습니다.

사용량은 세션 JSON 출력에서 읽어 이슈별로 한 줄씩 JSON Lines 파일에 쌓습니다.

```python
USAGE_KEYS = ("input_tokens", "output_tokens",
              "cache_read_input_tokens", "cache_creation_input_tokens")

def record_usage(issue_key, out, ledger=Path.home() / "issue-agent" / "usage.jsonl"):
    usage = out.get("usage") or {}
    row = {
        "ts": datetime.now().isoformat(timespec="seconds"),
        "issue": issue_key,
        "session_id": out.get("session_id"),
        "cost_usd": out.get("total_cost_usd"),
        "num_turns": out.get("num_turns"),
    }
    row.update({k: usage.get(k) for k in USAGE_KEYS})
    with ledger.open("a", encoding="utf-8") as f:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
```

기록을 보면 장기 이슈일수록 캐시 읽기 토큰이 입력 토큰보다 몇 자릿수 크게 쌓였습니다. 6절에서 `--resume`을 강등한 근거가 이 숫자였습니다.

필드 위치는 CLI 버전에 따라 달라질 수 있으니 직접 출력해 보고 맞추는 편이 안전합니다. 실제로 모델 이름을 최상위에서 읽도록 짰다가 그 자리에 키가 없어 모든 행이 `null`로 쌓인 적이 있습니다. 비용과 토큰 값은 정상이어서 한동안 아무도 알아채지 못했습니다. 계측이 조용히 틀어지는 경로는 4편에서 더 다룹니다.

### 9. 헤드리스에서 에이전트와 스킬이 로드되는 경로

폴러는 `claude -p`를 부를 때 특정 에이전트나 플러그인 디렉터리를 지정하는 인자를 쓰지 않았습니다. 그러면 무엇이 로드되는지는 Claude Code의 일반 탐색 규칙이 정합니다. 실행 디렉터리 기준의 프로젝트 설정, 사용자 설정의 활성 플러그인 목록, 사용자 전역 에이전트·스킬 디렉터리입니다.

이 구조에서 실제로 겪은 문제는 두 가지입니다.

1. **사본이 두 벌이면 로드되는 쪽이 최신이라는 보장이 없습니다.** 에이전트 정의가 설치 스크립트용 사본과 팀 공용 플러그인 사본으로 나뉘어 있었고, 개선은 한쪽에만 들어갔습니다. 점검해 보니 세션이 실제로 읽는 것은 플러그인 쪽의 오래된 정의였습니다. 그런데도 세션은 새 설계대로 움직였습니다. 행동 계약을 폴러가 매 회차 프롬프트에 직접 넣고 있었기 때문입니다. 결과는 맞았지만, 정의 파일을 고쳐도 아무 효과가 없는 상태였습니다.
2. **슬래시 명령으로 스킬을 부르는 방식은 저장소 정리 한 번에 끊깁니다.** 프롬프트 첫 줄에서 스킬을 슬래시 명령으로 불렀는데, 플러그인 쪽에서 스킬 디렉터리 배치를 바꾸자 그 명령이 미등록 상태가 됐습니다. CLI는 「알 수 없는 명령」으로 바로 끝났고 종료 코드는 0이었습니다. 지금은 스킬 문서를 절대 경로로 읽으라고 프롬프트에 적습니다. 파일만 있으면 성립하는 방식이 플러그인 배치, 캐시 버전, 이름공간 세 가지에 동시에 기대는 방식보다 덜 깨집니다.

정리하면, 헤드리스 세션에서 행동을 확실히 정하는 것은 **프롬프트에 직접 들어간 문장**입니다. 정의 파일과 스킬은 그 문장이 가리키는 참고 자료로 두고, 실제로 무엇이 로드됐는지는 `.prompt`와 세션 로그로 확인합니다.

## 함정과 트레이드오프: 폴러냐 에이전트냐

### 두 실행 모델

설계 초기에 두 실행 모델을 비교했습니다.

| | 무상태 헤드리스 | 상주 오케스트레이터 |
|---|---|---|
| 구조 | 주기 실행이 `claude -p`를 한 번씩 띄움 | 살아 있는 Claude 세션이 터미널 멀티플렉서에 워커 세션을 띄워 조율 |
| 강점 | 단순하고, 사람을 며칠 기다리는 구간에 강함 | 단계 안의 긴 멀티턴 작업, 워커 간 직렬·병렬 조율 |
| 약점 | 회차 하나 안에서만 생각함 | 상주 비용, GUI 세션 의존, 죽으면 스케줄도 함께 멈춤 |

결론은 둘 중 하나가 아니었습니다. 시간 척도가 다릅니다. 게이트 사이의 대기는 분에서 일 단위이고 그동안 세션을 붙잡아 두는 것은 낭비입니다. 반대로 구현과 검증 같은 단계 안의 작업은 멀티턴과 위임이 필요합니다. 그래서 **단계 사이는 무상태 폴러가, 단계 안의 깊은 작업은 세션 내부의 서브에이전트가** 맡는 혼합 모델로 갔습니다.

이 혼합이 성립하는 전제는 하나입니다. **상태는 항상 바깥에 둡니다.** 세션은 단계를 마칠 때마다 Jira 상태와 이슈 메모리 문서를 갱신합니다. 그러면 어떤 세션이 언제 죽어도 다음 폴링이 바깥 상태를 읽고 그 지점부터 이어 갑니다.

### 판정을 어디에 둘 것인가

폴러 코드가 커지면서 다시 한번 경계를 그었습니다. 폴러가 하는 일을 성격별로 나누면 두 층입니다.

- **배관(결정론)**: 주기 실행, 잠금, JQL 조회, 상태 파일 저장, heartbeat, HTTP 재시도. 매번 똑같이 동작해야 하므로 코드에 남깁니다.
- **판정(추론)**: 이번 회차가 어떤 성격의 단계인지, 어떤 댓글이 처리할 입력인지, 이슈 규모와 위험도가 어느 정도인지, 진행이 멈췄는지. 규칙이 늘수록 `if` 분기가 늘고 테스트가 어려워집니다.

보고 나니 판정의 상당 부분은 이미 프롬프트로 넘어가 있었습니다. 폴러가 단계를 판정하고 그 결과를 「이번 회차의 계약」으로 프롬프트에 써 주고 있었으니까요. 그래서 다음 설계는 판정의 위치를 파이썬에서 오케스트레이터 세션으로 옮기는 방향입니다. 폴러는 「이 이슈를 처리하라」만 넘기고, 오케스트레이터가 단계를 판정해 작업에 맞는 모델의 워커 서브에이전트에게 맡기고, 끝나면 Jira 정리를 합니다.

다만 판정을 모델에 넘기는 만큼 비결정성이 들어옵니다. 그래서 되돌리기 어려운 행위는 한곳에 모아 결정론적인 가드로 감쌉니다.

- 상태 전이는 허용 목록에 있는 전이만 합니다.
- Jira 쓰기는 오케스트레이터만, 정해진 래퍼 명령으로만 합니다. 워커가 각자 Jira를 건드리면 자기 댓글에 다시 깨어나는 고리가 되살아납니다.
- 서브에이전트 중첩은 얕게 둡니다. 허용 깊이와 그것을 제어하는 환경 변수는 Claude Code 버전마다 다르므로, 운영 장비의 `claude --version`부터 확인합니다.

모델은 서브에이전트 정의의 `model` 값이 CLI의 `--model`보다 우선합니다. 오케스트레이터를 가벼운 모델로 띄워도 구현 워커 정의에 상위 모델을 적어 두면 워커는 그 모델로 돕니다. 다만 오케스트레이터가 하는 일은 상태 전이와 사람 댓글의 의도 분류처럼 틀리면 영향이 큰 판단이라, 오케스트레이터를 가장 싼 모델로 내리는 것은 실측을 보고 결정하기로 했습니다. 비용은 오케스트레이터를 강등하는 쪽이 아니라 워커 모델을 작업에 맞게 고르는 쪽에서 먼저 줄입니다.

## 정리

- 폴러는 판정하고 발사한 뒤 바로 끝나고, 작업은 떨어져 나간 `claude -p` 세션이 합니다. 비용은 폴링 주기가 아니라 트리거 횟수에 비례합니다.
- 트리거는 Jira 상태로 정합니다. AI 차례 상태는 진입할 때 한 번, 게이트 상태는 사람의 새 댓글에만 반응합니다. 잠금, 처리 중 표시, 트리거 횟수, 처리한 댓글 ID, 자기 댓글 제외를 겹쳐 중복을 막습니다.
- 발사는 프롬프트를 파일로 넘기고, `--output-format json`으로 결과를 받고, `--disallowedTools`로 쓰기 도구를 막고, 새 세션 그룹으로 띄웁니다. 회차마다 프롬프트, 실행 스크립트, 로그, 종료 코드를 남깁니다.
- 단계 사이의 맥락은 길이 상한이 있는 이슈 메모리 문서로 복원하고, `--resume`은 캐시가 따뜻할 때만 쓰는 최적화로 둡니다.
- 헤드리스에서 행동을 확실히 정하는 것은 프롬프트에 직접 들어간 문장입니다. 실제로 무엇이 로드됐는지는 회차별 산출물로 확인합니다.
- 단계 사이는 무상태 폴러가, 단계 안은 세션 내부의 서브에이전트가 맡는 혼합 모델로 갔고, 그 전제는 상태를 항상 바깥에 두는 것입니다.

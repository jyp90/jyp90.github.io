## 문제와 배경

JDK 8, Spring 4, JSP, MyBatis로 된 레거시 웹 애플리케이션을 로컬 Tomcat에 띄우면, 스크립트를 실행한 뒤 첫 화면이 뜰 때까지 100초가 넘게 걸렸습니다. DB는 로컬이 아니라 사내망의 개발 DB 서버를 바라보는 구성입니다.

느린 이유에 대한 짐작은 여럿 있었습니다. "첫 요청이 느리니 JSP 최초 컴파일 때문이다", "Tomcat의 `work` 캐시가 재기동 때마다 지워진다", "Gradle 빌드가 무겁다" 같은 것들입니다. 셋 다 그럴듯했지만 셋 다 아니었습니다. 이 글은 짐작 대신 구간별로 재서 원인을 좁힌 순서를 정리합니다. 결론부터 말하면 원인은 커넥션 풀의 `initialSize` 하나였고, 그 과정에서 JDBC 로깅 프록시가 로그를 하나도 남기지 않으면서 매 요청 비용만 받아 가고 있다는 사실도 드러났습니다.

## 1단계: 구간을 나눠 잽니다

"기동이 느리다"는 말은 여러 구간을 한데 묶은 표현입니다. 먼저 스크립트 실행부터 첫 응답까지를 다음 네 구간으로 나눴습니다.

1. 빌드(`gradle clean war`)
2. Tomcat 실행 환경 준비와 WAR 배포
3. Tomcat 기동부터 Spring 컨텍스트 초기화 완료까지
4. 첫 HTTP 요청에 대한 응답

구간마다 시각을 찍는 스크립트는 따로 만들 필요가 없을 만큼 단순합니다. 아래는 이 글을 위해 새로 쓴 예시라 그대로 실행해 본 것은 아니며, 빌드 명령과 기동 명령, 포트는 환경에 맞게 바꿔야 합니다.

```bash
#!/usr/bin/env bash
# phase-timer.sh — 로컬 기동을 구간별로 잽니다.
set -euo pipefail

PORT=${PORT:-8080}
URL=${URL:-http://localhost:${PORT}/login}

now() { python3 -c 'import time; print(f"{time.time():.3f}")'; }
lap() { printf '%-28s %7.1fs\n' "$1" "$(echo "$3 - $2" | bc)"; }

t0=$(now)
./gradlew -q clean war
t1=$(now)

cp build/libs/app.war "$CATALINA_HOME/webapps/ROOT.war"
t2=$(now)

"$CATALINA_HOME/bin/catalina.sh" start >/dev/null
# 컨텍스트 초기화가 끝났다는 로그 한 줄을 기다립니다.
until grep -q 'Server startup in' "$CATALINA_HOME/logs/catalina.out" 2>/dev/null; do
  sleep 0.2
done
t3=$(now)

# 첫 요청: 상태 코드와 전체 소요 시간을 함께 남깁니다.
curl -s -o /dev/null -w 'first  %{http_code} %{time_total}s\n' --max-time 300 "$URL"
t4=$(now)
curl -s -o /dev/null -w 'second %{http_code} %{time_total}s\n' "$URL"

lap "build"                "$t0" "$t1"
lap "deploy"               "$t1" "$t2"
lap "tomcat + spring"      "$t2" "$t3"
lap "first request"        "$t3" "$t4"
```

로그 문구(`Server startup in`)는 Tomcat 버전과 로케일에 따라 다릅니다. 한국어 로케일에서는 "서버가 [N] 밀리초 내에 시작되었습니다"처럼 번역되어 나오므로 grep 패턴을 맞춰야 합니다. macOS 기본 `date`는 소수점 이하 초를 지원하지 않아서 시각은 `python3`로 찍었습니다.

결과는 다음과 같았습니다.

| 구간 | 소요 | 비중 |
|---|---:|---:|
| 빌드 | 3.7초 | 3% |
| 실행 환경 준비 + WAR 배포 | 0.8초 | 1% |
| Tomcat 기동 + Spring 컨텍스트 | 8.1초 | 7% |
| **첫 요청 한 건** | **106.7초** | **88%** |
| 같은 URL 두 번째 요청 | 0.648초 | — |

이 표 하나로 탐색 범위가 정해졌습니다. 같은 URL이 처음에는 106.7초, 두 번째에는 0.6초 남짓입니다. 전체 시간의 대부분이 첫 요청 한 건에 몰려 있으니, 빌드를 아무리 줄여도 3%를 건드리는 셈입니다. Spring 컨텍스트도 10초 안쪽에 올라왔으므로 "Spring이 무겁다"는 가설도 여기서 빠집니다.

## 2단계: 범인이 아닌 것부터 지웁니다

"첫 요청만 느리다"는 증상은 지연 초기화를 가리킵니다. 레거시 JSP 애플리케이션에서 가장 먼저 떠오르는 지연 초기화는 JSP 최초 컴파일입니다. 그래서 이것부터 확인했습니다.

| 의심 | 확인 방법 | 결과 |
|---|---|---|
| JSP 최초 컴파일 | 컴파일된 JSP 클래스가 `work` 디렉터리에 남아 있는 상태로 재기동 | 첫 요청 110.9초. 캐시가 있어도 그대로입니다 |
| 재기동 때 `work` 캐시가 지워짐 | 재기동 전후로 `work` 아래 `.class` 개수를 셈 | 개수가 같습니다. 캐시는 이미 재사용되고 있었습니다 |
| Gradle 빌드 | 변경 없을 때와 실제 컴파일이 일어날 때 각각 측정 | 3~7초, 전체의 3~7% |
| Tomcat·Spring 기동 | Tomcat이 남기는 기동 완료 로그의 밀리초 값 | 약 13초 |

`work` 캐시 확인은 명령 한 줄이면 됩니다.

```bash
# Tomcat이 JSP를 컴파일해 둔 클래스 파일 수 — 재기동 전후로 비교합니다.
find "$CATALINA_HOME/work" -name '*_jsp.class' | wc -l
```

캐시가 살아 있는데도 첫 요청 시간이 그대로라면 JSP 컴파일은 원인이 아닙니다. JSP를 빌드 시점에 미리 컴파일하는 방안도 후보로 올라와 있었지만, 병목이 아닌 곳을 고치면 빌드 시간만 늘어납니다. 짐작으로 개선안부터 세웠다면 실제로 없는 병목을 고치는 데 시간을 썼을 것입니다.

## 3단계: 컨테이너 비용과 요청 비용을 가릅니다

남은 후보는 "첫 요청이 애플리케이션 안에서 무엇을 기다리는가"입니다. 그 전에 WAS 자체가 요청당 얼마를 쓰는지 기준선을 잡아 두면 이후 숫자를 해석하기 쉬워집니다. 서블릿 필터 단계에서 끝나는 리다이렉트, 정적 리소스, 가장 가벼운 동적 페이지를 각각 여러 번 재서 중앙값을 봤습니다.

| 요청 종류 | 중앙값 |
|---|---:|
| 필터에서 끝나는 301 리다이렉트 | 0.001초 |
| 정적 이미지 | 0.004초 |
| 가장 가벼운 동적 페이지 | 0.818초 |

1ms와 800ms의 차이입니다. 컨테이너가 차지하는 몫은 거의 없고, 시간은 애플리케이션 코드와 그 뒤의 DB 왕복에서 나온다는 뜻입니다.

반복 측정 스크립트도 단순하게 만들 수 있습니다. 역시 이 글을 위해 새로 쓴 예시입니다.

```bash
#!/usr/bin/env bash
# median.sh URL [횟수] — 같은 URL을 N번 요청해 중앙값을 출력합니다.
set -euo pipefail
url=$1; n=${2:-7}

for _ in $(seq "$n"); do
  curl -s -o /dev/null -w '%{time_total}\n' "$url"
done | sort -n | awk '{ a[NR] = $1 }
  END {
    m = (NR % 2) ? a[(NR + 1) / 2] : (a[NR / 2] + a[NR / 2 + 1]) / 2
    printf "n=%d min=%.3f median=%.3f max=%.3f\n", NR, a[1], m, a[NR]
  }'
```

중앙값을 고집한 이유가 있습니다. DB가 사내망 건너편에 있으면 왕복 시간이 응답 시간을 지배하고, 같은 서버의 같은 경로도 회차에 따라 1.5초에서 6초 넘게까지 흔들렸습니다. 이 정도 편차에서 1회 측정으로 20% 차이를 논하면 잡음을 결론으로 착각하게 됩니다. 경로당 5~7회를 재고, 평균 대신 이상치에 덜 흔들리는 중앙값을 썼습니다.

## 4단계: 커넥션 풀 `initialSize`로 좁힙니다

첫 요청에서 처음 일어나는 일 중 DB와 관련된 것은 커넥션 풀 초기화입니다. 데이터소스 설정을 열어 보니 Commons DBCP 1.x의 `BasicDataSource`가 세 속성에 같은 프로퍼티를 쓰고 있었습니다. 아래는 구조만 옮겨 새로 쓴 예시입니다.

```xml
<bean id="dataSource" class="org.apache.commons.dbcp.BasicDataSource" destroy-method="close">
    <property name="driverClassName" value="${db.driver}"/>
    <property name="url"             value="${db.url}"/>
    <property name="username"        value="${db.username}"/>
    <property name="password"        value="${db.password}"/>
    <property name="maxActive"       value="${db.pool.size}"/>
    <property name="maxIdle"         value="${db.pool.size}"/>
    <property name="initialSize"     value="${db.pool.size}"/>
</bean>
```

그리고 로컬 프로파일 하나의 `db.pool.size`가 200이었습니다.

DBCP 1.x의 `BasicDataSource`는 빈이 만들어질 때 커넥션을 열지 않습니다. 첫 `getConnection()` 호출에서 내부 풀을 만들고, 이때 `initialSize`만큼 커넥션을 미리 채운 다음에야 호출자에게 커넥션을 돌려줍니다. 그래서 Spring 컨텍스트는 10초 안쪽에 멀쩡히 올라오고, 기다림은 전부 첫 요청으로 밀립니다. 첫 요청은 원격 DB 커넥션 200개가 다 열릴 때까지 기다리고 있었던 셈입니다. 커넥션 하나를 여는 데 TCP 연결, TLS나 인증 핸드셰이크, 세션 초기화까지 합쳐 0.4초 정도라고 하면 200개에 80초입니다. 이 0.4초는 실측 결과를 거꾸로 나눠 본 추정치이고, 커넥션 하나의 개설 시간을 따로 잰 것은 아닙니다.

가설을 확인하는 방법은 이 값만 바꾸고 나머지는 그대로 두는 것입니다.

| 조건 | 첫 200 응답까지 |
|---|---:|
| 풀 크기 200 | 106.7초 |
| **풀 크기 10** | **26.1초** |

다른 로컬 프로파일들과 같은 10으로 낮추자 첫 응답까지 80초가 줄었습니다. 이 단계에서는 드라이버나 로그 설정 같은 다른 변수는 일부러 건드리지 않았습니다. 두 가지를 같이 바꿨다면 어느 쪽 효과인지 가를 수 없기 때문입니다. 실제로 뒤에서 다룰 드라이버 교체까지 적용한 최종값은 25.4초였으니, 기동 시간 단축은 사실상 전부 풀 크기 덕분이었습니다.

### 200은 실수가 아니었습니다

로컬 프로파일의 200은 운영과 비슷한 동시 접속을 재현해 부하를 재려고 일부러 올려 둔 값이었습니다. 그 측정이 끝난 뒤에도 값이 남아서 평소 개발까지 느리게 만들고 있었습니다. 그래서 값을 되돌리면서 설정 파일 주석에 "부하 측정을 다시 할 때는 이 한 줄만 올리면 된다"고 적어 두었습니다. 목적이 있어서 바꾼 설정은 목적이 끝났을 때 되돌릴 방법까지 함께 남겨야 다음 사람이 헷갈리지 않습니다.

### 풀을 키우면 기동도 같이 느려지는 구조

이 설정은 `initialSize`와 `maxActive`를 한 프로퍼티로 묶어 두었기 때문에, 풀을 키우면 첫 요청도 반드시 같이 느려집니다. 서버 환경도 같은 구조라면 배포할 때마다 첫 요청이 풀 전체가 열리기를 기다립니다. DB와 같은 네트워크에 있는 서버라면 커넥션 개설이 훨씬 빠르겠지만, 구조 자체는 같습니다.

풀은 크게 두고 기동만 빠르게 하려면 둘을 떼면 됩니다.

```xml
<property name="maxActive"   value="${db.pool.max}"/>
<property name="maxIdle"     value="${db.pool.max}"/>
<property name="initialSize" value="${db.pool.initial}"/>  <!-- 예: 5~10 -->
```

```properties
db.pool.max=200
db.pool.initial=10
```

이 분리안은 모든 환경이 공유하는 설정 파일을 건드려야 해서 아직 적용하지 않았습니다. 적용한다면 트래픽이 몰리는 시각 직후에 배포할 때 풀이 늘어나는 동안 커넥션 대기가 생기는지 함께 봐야 합니다. 미리 채워 두는 것은 첫 요청을 느리게 만드는 대신, 피크 상황에서 커넥션을 새로 여는 비용을 앞당겨 치르는 장치이기도 하기 때문입니다.

## 5단계: 로그를 꺼도 남는 JDBC 로깅 프록시 비용

풀 문제는 기동 시간을 설명하지만, 기동 뒤의 응답도 체감상 느렸습니다. 로컬 프로파일들은 JDBC 드라이버로 log4jdbc의 `net.sf.log4jdbc.DriverSpy`를, URL로 `jdbc:log4jdbc:` 접두어가 붙은 주소를 쓰고 있었습니다. log4jdbc는 실제 드라이버 앞에 서서 `Connection`, `Statement`, `ResultSet`을 모두 자기 프록시 객체로 감싸고, 그 프록시가 호출을 실행하는 김에 SQL과 실행 시간을 로그로 남기는 방식입니다.

여기서 흔히 하는 판단이 "로그를 끄면 비용도 사라진다"입니다. 실제로 로그 설정에서는 `jdbc.audit`, `jdbc.connection`, `jdbc.sqlonly`, `jdbc.resultset`이 모두 `OFF`, `jdbc.sqltiming`은 `ERROR`여서 SQL이 한 줄도 남지 않고 있었습니다. 그런데 드라이버만 벤더 순정 드라이버로 바꾸고 경로마다 7회씩 재 보니 차이가 분명했습니다.

| 경로 | 로깅 프록시 | 순정 드라이버 | 변화 |
|---|---:|---:|---:|
| 로그인 화면 | 0.907초 | 0.630초 | −30.5% |
| 메인 화면 | 1.040초 | 0.700초 | −32.7% |
| 검색 결과 | 2.088초 | 1.423초 | −31.9% |
| 분류별 목록 | 2.700초 | 2.162초 | −19.9% |

로그는 하나도 남기지 않으면서 감싸는 비용만 치르고 있었던 것입니다. 프록시 객체 생성과 호출 위임, 로그 레벨 확인은 로그 출력 여부와 관계없이 JDBC 호출마다 일어납니다. 화면 하나가 쿼리를 수십 번 실행하고 결과 행마다 `ResultSet` 메서드를 여러 번 부른다면 그 횟수만큼 쌓입니다. 다만 이 비용을 프로파일러로 쪼개 어느 부분이 가장 큰지까지 확인하지는 않았습니다. 위 표는 드라이버만 바꿨을 때의 관찰 결과이고, 같은 비율이 다른 환경에서도 나온다는 보장은 없습니다.

드라이버 교체는 프로퍼티 두 줄입니다.

```properties
# 기본: 순정 드라이버
db.driver=com.microsoft.sqlserver.jdbc.SQLServerDriver
db.url=jdbc:sqlserver://dbhost:1433;databaseName=appdb

# SQL을 봐야 할 때만 아래 두 줄로 바꾸고, 로그 설정에서 jdbc.sqltiming을 INFO로 올립니다.
# db.driver=net.sf.log4jdbc.DriverSpy
# db.url=jdbc:log4jdbc:sqlserver://dbhost:1433;databaseName=appdb
```

교체하면서 한 가지 함정이 더 있었습니다. 프로파일 파일에는 다른 DB를 가리키는 URL들이 주석으로 남아 있었는데, 이것들이 `jdbc:log4jdbc:` 접두어를 단 채로 남아 있으면 나중에 누군가 주석을 푸는 순간 순정 드라이버가 그 URL을 받아들이지 못해 `No suitable driver`로 기동이 실패합니다. 기본 드라이버를 바꿀 때는 주석 처리된 대안 URL까지 같은 형식으로 맞춰 둬야 합니다.

### 로그가 정말 붙어 있는지도 확인합니다

측정하는 과정에서 하나 더 발견한 것이 있습니다. 일부 로컬 프로파일에서는 애플리케이션 로그가 아예 남지 않고 있었습니다. log4j 1.2는 별도 지정이 없으면 클래스패스에서 `log4j.xml`이나 `log4j.properties`라는 이름을 찾는데, 저장소에는 `log4j-local.xml`처럼 환경별 이름을 붙인 파일만 있었고 기동 스크립트도 어느 파일을 쓸지 지정하지 않았습니다. 기동 실패 원인조차 로그에 남지 않는 상태였습니다.

JVM 옵션으로 설정 파일을 지정하면 됩니다. 값을 파일 시스템 경로가 아니라 클래스패스 리소스 이름으로 주면, WAR로 배포하든 압축을 푼 디렉터리로 띄우든 `WEB-INF/classes`에서 같은 이름으로 찾으므로 기동 방식과 무관하게 동작합니다.

```bash
# setenv.sh
JAVA_OPTS="$JAVA_OPTS -Dlog4j.configuration=log4j-local.xml"
```

이 옵션을 기동 스크립트뿐 아니라 Tomcat의 `setenv.sh`에도 넣어 두면 IDE나 `catalina.sh`로 직접 띄울 때도 똑같이 적용됩니다. 측정 전에 "로그가 없다"는 사실이 "아무 일도 일어나지 않았다"는 뜻인지, "로그가 연결되어 있지 않다"는 뜻인지부터 가려 두는 편이 안전합니다.

## 함정과 트레이드오프

- **`initialSize`는 기동 비용을 없애지 않고 옮깁니다.** DBCP 1.x처럼 지연 초기화하는 풀에서는 그 비용이 첫 요청으로 가고, 컨텍스트 기동 중에 DB를 건드리는 빈이 있다면 기동 단계로 갑니다. 어느 쪽이든 원격 DB에서는 "풀 크기 × 커넥션 개설 시간"만큼 기다립니다.
- **`initialSize`를 무작정 0이나 1로 내리는 것도 답이 아닙니다.** 운영에서는 미리 채운 커넥션이 배포 직후 몰리는 요청을 받아 냅니다. 로컬은 작게, 서버는 측정한 동시 사용량에 맞춰 두되 `maxActive`와는 따로 관리하는 편이 낫습니다.
- **로깅 프록시는 끄는 것이 아니라 빼는 것입니다.** 로그 레벨을 `OFF`로 내려도 프록시는 그대로 호출 경로에 남습니다. SQL을 봐야 하는 상황에서만 드라이버를 바꿔 끼우는 방식이 더 정직합니다.
- **측정값은 환경을 탑니다.** 커넥션 하나의 개설 시간은 네트워크 거리, 인증 방식, VPN 여부에 따라 크게 다릅니다. 위 숫자는 사내망 건너편 DB를 기준으로 한 값이고, 같은 네트워크에 있는 서버에서는 훨씬 작게 나올 것입니다.

## 정리

- 기동이 느리면 먼저 빌드, 배포, 컨텍스트 초기화, 첫 요청으로 구간을 나눠 잽니다. 이번에는 첫 요청 한 건이 전체의 88%였고, 그 표 하나로 빌드와 Spring 기동이 후보에서 빠졌습니다.
- 그럴듯한 가설(JSP 최초 컴파일, `work` 캐시 유실)은 캐시가 있는 상태로 재기동하고 클래스 개수를 세는 것만으로 반증했습니다.
- 변수를 하나씩만 바꿔 원인을 확정했습니다. 커넥션 풀 크기 하나를 200에서 10으로 내리자 첫 응답이 106.7초에서 26.1초로 줄었습니다. DBCP 1.x는 첫 `getConnection()`에서 `initialSize`만큼 커넥션을 열고 나서야 응답하기 때문입니다.
- log4jdbc 같은 JDBC 로깅 프록시는 로그를 모두 꺼도 요청당 20~30% 안팎의 비용을 남겼습니다. 기본은 순정 드라이버로 두고 필요할 때만 바꿔 끼웁니다.
- 원격 DB를 낀 응답 시간은 회차마다 크게 흔들리므로, 경로당 여러 번 재고 중앙값으로 비교합니다.

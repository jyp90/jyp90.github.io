## 문제와 배경

오래된 Java 웹 애플리케이션 몇 개가 각자 웹폰트를 git 저장소에 커밋해 두고 있었습니다. 같은 본문용 글꼴 파일이 프런트 웹 애플리케이션, 관리자 애플리케이션, 그 밖의 내부 애플리케이션에 따로 들어 있었고, 빌드할 때마다 WAR에 실려 배포됐습니다. 그러다 보니 문제가 몇 가지 생겼습니다.

- 배포 산출물이 글꼴 용량만큼 무거워집니다. 업로드와 배포 시간도 그만큼 늘어납니다.
- 글꼴을 고치거나 바꿀 때 애플리케이션마다 같은 작업을 반복해야 합니다.
- 일부 애플리케이션은 woff2 파일만 커밋해 두고 CSS에서는 여러 포맷과 굵기를 선언하고 있었습니다. 선언한 나머지 파일은 모두 404였습니다.
- 반대 방향의 요청도 헷갈렸습니다. 「이 PDF 파일 바꿔 주세요」라는 요청을 받으면 배포가 필요한지, 파일만 바꾸면 되는지를 소스만 봐서는 판단할 수 없었습니다.

그래서 정적 리소스를 WAR에서 덜어내 오브젝트 스토리지(S3)와 그 앞의 CDN(CloudFront)으로 옮기기로 했습니다. 다만 옮기기 전에 먼저 답해야 할 질문이 있습니다. **지금 이 URL은 누가 응답하고 있는가**입니다.

글에 나오는 스크립트와 명령은 이 글을 위해 일반 이름으로 새로 쓴 예시이고, 그대로 실행해 보지는 않았습니다.

## 이 URL은 누가 응답하는가

레거시 웹 서비스에서 정적 파일 하나가 브라우저에 오기까지 거칠 수 있는 곳은 대략 셋입니다.

| 계층 | 파일이 있는 곳 | 교체 방법 |
|---|---|---|
| WAR 안 | `src/main/webapp/` 아래, 서블릿 컨테이너가 서빙 | 빌드와 배포가 필요합니다 |
| 앞단 웹 서버 | 웹 서버 장비의 파일시스템, 또는 거기에 마운트한 오브젝트 스토리지 | 파일만 바꾸면 됩니다 |
| 오브젝트 스토리지 + CDN | 버킷 객체, CDN 엣지 캐시 | 객체를 바꾸고 캐시 수명을 고려합니다 |

같은 도메인 아래에서도 경로마다 계층이 다릅니다. 예를 들어 `/css/`, `/js/`, `/images/`는 WAR 안에 있고, `/files/` 같은 첨부 경로는 앞단 웹 서버가 마운트된 스토리지에서 읽어 주는 식입니다.

### 설정 파일은 증거가 아닙니다

소스에서 Spring MVC의 정적 리소스 매핑을 찾으면 이런 줄이 나올 수 있습니다.

```xml
<mvc:resources mapping="/files/**" location="file:///D:/attach/files/" />
<mvc:resources mapping="/images/**" location="/images/" cache-period="31536000" />
```

첫 줄만 보면 WAS가 `/files/`를 서빙한다고 판단하기 쉽습니다. 그런데 운영 서버가 Linux라면 `D:` 드라이브 경로는 존재하지 않으므로 이 핸들러는 파일을 찾지 못합니다. Windows에서 돌던 시절의 잔재입니다. 앞단 웹 서버가 이 경로를 먼저 가로채면 요청은 애초에 WAS까지 오지 않습니다. **매핑이 선언돼 있다는 사실은 그 핸들러가 실제로 응답한다는 증거가 아닙니다.**

### 응답 헤더로 판정합니다

소스를 읽는 것보다 헤더 한 번이 빠릅니다.

```bash
curl -sSI "https://www.example.com/files/manual.pdf"
curl -sSI "https://www.example.com/images/logo.png"
curl -sSI "https://static.example.com/static/fonts/body-regular.woff2"
```

판정에 쓸 수 있는 신호는 다음과 같습니다.

| 관측 | 해석 |
|---|---|
| `server: Apache` | Apache httpd가 응답했습니다. Tomcat이라면 `Apache-Coyote`이거나 헤더가 아예 없는 경우가 많습니다 |
| ETag가 `"<16진수>-<16진수>"`이고 앞부분이 `content-length`를 16진수로 바꾼 값 | httpd의 기본 ETag(`FileETag MTime Size`) 형식입니다. 웹 서버가 파일시스템에서 직접 읽었다는 뜻입니다 |
| ETag가 32자리 16진수(MD5 형태), `server: AmazonS3` | S3가 응답했습니다(멀티파트 업로드 객체는 `-<파트 수>`가 붙습니다) |
| `x-cache: Hit from cloudfront`, `age`, `via` | CDN 엣지 캐시가 응답했습니다 |
| ETag가 `W/"<길이>-<수정 시각>"` | Tomcat `DefaultServlet`의 약한 ETag입니다 |
| 선언한 `Cache-Control`이 없음 | 위 예시처럼 `cache-period`를 선언한 경로인데 `Cache-Control`이 안 붙는다면, 요청이 Spring 핸들러까지 가지 않았다는 신호입니다 |

마지막 줄이 특히 쓸모 있습니다. 「있어야 할 헤더가 없다」는 것도 증거가 됩니다. 다만 ETag 형식은 각 서버의 기본 설정 기준이므로, 설정을 바꾼 환경에서는 다르게 보일 수 있습니다.

### 서버에서 파일을 찾을 때는 `mount`부터 봅니다

헤더로 「웹 서버가 파일시스템에서 읽는다」까지 알았다면, 다음은 그 파일시스템이 실제로 어디인지입니다. 서버에 들어가 파일명으로 `find`를 돌리면 못 찾는 경우가 있습니다.

```bash
# 이렇게 하면 마운트된 파일시스템을 건너뜁니다
find / -xdev -name 'manual.pdf'
```

`-xdev`는 다른 파일시스템으로 내려가지 않는 옵션이라, FUSE로 마운트한 S3나 NFS 경로가 정확히 빠집니다. `-xdev`를 빼면 FUSE 마운트 전체를 순회하느라 매우 느려집니다. 순서를 뒤집어 마운트 목록부터 봅니다.

```bash
mount | grep -iE 's3|fuse|nfs|efs'
ps -ef | grep -i mount-s3 | grep -v grep   # 버킷 이름과 prefix가 커맨드라인에 보입니다
```

`mountpoint-s3 on /data/files type fuse ...` 같은 한 줄이 나오면, 그 경로의 실체는 서버 디스크가 아니라 버킷입니다.

## 옮길 대상 고르기

### 실제로 쓰는 파일만 셉니다

`font-family` 이름으로 사용처를 세면 참조가 부풀려집니다. 브라우저가 파일을 받는 것은 `@font-face`의 `url()`이므로, 그 경로가 로컬 파일을 가리키는지를 봅니다.

이때 상대경로는 **CSS 파일 위치 기준**으로 풀어야 합니다. `assets/icon-font/css/icons.css` 안의 `url(../fonts/icons.woff)`는 웹 루트의 `fonts/`가 아니라 `assets/icon-font/fonts/`입니다. 라이브러리째 들어온 아이콘 폰트는 대개 이런 구조라서, 웹 루트 기준으로 풀면 엉뚱한 파일을 지우게 됩니다.

### 이름이 아니라 해시로 대조합니다

CDN에 같은 이름의 파일이 이미 있어도 같은 파일이라는 보장은 없습니다. 글꼴은 이름은 같고 버전만 다른 경우가 흔합니다. 파일마다 CDN에서 받아 해시를 비교합니다.

```bash
#!/usr/bin/env bash
# 로컬 폰트와 CDN 사본을 sha256으로 대조합니다
CDN=https://static.example.com/static/fonts
for f in src/main/webapp/fonts/*; do
  name=$(basename "$f")
  remote=$(curl -sf "$CDN/$name" | shasum -a 256 | cut -d' ' -f1)
  local_=$(shasum -a 256 "$f" | cut -d' ' -f1)
  if [ -z "$remote" ] || [ "$remote" = "$(printf '' | shasum -a 256 | cut -d' ' -f1)" ]; then
    echo "MISSING $name"
  elif [ "$remote" = "$local_" ]; then
    echo "SAME    $name"
  else
    echo "DIFF    $name"
  fi
done
```

`curl -f`는 4xx 응답에서 본문을 버리므로, 없는 파일은 빈 입력의 해시가 나옵니다. 그 경우를 `MISSING`으로 분류합니다. 결과는 세 갈래로 나뉩니다.

- `SAME`: 경로만 바꾸면 됩니다. 다른 애플리케이션이 이미 CDN 주소로 쓰고 있는 파일이라면 더 안전합니다. 다만 「누가 이미 참조한다」는 사실이 「같은 파일이다」를 뜻하지는 않으므로 해시 대조는 따로 합니다.
- `MISSING`: 먼저 업로드해야 합니다. 여러 애플리케이션의 파일이 해시까지 같다면 한 벌만 올리면 됩니다.
- `DIFF`: CDN 판으로 바꾸면 글꼴 버전이 바뀝니다. 화면을 대조해 보고 결정합니다.

### 옮기면 안 되는 것

모든 폰트 파일이 브라우저용은 아닙니다. 다음은 그대로 둡니다.

| 대상 | 이유 |
|---|---|
| 모바일 앱 번들, 브라우저 확장 패키지 안의 폰트 | 패키지 안에 있어야 오프라인에서도 동작합니다 |
| pdf.js의 `standard_fonts` 같은 라이브러리 내장 폰트 | 라이브러리가 상대경로로 직접 읽습니다 |
| 서버 코드가 읽는 폰트(PDF 생성, 이미지 렌더링 등) | 브라우저가 아니라 Java 코드가 파일시스템에서 엽니다 |
| 재배포가 허용되지 않는 상용 폰트 | 공개 CDN에 올리면 라이선스 위반이 될 수 있습니다 |
| 코드 참조는 없지만 DB에 저장된 HTML이 부를 수 있는 폰트 | 게시물·이벤트 페이지 본문을 DB에 HTML로 저장하는 서비스라면, 코드 검색으로는 사용처가 보이지 않습니다. 지우기 전에 담당자에게 확인합니다 |

서버 쪽 폰트는 `getRealPath("fonts/...")` 같은 호출로 드러납니다. 호출이 주석 처리돼 있는지까지 확인하면 오판을 줄일 수 있습니다.

## 애플리케이션별 전환 절차

애플리케이션 하나마다 아래 순서를 따릅니다. 여러 애플리케이션을 한 번에 바꾸기보다 하나씩 브랜치를 나누는 편이 되돌리기 쉽습니다.

1. **사용 여부 확인**: CSS의 `url()`이 로컬 폰트를 가리키는지 확인합니다. 상대경로는 CSS 위치 기준으로 풉니다.
2. **해시 대조**: 위 스크립트로 `SAME`/`MISSING`/`DIFF`를 가릅니다.
3. **업로드 요청**: `MISSING`·`DIFF` 중 올리기로 한 파일은 원본 경로와 함께 스토리지 권한이 있는 사람에게 넘기고, 올라온 뒤 2번을 다시 돌립니다.
4. **경로 치환**: `url(../fonts/…)`를 CDN 절대경로로 바꿉니다. `?v=4.7.0` 같은 쿼리 문자열과 `#iefix`, `#fontname` 같은 프래그먼트는 그대로 둡니다.
5. **로컬 검수**: 해당 폰트를 쓰는 요소가 있는 화면을 띄우고, 폰트 요청이 CDN에서 200인지, 지운 옛 로컬 경로를 부르는 요청이 남아 있지 않은지 확인합니다.
6. **로컬 파일 삭제와 커밋**: 경로 치환과 파일 삭제를 한 커밋에 담습니다. 문제가 생기면 커밋 하나만 되돌리면 됩니다.

경로 치환은 이런 식으로 할 수 있습니다(macOS의 BSD `sed` 기준입니다).

```bash
sed -i '' 's#url(\.\./fonts/#url(https://static.example.com/static/fonts/#g' \
  src/main/webapp/css/fonts.css
```

5번 검수는 브라우저 개발자 도구 콘솔에서 확인할 수 있습니다. 아이콘 폰트처럼 화면에 해당 글자가 없으면 브라우저가 폰트를 아예 받지 않으므로, 먼저 그 폰트를 쓰는 요소를 화면에 넣어 둡니다.

```javascript
// 선언된 각 폰트의 상태를 출력합니다. 'loaded'가 아니면 경로나 CORS를 의심합니다
await document.fonts.ready;
[...document.fonts].forEach(f => console.log(f.family, f.weight, f.status));

// 폰트 요청이 어디서 왔는지도 함께 봅니다
performance.getEntriesByType('resource')
  .filter(e => /\.(woff2?|ttf|eot|otf)/.test(e.name))
  .forEach(e => console.log(e.name, e.responseStatus));
```

`responseStatus`는 비교적 최근 브라우저에만 있는 속성이라, 오래된 브라우저에서는 Network 탭으로 확인합니다. 로그인 화면처럼 계정 없이 접근할 수 있으면서 공통 CSS를 모두 불러오는 화면이 있으면 검수가 훨씬 쉽습니다.

## 폰트 응답 헤더: CORS, Content-Type, Cache-Control

### CORS

`@font-face`로 불러오는 폰트는 브라우저가 CORS 모드로 요청합니다. 이미지나 스크립트와 달리, 다른 출처에서 받는 폰트는 응답에 `Access-Control-Allow-Origin`이 없으면 적용되지 않습니다. 관리자 애플리케이션처럼 CDN과 다른 도메인에서 쓰는 경우가 여기에 해당합니다. 전환 전에 헤더부터 확인합니다.

```bash
curl -sI -H 'Origin: https://admin.example.com' \
  https://static.example.com/static/fonts/body-regular.woff2 \
  | grep -i '^access-control'
```

폰트처럼 공개 자산이라면 `*`로 열어 두는 것이 일반적입니다. 특정 도메인만 허용한다면 CDN이 `Origin` 헤더를 캐시 키에 포함하도록 설정해야 합니다. 그렇지 않으면 한 도메인의 응답이 캐시돼 다른 도메인에 잘못 전달될 수 있습니다.

### Content-Type

S3에 올릴 때 `Content-Type`을 지정하지 않으면 엉뚱한 값이 붙을 수 있습니다. 실제로 폰트가 `application/x-www-form-urlencoded`로 내려오는 경우를 봤는데, 확인한 브라우저들은 그래도 폰트를 적용했습니다. 이것은 명세가 보장하는 동작이 아니라 직접 관찰한 결과입니다. 올바른 값은 `font/woff2`, `font/woff`, `font/ttf`처럼 `font/` 계열입니다.

### Cache-Control

CDN 앞에 둔 객체에 `Cache-Control`이 없으면 두 곳에서 캐시 수명이 정해지지 않은 채 동작합니다.

- **CDN 엣지**: 배포 설정의 기본 TTL을 따릅니다.
- **브라우저**: 명시적인 수명이 없으므로 `Last-Modified`를 기준으로 휴리스틱하게 캐시합니다.

오리진이 `Cache-Control`을 주면 CloudFront는 기본 캐시 정책에서 그 값을 따릅니다. 따라서 업로드할 때 메타데이터를 함께 지정하는 것이 가장 간단합니다.

```bash
aws s3api put-object \
  --bucket example-bucket \
  --key static/fonts/body-regular.woff2 \
  --body ./body-regular.woff2 \
  --content-type font/woff2 \
  --cache-control "public, max-age=31536000, immutable"
```

`immutable`은 「이 URL의 내용은 바뀌지 않는다」는 약속입니다. 같은 이름으로 내용을 덮어쓸 가능성이 있는 파일이라면 `max-age`를 짧게 잡거나, 파일명이나 쿼리 문자열에 버전을 넣어 URL을 바꾸는 방식으로 갑니다.

### 캐시를 관측할 때는 엣지를 고정합니다

같은 객체를 연달아 요청했는데 `x-cache: Miss from cloudfront`가 반복되면 「캐시가 안 된다」고 오독하기 쉽습니다. 실제로는 요청마다 다른 엣지로 갔을 수 있습니다(`x-amz-cf-id`가 매번 다릅니다). IP를 고정하고 봐야 `age`가 늘어나다가 TTL이 끝날 때 `RefreshHit`으로 바뀌며 초기화되는 흐름이 보입니다.

```bash
IP=$(dig +short static.example.com | grep -E '^[0-9.]+$' | head -1)
for i in 1 2 3; do
  curl -sI --resolve "static.example.com:443:$IP" \
    https://static.example.com/static/fonts/body-regular.woff2 \
    | grep -iE '^(x-cache|age|etag|cache-control)'
  sleep 30
done
```

### 없는 파일이 403으로 오는 이유

S3 오리진에서 없는 객체를 요청하면 404가 아니라 403이 올 수 있습니다. 요청자에게 버킷 목록 조회 권한(`s3:ListBucket`)이 없으면, S3는 객체가 없다는 사실 자체를 숨기고 접근 거부로 응답하기 때문입니다. 전환 검수에서 403을 보고 권한 문제부터 의심하기 전에 경로와 파일명을 먼저 확인합니다.

## 정적 파일을 안전하게 교체하기

정적 파일 교체는 「어느 계층에 있는가」에 따라 절차가 완전히 달라집니다.

### 오브젝트 스토리지에 있는 파일

매뉴얼 PDF처럼 화면이 고정된 파일명으로 링크하는 파일을 바꾸는 경우입니다.

```bash
BUCKET=example-bucket
KEY=board/manual.pdf
# 1) 백업: 같은 버킷 안에 날짜를 붙인 사본을 만듭니다
aws s3api copy-object --bucket "$BUCKET" \
  --copy-source "$BUCKET/$KEY" --key "$KEY.bak-$(date +%Y%m%d)"
# 2) 교체: 파일명은 코드에 박혀 있으므로 이름은 그대로 두고 내용만 바꿉니다
aws s3api put-object --bucket "$BUCKET" --key "$KEY" \
  --body ./manual-new.pdf --content-type application/pdf
# 3) 확인: content-length와 last-modified가 바뀌었는지 봅니다
curl -sI "https://www.example.com/files/manual.pdf" | grep -iE '^(content-length|last-modified|etag)'
```

주의할 점이 셋 있습니다.

- **마운트 경로에 직접 쓰지 않습니다.** `mountpoint-s3`는 기본 설정에서 기존 객체 덮어쓰기를 허용하지 않습니다. 마운트가 `rw`로 보여도 쓰기가 실패하거나 어중간한 상태로 남을 수 있습니다. 교체는 AWS CLI나 SDK로 객체를 직접 올려서 합니다.
- **한 번만 실행합니다.** 여러 대의 서버가 같은 버킷을 마운트하고 있다면 교체는 한 곳에서 한 번이면 됩니다. 여러 서버에 같은 명령을 동시에 보내는 도구를 켠 채로 실행하지 않습니다.
- **앞에 CDN이 있는지 확인합니다.** CDN이 없는 경로라면 교체 즉시 새 파일이 나옵니다. CDN이 있다면 TTL이 끝날 때까지 이전 파일이 남으므로, 무효화를 하거나 `Cache-Control`로 수명을 짧게 잡아 둡니다.

### WAR 안에 있는 파일

`/css/`, `/js/`처럼 WAR 안에 있는 파일은 원칙적으로 배포로 바꿉니다. 급해서 서버의 파일만 직접 바꾸는 경우에는 이런 것들을 놓치기 쉽습니다.

- **minify 접미사**: JSP가 `common${minify}.js`처럼 환경별 접미사를 붙여 파일명을 조립한다면, 운영에서 실제로 서빙되는 것은 `common.min.js`입니다. 원본만 바꾸면 아무 변화가 없습니다. 접미사 없이 직접 부르는 참조가 섞여 있을 수도 있으니 대상 파일이 어떤 이름으로 불리는지 매번 확인합니다.
- **캐시 버스팅 값**: 정적 링크에 `?ver=...`를 붙이는 구조라면, 그 값이 어디서 오는지 봅니다. 서버의 버전 파일에서 읽는다면 그 파일을 갱신해야 URL이 바뀌고 브라우저가 새 파일을 받습니다.
- **다음 배포에 덮이지 않게**: 서버 파일만 바꾸면 브랜치에는 흔적이 없습니다. 같은 내용을 커밋해 두지 않으면 다음 배포가 이전 파일로 되돌립니다.

## 함정 모음

### 새 정적 경로가 404를 냅니다

`webapp/` 아래에 `/media/` 같은 새 최상위 폴더를 만들고 파일을 넣었는데 404가 나는 경우입니다. `DispatcherServlet`이 루트(`/`)에 매핑돼 있고 정적 리소스는 `/css/**`, `/js/**`, `/images/**` 같은 특정 경로만 따로 매핑돼 있으면, 새 경로는 컨트롤러 요청으로 처리됩니다. 대응하는 핸들러가 없으니 404입니다.

새 자산은 이미 정적 매핑된 경로의 하위 폴더에 두거나, 매핑에 경로를 추가합니다. 영상처럼 큰 바이너리라면 애초에 WAR보다 CDN에 두는 편이 낫습니다.

### 로컬에서 고쳤는데 반영되지 않습니다

로컬 서버에서 `?ver` 값을 서버 기동 시각으로 만드는 구조라면, 그 값은 서버가 떠 있는 동안 고정입니다. CSS·JS 파일만 바꾸면 URL이 그대로라 브라우저가 캐시된 이전 파일을 씁니다. 개발자 도구의 「Disable cache」를 켜 두거나 서버를 다시 띄웁니다. IDE에 내장된 간이 브라우저는 강력 새로고침이 잘 먹지 않는 경우가 있어, 확실히 하려면 일반 브라우저에서 엽니다.

### 빌드 산출물처럼 보이는 소스가 있습니다

스타일 원본(SCSS)을 고치고 컴파일과 배포까지 마쳤는데 화면이 그대로이고, 캐시를 지우고 서버를 다시 띄워도 그대로인 경우입니다. 원인은 화면이 다른 파일을 보고 있기 때문입니다.

예를 들어 빌드는 `scss/`를 `webapp/css/`로 한 방향으로만 컴파일하는데, 특정 화면은 `viewer/web/css/viewer.css`를 직접 불러옵니다. 이 폴더에는 대응하는 `.scss`가 없고 컴파일 대상도 아니며 git으로 추적됩니다. 이름과 위치가 산출물처럼 보여도 **사실은 손으로 관리하는 소스**입니다. 그래서 원본만 고치면 화면은 그대로이고, 화면이 부르는 파일만 고치면 원본이 낡습니다.

스타일이나 스크립트를 고치기 전에 순서대로 확인합니다.

1. 화면이 실제로 어느 경로를 불러오는지 마크업(`<link>`, `<script>`)에서 역추적합니다.
2. 그 파일에 대응하는 원본이 있는지 봅니다. 없다면 그 파일이 곧 소스입니다.
3. 빌드 설정에서 그 경로가 컴파일 대상에 들어 있는지 확인합니다.

「고쳤는데 반영이 안 된다」의 원인은 대개 캐시입니다. 그러나 캐시를 지워도 그대로라면 다른 파일을 보고 있다고 의심합니다.

### 존재하지 않는 경로를 가리키는 선언

전환하면서 모든 CSS의 `url()`을 훑다 보면, 오래전부터 404였던 선언이 나오기도 합니다. 다른 CSS가 같은 글꼴을 올바른 경로로 다시 선언하고 있으면 화면에는 티가 나지 않습니다. 하지만 두 CSS가 항상 함께 로드된다는 보장이 없다면 어떤 화면에서는 글꼴이 빠질 수 있습니다. 이런 선언은 전환 범위에 섞지 말고 따로 기록해 두었다가 원본 담당자와 함께 정리합니다.

## 기대할 것과 기대하면 안 되는 것

| 얻는 것 | 기대하면 안 되는 것 |
|---|---|
| 배포 산출물이 가벼워집니다 | git clone 크기는 줄지 않습니다. 이력에 예전 파일이 남아 있습니다 |
| 폰트 요청이 WAS 대신 CDN 엣지에서 처리됩니다 | 도메인 간 브라우저 캐시 공유는 기대하기 어렵습니다. 최근 브라우저는 최상위 사이트별로 HTTP 캐시를 나눕니다 |
| 원본이 한 벌로 모여, 글꼴 교체가 한 곳에서 끝납니다 | CDN이라는 의존이 하나 늘어납니다. CDN이 응답하지 않으면 글꼴이 시스템 기본 글꼴로 바뀝니다 |
| 일부만 커밋돼 있던 포맷·굵기가 CDN에서 모두 응답합니다 | `Cache-Control`을 지정하지 않으면 브라우저 캐시 수명은 휴리스틱에 맡겨집니다 |

CDN 의존이 신경 쓰인다면 `font-display: swap`과 적절한 대체 글꼴 스택을 두는 것으로 영향을 줄일 수 있습니다. 글꼴이 늦거나 실패해도 본문은 먼저 보입니다.

## 정리

- 정적 파일을 옮기거나 바꾸기 전에 **그 URL을 누가 응답하는지**부터 가립니다. 소스의 매핑 선언은 증거가 아니고, 응답 헤더(`server`, ETag 형식, `x-cache`, 있어야 할 `Cache-Control`의 유무)가 증거입니다.
- 서버에서 파일의 실체를 찾을 때는 `find -xdev`가 아니라 `mount`부터 봅니다. 마운트된 오브젝트 스토리지는 `-xdev`에 걸려 빠집니다.
- 옮길 폰트는 `url()` 참조로 고르고, 상대경로는 CSS 위치 기준으로 풀고, 같은지는 이름이 아니라 sha256으로 판정합니다. 앱·확장·라이브러리 내장·서버 측·라이선스 제한 폰트와 DB에 저장된 HTML이 부를 수 있는 폰트는 남겨 둡니다.
- 전환은 애플리케이션별로 경로 치환과 로컬 파일 삭제를 한 커밋에 담고, `document.fonts`와 네트워크 요청으로 검수합니다.
- 다른 도메인에서 쓰는 폰트는 CORS 헤더가 필요합니다. 업로드할 때 `Content-Type`과 `Cache-Control`을 함께 지정하고, 캐시 동작은 엣지를 고정해 관측합니다.
- 오브젝트 스토리지의 파일은 마운트가 아니라 AWS CLI로 백업한 뒤 덮어쓰고, WAR 안의 파일은 minify 접미사와 캐시 버스팅 값, 다음 배포와의 정합까지 확인합니다.

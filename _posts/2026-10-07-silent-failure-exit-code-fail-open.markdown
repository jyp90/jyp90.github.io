## 문제와 배경

매일 새벽에 도는 적재 배치가 며칠 동안 아무것도 넣지 못했습니다. 그동안 cron은 매일 정상적으로 배치를 실행했고, 프로세스는 매번 종료 코드 `0`으로 끝났습니다. 모니터링은 종료 코드만 보고 있었으니 경보가 울릴 이유가 없었습니다.

다른 영역에서도 같은 모양의 문제가 있었습니다. 특정 조건의 요청을 막아야 하는 서버 쪽 게이트가, 판정에 필요한 외부 호출이 실패하면 요청을 **그냥 통과시키고** 있었습니다. 정상일 때는 잘 막았고, 장애가 났을 때만 문이 열렸습니다.

두 사례는 영역이 전혀 다르지만 구조는 같습니다.

- 배치: 실패했는데 **성공 신호**를 냈습니다.
- 게이트: 실패했는데 **허용 판정**을 냈습니다.

둘 다 "실패가 조용한 시스템"입니다. 실패 경로가 성공 경로와 같은 출구로 빠져나가니, 출구만 지켜보는 쪽에서는 구별할 방법이 없습니다. 이 글은 이런 시스템을 어떻게 판정하고 점검하는지, 그리고 그 판정법이 어디서 다시 함정을 만드는지를 정리합니다.

## 왜 실패가 성공처럼 보이는가

### 배치: 예외를 삼키는 진입점

JVM 배치에서 흔한 모양은 이렇습니다.

```java
public static void main(String[] args) {
    try {
        new ImportJob().run();
    } catch (Exception e) {
        log.error("작업 실행 실패", e);
        // 다시 던지지도, System.exit(1)을 부르지도 않습니다
    }
}
```

예외를 로그에만 남기고 `main`이 정상 반환하니 JVM은 `0`으로 종료합니다. 셸이나 스케줄러가 볼 수 있는 유일한 신호가 거짓말을 하는 셈입니다. 가장 좋은 처방은 물론 진입점을 고쳐 실패 시 비0으로 끝내는 것입니다. 하지만 같은 진입점을 수십 개의 작업이 공유하고 있고 각 작업의 운영 스크립트가 그 동작에 기대고 있다면, 한 번에 바꾸기 어렵습니다. 그럴 때는 바깥에서 결과를 판정해야 합니다.

### 게이트: 성공 응답에서만 차단을 세우는 구조

게이트 쪽에서 반복되는 모양은 이렇습니다.

```java
boolean blocked = false;               // 초기값이 '허용'
try {
    String body = httpClient.get(policyUrl);
    if (body != null && !body.isEmpty()) {
        blocked = parse(body).isBlocked();
    }
} catch (Exception e) {
    log.warn("정책 조회 실패", e);      // 차단 플래그는 그대로 false
}
return blocked;
```

문제는 두 군데입니다.

1. 일부 HTTP 유틸은 오류가 나면 예외 대신 **빈 문자열**을 돌려줍니다. 그러면 `if` 조건이 거짓이 되어 블록 전체를 건너뛰고, `catch`는 한 번도 실행되지 않습니다. "예외 처리를 해 두었으니 안전하다"는 생각이 통하지 않습니다.
2. 예외가 나서 `catch`로 들어가도, 차단 플래그를 세우지 않으니 결국 초기값인 '허용'이 반환됩니다.

즉 **성공 응답을 받았을 때만 차단이 성립**하는 구조입니다. 이런 게이트는 판정이 불가능한 모든 상황에서 열립니다.

## 접근: 출구 하나가 아니라 신호 여러 개를 본다

두 문제의 처방은 같은 원칙에서 나옵니다.

> 성공을 **확인하지 못했다면** 실패로 취급합니다(fail-closed).

배치라면 "에러가 안 보였으니 성공"이 아니라 "성공했다는 증거가 있으니 성공"이어야 합니다. 게이트라면 "차단 응답을 받았으니 차단"이 아니라 "차단 아님이 확인됐으니 허용"이어야 합니다. 판정의 기본값을 실패 쪽에 두는 것입니다.

## 구현 1: 셸에서 배치 결과를 판정하기

종료 코드를 믿을 수 없다면 셸은 로그를 읽어야 합니다. 이때 보는 신호는 대략 네 가지입니다.

- 종료 코드 자체 (`0`이 아닌 경우는 여전히 의미가 있습니다)
- 실행 실패를 알리는 로그 줄
- 작업이 끝까지 갔다는 완료 로그 줄
- 처리 건수 요약 줄

중요한 것은 **보는 순서**입니다. 위에서부터 처음 걸리는 조건이 판정이 됩니다.

### 핵심 코드

```bash
#!/usr/bin/env bash
set -u
export LANG="${LANG:-C.UTF-8}"   # 비어 있을 때만 채웁니다 (아래 함정 참고)

LOG="run-$(date +%Y%m%d).log"
timeout 2h flock -n -E 75 /var/lock/import.lock \
  java -jar job.jar import >"$LOG" 2>&1
rc=$?

verdict() {
  # 1) 프로세스가 정상 종료하지 못한 경우는 로그를 볼 필요가 없습니다
  case $rc in
    0)   ;;
    75)  echo "SKIP: 이전 실행이 아직 진행 중"; return ;;
    124) echo "FAIL: 시간 상한 초과";          return ;;
    137) echo "FAIL: 강제 종료(SIGKILL)";      return ;;
    *)   echo "FAIL: 종료 코드 $rc";           return ;;
  esac

  # 2) 실행 실패 줄을 요약보다 먼저 봅니다
  grep -qF '작업 실행 실패' "$LOG" && { echo "FAIL: 실행 중 예외"; return; }

  # 3) 빈 입력은 완료 줄 없이 끝나는 작업일 수 있습니다
  if ! grep -qF '작업 완료' "$LOG"; then
    grep -qF '처리할 입력 없음' "$LOG" && { echo "WARN: 입력 0건"; return; }
    echo "FAIL: 완료 기록 없음"; return            # 4)
  fi

  # 5) 요약 숫자를 못 읽으면 실패입니다
  read -r total ok skip err < <(
    sed -nE 's/.*대상=([0-9]+) 처리=([0-9]+) 스킵=([0-9]+) 에러=([0-9]+).*/\1 \2 \3 \4/p' "$LOG" | tail -1)
  [ -n "${err:-}" ] || { echo "FAIL: 요약 줄 해석 불가"; return; }

  # 6) 숫자 해석
  if   [ "$err" -gt 0 ];                       then echo "FAIL: 에러 $err건"
  elif [ "$total" -eq 0 ];                     then echo "WARN: 대상 0건"
  elif [ "$ok" -eq 0 ] && [ "$skip" -eq "$total" ]; then echo "OK: 전량 스킵(이미 처리됨)"
  elif [ "$ok" -eq 0 ];                      then echo "FAIL: 처리 0건"
  else echo "OK: 처리 $ok/$total"
  fi
}

result=$(verdict)
notify "$result" || echo "알림 전송 실패: $result" >&2   # 알림 실패가 판정을 바꾸지는 않습니다
```

순서마다 이유가 있습니다.

- **실행 실패 줄을 요약보다 먼저 봅니다.** 실행 도중 예외가 나도 요약 줄은 대개 "처리 0"으로 찍힙니다. 요약을 먼저 보면 저장소나 DB 장애가 "입력이 비었네" 수준의 경고로 격하됩니다.
- **완료 줄의 부재를 따로 다룹니다.** 입력이 비면 요약을 찍기 전에 일찍 반환하는 작업이 많습니다. 이런 작업은 완료 줄 자체가 없으니, "완료 줄 없음 = 실패"로만 판정하면 빈 입력이 매번 실패로 보입니다.
- **알림은 판정과 분리합니다.** 알림은 fail-open으로 둡니다. 배치는 이미 끝났고, 알림이 실패했다고 결과가 바뀌지는 않습니다. 대신 알림 실패 사실은 로그에 남깁니다.

### "처리 0"은 한 가지 뜻이 아닙니다

이 판정에서 가장 놓치기 쉬운 부분입니다. 처리 건수가 0이 되는 경로는 적어도 세 가지입니다.

| 상황 | 의미 | 판정 |
|---|---|---|
| 입력이 비어 있음 | 할 일이 없었음 | 경고 |
| 실행 중 예외 | 하려다 실패함 | 실패 |
| 모든 건을 스킵 | 이미 처리돼 있어서 건너뜀 | 정상 |

숫자가 같다고 같은 상황으로 묶으면, 빈 입력이 실패로 울리거나 실제 장애가 경고로 묻힙니다. 숫자 하나가 아니라 "그 숫자를 만든 경로"를 다른 신호로 구별해야 합니다.

## 구현 2: 게이트의 실패 경로를 전수 열거하기

게이트 쪽은 코드를 읽는 점검입니다. 판정이 외부 호출이나 세션 조회에 기대고 있다면, 실패할 수 있는 경로를 모두 적고 **각각이 차단으로 수렴하는지** 하나씩 확인합니다.

- 비200 응답
- 타임아웃
- 예외
- 빈 응답
- 파싱 실패
- 응답에 판정 필드가 없음
- 선행 조회(권한, 기간, 자격) 실패

앞의 코드를 고치면 이런 모양이 됩니다.

```java
Decision decide(Request req) {
    PolicyResponse res;
    try {
        res = policyClient.fetch(req);          // 비200·빈 응답이면 예외를 던지도록 감쌉니다
    } catch (Exception e) {
        log.warn("정책 조회 실패, 차단으로 처리", e);
        return Decision.BLOCK;
    }
    Boolean allowed = res.getAllowed();         // 필드 부재는 null
    return Boolean.TRUE.equals(allowed) ? Decision.ALLOW : Decision.BLOCK;
}
```

핵심은 질문을 바꾸는 것입니다. "응답이 비어 있지 않은가"가 아니라 "**허용이 명시적으로 확인됐는가**"를 묻습니다. 필드가 없을 때 `false`(검사 생략)가 아니라 차단으로 읽히도록, 판정 신호의 부재는 항상 거짓 쪽이어야 합니다.

코드 한 곳만 보고 끝내면 안 되는 지점도 있습니다.

- **모듈마다 따로 확인합니다.** 같은 외부 API를 쓰더라도 모듈마다 HTTP 클라이언트가 다를 수 있습니다. 한쪽은 실패 시 예외를 던져 `catch`가 차단을 세우고, 다른 쪽은 빈 문자열을 돌려줘 통과시키는 일이 실제로 일어납니다. 같은 계약인데 결과가 반대입니다.
- **필터와 인터셉터의 매핑 범위를 봅니다.** 정확한 경로에만 걸려 있으면 하위 경로가 새로 생기는 순간 그 경로는 게이트 밖에 놓입니다.
- **코드 값의 흐름을 따라갑니다.** "판정 불가"를 뜻하는 상태 코드가 하류에서 "조건부 허용"으로 해석되지 않는지 봅니다. 판정 불가와 부분 허용은 다른 결과여야 합니다.
- **자기주장 신호를 신뢰하지 않습니다.** User-Agent처럼 호출자가 마음대로 적을 수 있는 값은 분류 힌트일 뿐입니다. 검색봇 예외가 필요하다면 공개 색인 경로에만 두고, 결제나 권한 경로와 같은 예외 목록을 공유하지 않습니다.

경험상 출시 직전에 발견되는 차단 수준의 결함은 생각보다 자주 이 한 가지 유형으로 모입니다. 겉모습은 매번 다른데, 뜯어보면 "실패가 차단이 아니라 통과로 흘렀다"는 같은 구조입니다. 그래서 게이트를 리뷰할 때는 이 목록을 렌즈처럼 들고 먼저 훑어보는 편이 효율적입니다.

### 반대 방향도 있습니다

모든 의존을 fail-closed로 만들라는 뜻은 아닙니다. 로그인처럼 실패가 곧 사용자 차단인 경로에 새로운 부가 조회를 붙일 때는 반대로 생각해야 합니다. 부가 조회가 실패하면 **그 기능만** 닫고 경로 자체는 통과시킵니다. 권한 조회가 실패하면 "권한 없음"으로 떨어지되 로그인은 성공해야 합니다.

정리하면 기준은 하나입니다. **실패했을 때 무엇이 닫혀야 하는가**를 경로마다 명시적으로 정하고, 코드가 그 방향으로 수렴하는지 확인합니다. 이 방어를 리뷰어가 "불필요한 예외 처리"로 보고 지우려 할 수 있으니, 의도를 설계 문서나 주석에 미리 적어 두는 것도 좋습니다.

## 함정과 트레이드오프: 판정법이 만드는 새 함정

종료 코드 대신 로그를 읽기로 한 순간, 판정은 새로운 것들에 의존하게 됩니다.

### 로그 문구가 계약이 됩니다

셸의 `grep -F '작업 완료'`는 애플리케이션 로그 문구와 바이트 단위로 일치해야 동작합니다. 누군가 로그 메시지를 "작업이 완료되었습니다"로 다듬는 순간, 셸 판정은 전부 "완료 기록 없음 → 실패"로 기웁니다. 로그 문구가 사실상 외부 인터페이스가 된 것입니다.

완전히 피하기는 어렵지만 깨지는 지점을 드러낼 수는 있습니다.

- 셸 머리 주석에 의존하는 로그 줄을 그대로 적어 둡니다.
- 애플리케이션 쪽 해당 로그 호출 옆에도 "판정 스크립트가 이 문구를 읽음"이라고 남깁니다.
- 여력이 되면 사람용 문구와 별도로 `RESULT status=ok processed=12` 같은 기계용 요약 줄을 하나 찍습니다. 문구가 다듬어져도 판정이 흔들리지 않습니다.

### 로케일도 계약에 들어갑니다

`grep -F`는 로케일과 무관하게 바이트만 비교합니다. 그런데 비교 대상인 로그를 찍는 JVM은 로케일을 따릅니다. JVM이 UTF-8이 아닌 문자셋으로 뜨면 한글 로그가 `?`로 찍히고, 판정은 다시 실패 쪽으로 무너집니다.

cron은 로그인 셸의 환경 변수를 물려받지 않습니다. 서버마다 시스템 기본 로케일이 달라서, 어떤 서버에서는 멀쩡하고 어떤 서버에서는 깨지는 일이 생깁니다. 직접 확인하고 싶다면 환경을 비운 채 실행해 보면 됩니다.

```bash
env -i /bin/bash -c 'java -jar job.jar import' | head
```

그래서 위 스크립트 첫머리에 `export LANG="${LANG:-C.UTF-8}"` 한 줄을 두었습니다. 값이 이미 있으면 존중하고, 비어 있을 때만 채웁니다. 반대로 "안전하게" 하겠다고 `LC_ALL=C`를 강제하면 JVM 문자셋이 ASCII로 바뀌어 바로 이 문제를 일으킵니다.

한 가지 더 있습니다. JVM에서 로그 파일에 쓰는 인코딩(`file.encoding`)과 명령줄 인자를 해석하는 인코딩(`sun.jnu.encoding`)은 별개의 설정입니다. 보통 함께 움직이지만, 판정 결과를 명령줄 인자로 넘겨 알림을 보낸다면 cron이 보낸 첫 알림의 한글이 제대로 보이는지 따로 확인하는 편이 안전합니다.

이런 깨짐은 실패 쪽으로 무너지므로 장애를 놓치지는 않습니다. 하지만 거짓 경보가 날마다 쌓이면 사람들은 곧 그 알림을 무시하게 되고, 결국 진짜 실패도 함께 묻힙니다. fail-closed가 안전한 것은 거짓 경보가 드물 때뿐입니다.

### 알림이 오지 않은 것을 어떻게 읽을 것인가

판정 스크립트를 붙이고 나면 "오늘은 알림이 안 왔으니 괜찮다"는 생각이 생깁니다. 알림이 없다는 사실은 여러 가지를 뜻할 수 있습니다.

- 판정이 정상이라 알림을 보내지 않도록 설정돼 있다
- 알림을 보내려 했지만 실패했다
- 알림 코드까지 가지도 못했다

세 번째를 가려내려면 알림 모듈이 **성공과 실패를 모두 로그에 남기도록** 만들어 두어야 합니다. 그러면 "전송 성공" 줄도 "전송 실패" 줄도 어디에도 없을 때, 전송을 시도조차 하지 않았다고 판단할 수 있습니다. 실제로 이런 상황은 서버에 개편 전 옛 스크립트가 그대로 남아 돌고 있었거나, 배포된 jar에 알림 클래스가 빠져 알림 프로세스가 바로 죽은 경우에 생깁니다.

알림을 배치와 같은 jar로 보내는 구조라면 jar 자체가 없을 때는 알릴 방법이 없습니다. 이 경우를 위해 셸은 jar 존재부터 확인하고, 없으면 별도의 종료 코드로 끝내 스케줄러 쪽에서라도 보이게 합니다.

정리하면, **알림의 부재는 신호가 아닙니다.** 부재를 해석하려면 "보냈다", "보내다 실패했다"는 흔적이 양쪽 모두 남아 있어야 합니다.

### 테스트도 같은 함정에 빠집니다

fail-closed 판정은 보통 "A 실패 또는 B 실패 또는 C 실패면 차단" 같은 OR 조건입니다. 이를 단위 테스트할 때 검증 대상이 아닌 인자에 그럴듯한 정상값을 남겨 두면, 어느 인자가 판정을 만들었는지 분리되지 않습니다. 거짓 통과와 거짓 실패가 함께 납니다. 테스트마다 **검증하려는 인자 하나만** 유효하게 두고 나머지는 판정에 영향을 주지 않는 값으로 채웁니다.

## 다른 배치와 게이트에 옮길 때

판정 스크립트를 다른 작업에 옮길 때 작업마다 다시 확인해야 하는 것은 세 가지입니다.

- 입력이 비었을 때 완료 줄과 요약 줄이 찍히는지, 찍히지 않는지
- 실행 중 예외가 어떤 문구를 남기고, 그때 요약 줄이 어떻게 찍히는지
- 실행이 겹치면 안 되는 작업인지(`flock`), 넘기면 안 되는 마감 시각이 있는지(`timeout`)

게이트 쪽은 앞의 실패 경로 목록을 모듈별로 다시 적용합니다. 같은 API를 쓰는 다른 모듈에서 이미 안전하게 처리했다고 해서, 이 모듈도 그렇다는 보장은 없습니다.

## 정리

- 실패가 성공과 같은 출구로 나가는 시스템은 출구만 봐서는 판정할 수 없습니다. 배치의 종료 코드 0과 게이트의 기본 허용은 같은 문제입니다.
- 성공을 확인하지 못했으면 실패로 둡니다. 배치는 여러 신호를 정해진 순서로 보고, 게이트는 "허용이 확인됐는가"를 묻습니다.
- 숫자 하나(처리 0건, 빈 응답)를 한 가지 뜻으로 읽지 않습니다. 같은 값을 만드는 경로가 여러 개입니다.
- 로그를 읽는 순간 로그 문구와 로케일이 계약이 됩니다. 의존 관계를 드러내 두고, 가능하면 기계용 요약 줄을 따로 둡니다.
- 알림이 없다는 것은 아무것도 증명하지 않습니다. 성공과 실패 흔적을 모두 남겨야 부재를 읽을 수 있습니다.

1편의 3D 배치 화면은 가구가 들어가는지 보기에는 충분했지만, 벽을 새로 그리거나 문 위치를 cm 단위로 맞추기에는 불편했습니다. 탑뷰는 위에서 본 3D일 뿐 편집 도구가 아니었습니다. 2편은 그 뒤에 붙인 2D 평면 편집기(구현 계획 2)와 배치안 비교·내보내기·복구 이력(구현 계획 3)을 다룹니다.

## 외부 조사 문서를 스펙의 새 절로 흡수하기

계획 2에 들어가기 전에 Planner 5D 같은 기존 서비스를 조사한 설계 문서를 따로 받아 두었습니다. 이 문서를 기존 스펙에 섞어 고치지 않고, 스펙 끝에 「§14 2차 반영」이라는 새 절로 붙이게 했습니다. 절 첫머리에 「이 절이 1–13절과 충돌하면 이 절이 우선한다」고 적고, 반영하는 것, 유지하는 결정, 범위 밖을 표로 나눴습니다.

| 구분 | 예 |
|---|---|
| 반영 | 배치안 A/B, 2D에서 배치, 방 만들기 도구, 축척 검증, 실측/추정 표시, 복구 이력, 이미지 내보내기 |
| 유지(출처와 다름) | 저장 단위는 mm가 아니라 정수 cm, 방 경계는 벽 중심선 모델, 업체용 PDF는 범위 안 |
| 범위 밖 | 계정·클라우드 저장, 공유 링크, 자동 도면 인식, 실시간 공동 편집 |

출처 문서는 내부 단위를 mm로 제안했지만, 가구 배치 판단에는 1cm 해상도면 충분하고 계획 1의 기하·저장 코드가 이미 cm로 검증돼 있어서 바꾸지 않았습니다. 「유지하는 결정」을 이유와 함께 적어 두면, 다음 세션의 Claude Code가 출처 문서를 다시 읽고 mm로 바꾸자고 제안하는 일을 막을 수 있습니다.

이 방식이 이후 모든 요청의 기본이 됐습니다. 새 요구가 오면 날짜가 붙은 §N 절을 덧붙이고, 예전 절은 고치지 않습니다. 스펙은 §57까지 늘었고, 어떤 결정이 왜 바뀌었는지는 절 순서대로 읽으면 나옵니다.

## 2D 편집기: 같은 store를 쓰는 SVG 화면

2D 편집기는 SVG로 그립니다. 팬·줌, 벽·문·창·방 렌더링, 선택, 벽 끝점 드래그가 먼저 들어가고, 그다음 구조 도구(벽 그리기, 방 만들기, 문, 창, 방 이름)와 배경 이미지·축척 보정이 붙었습니다.

![계획 2 시점의 구조 탭 2D 편집기에서 문을 선택한 화면](/assets/images/posts/floor-plan-editor-layouts/01-structure-2d.webp)
*계획 2 시점: 구조 탭의 2D 편집기입니다. 왼쪽은 구조 도구와 배경 도면, 오른쪽은 선택한 문의 속성(벽 시작점에서 거리, 폭, 높이, 경첩·열림 방향, 실측 확인)이고, 벽마다 `≈900`처럼 실측 전 치수가 표시됩니다.*

핵심은 2D와 3D가 **같은 store**를 본다는 점입니다. 2D에서 가구를 옮기면 3D에 그대로 반영되고, 검증 결과(충돌, 벽 거리, 문 열림)도 같은 순수 함수에서 나옵니다. 화면마다 따로 상태를 들고 있지 않으니 「2D에서는 괜찮은데 3D에서는 겹친다」 같은 불일치가 생기지 않습니다.

![계획 2 시점의 배치 탭 2D 화면에서 세탁기를 선택한 모습](/assets/images/posts/floor-plan-editor-layouts/02-place-2d.webp)
*같은 시점의 배치 탭 2D 화면입니다. 세탁기를 선택하면 사방 벽까지의 거리가 파란 점선으로 표시되고, 속성 패널에 「방문 열림 간섭」 「문 열림 공간 부족」 배지가 뜹니다. 잠금과 실측 확인 체크박스도 이 계획에서 들어왔습니다.*

배경 이미지 축척 보정은 기준 길이 하나로 끝내지 않았습니다. 다른 방향의 검증 길이를 하나 더 입력할 수 있고, 두 축척 차이가 2%를 넘으면 경고하고 배경 정렬을 「근사」로 표시합니다. 이미지의 가로세로 비율이 실제와 조금이라도 다르면, 한 방향만 맞췄을 때 다른 방향 치수가 표시 없이 어긋날 수 있기 때문입니다. 배경 이미지는 크기를 줄여 IndexedDB에 따로 저장하고, 평면 JSON에는 참조만 둡니다.

## 2D 편집기에서 잘못된 것들

계획 2의 과제가 끝난 뒤 실제로 조작해 보면서 나온 수정이 이어졌습니다.

| 증상 | 원인 | 수정 |
|---|---|---|
| 2D로 전환하면 3D 쪽에서 portal 정리 오류 | 탭 전환마다 3D 뷰포트를 조건부로 마운트·해제 | 3D 뷰포트를 항상 마운트하고 숨김 클래스로만 전환 |
| 벽 끝점을 끌다 보면 벽이 점 하나로 붕괴 | 길이 하한이 없었고, 스냅 대상에 같은 벽의 반대쪽 끝점이 포함됨 | 벽 길이가 두께보다 짧아지는 이동은 거부, 반대쪽 끝점은 스냅 대상에서 제외 |
| 문을 클릭만 했는데 위치가 움직임 | 클릭과 드래그를 구분하지 않았음 | 3px 미만 움직임은 클릭으로 처리, 문 열림 부채꼴은 포인터 이벤트를 받지 않고 화면 이동으로 넘김 |
| 배경 불투명도 슬라이더를 끄는 동안 값마다 undo 단계가 생김 | 값 변경마다 이력이 쌓였음 | 슬라이더 조작 한 번을 undo 한 단계로 묶음 |

「2D와 3D 뷰는 항상 마운트」는 이 수정 이후 `CLAUDE.md`의 아키텍처 규칙으로 올라갔습니다. 조건부 렌더링으로 바꾸고 싶어지는 자리라서, 규칙으로 적어 두지 않으면 다른 세션이 같은 실수를 되풀이할 수 있습니다.

## 배치안 A/B와 첫 스키마 마이그레이션

계획 3은 「같은 구조에서 배치만 다른 안」을 만드는 기능입니다. 벽·문·창·방·전기는 모든 배치안이 공유하고, 가구 목록만 배치안별로 둡니다. 이 때문에 저장 형식이 처음 바뀌었습니다. `plan.items`가 `plan.layouts[n].items`로 옮겨 가면서 스키마가 v1에서 v2가 됐습니다.

마이그레이션은 「버전 n을 n+1로 바꾸는 함수」의 목록으로 둡니다. 아래는 구조만 보이도록 새로 쓴 예시입니다.

```ts
type RawPlan = { version: number; [key: string]: unknown };
type Step = (p: RawPlan) => RawPlan;

const STEPS: Record<number, Step> = {
  1: ({ items, ...rest }) => ({
    ...rest,
    version: 2,
    layouts: [{ id: 'layout-a', name: 'A안', items: Array.isArray(items) ? items : [] }],
    activeLayoutId: 'layout-a',
  }),
};

export function migrate(raw: RawPlan, current: number): RawPlan | null {
  let plan = raw;
  while (plan.version < current) {
    const step = STEPS[plan.version];
    if (!step) return null;              // 모르는 버전은 열지 않음
    const next = step(plan);
    if (next.version <= plan.version) return null; // 버전이 오르지 않는 단계는 무한 루프 방지
    plan = next;
  }
  return plan;
}
```

계획 3에 앞서 `plan.items`에 직접 접근하던 코드를 `activeItems(plan)` / `withActiveItems(plan, fn)` 접근자로 먼저 모았습니다. 접근 지점을 한곳으로 모은 뒤에 저장 형식을 바꾸니 v2 전환 커밋이 작아졌습니다. 「스키마를 바꾸면 버전 증가 + 마이그레이션 단계 + 테스트를 같은 커밋에」라는 규칙은 나중에 프로젝트 스킬(`migrating-plan-schema`)로 분리됐습니다.

![배치안 A를 보면서 B안을 점선으로 겹쳐 본 화면](/assets/images/posts/floor-plan-editor-layouts/03-layout-compare.webp)
*계획 3 시점: 왼쪽 위에 배치안 탭(A안·B안)과 복제·이름·메모가 생겼습니다. 「겹쳐 볼 배치안」으로 B안을 고르면 B안의 가구 위치가 보라색 점선으로 A안 위에 겹쳐 그려집니다.*

「비교 대상과 전환」 버튼을 누르면 카메라 시점은 그대로 두고 두 안을 오갑니다. 가족이 같은 시점에서 두 안을 보고 고를 수 있게 하는 것이 스펙의 성공 기준 중 하나였습니다.

## PNG 내보내기와 복구 이력

![2D PNG로 내보낸 A안 배치도](/assets/images/posts/floor-plan-editor-layouts/04-png-export.webp)
*같은 시점에 「2D PNG」로 내려받은 이미지입니다. 제목에 평면 이름과 배치안이 들어가고, 실측 확인 전 치수 개수(15개)가 범례에 표시됩니다.*

PNG 내보내기에서도 수정이 몇 번 이어졌습니다. 라벨이 가구 도형 아래에 깔려 안 보였고, 사용자가 입력한 이름에 제어 문자가 섞이면 그림이 깨질 수 있었고, 고해상도 화면에서는 3D PNG의 머리글이 작게 찍혔습니다. 라벨을 도형 위에 흰 외곽선과 함께 그리고, 제어 문자를 걸러 내고, 머리글을 기기 픽셀 비율(DPR)에 맞춰 키웠습니다.

복구 이력은 자동 저장과 별개로 로컬에 스냅샷을 쌓아 두는 기능입니다. 5분마다 한 번, 최근 20개를 보관하고 목록에서 골라 되돌립니다. 되돌리기 자체도 undo할 수 있어야 해서, 복원 직전 상태를 먼저 스냅샷으로 남기도록 고쳤습니다. 이 수정이 없으면 복원을 잘못 눌렀을 때 직전 작업이 사라집니다.

## 정리

- 외부 자료는 스펙을 고쳐 쓰지 말고 새 절로 붙이게 하고, 「반영 / 유지 / 범위 밖」을 이유와 함께 나눠 두면 다음 세션이 같은 논의를 반복하지 않습니다.
- 2D와 3D가 같은 store와 같은 검증 함수를 쓰게 하면 화면 사이 불일치가 구조적으로 생기지 않습니다.
- 저장 형식을 바꾸기 전에 접근 지점부터 모으면 마이그레이션 커밋이 작아집니다.
- 다음 편에서는 전기 계획, 체크리스트, 업체용 PDF, 그리고 닫힌 벽에서 방 영역을 자동으로 찾는 기능을 다룹니다.

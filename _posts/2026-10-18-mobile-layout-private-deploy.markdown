마지막 편은 기능보다 결정과 운영 이야기입니다. 모바일 화면 방침이 세 번 바뀐 과정, 공개 주소로 배포하면서 실제 집 정보를 지키려고 쌓은 장치들, 그리고 3편까지의 모든 라운드를 돌린 Claude Code 작업 방식을 정리합니다.

## 모바일 화면 방침이 세 번 바뀐 과정

처음 스펙의 범위 제외 목록에는 「모바일은 보기 전용」이 들어 있었습니다. 시공 현장에서 폰으로 평면과 체크리스트를 보는 용도면 충분하다고 봤기 때문입니다. 실제로 폰에서 써 보니 그 판단이 두 번 틀렸습니다.

![같은 예시 평면을 세 시점의 모바일 화면으로 띄운 비교](/assets/images/posts/mobile-layout-private-deploy/01-mobile-three-rounds.webp)
*폭 390px 폰 화면입니다. 왼쪽은 §33 보기 전용, 가운데는 §44 PC 화면 축소, 오른쪽은 §48 1열 배치가 들어간 현재 `main`입니다.*

| 라운드 | 방침 | 철회한 이유 |
|---|---|---|
| §33 보기 전용 | 폭 820px 이하면 편집 도구를 숨기고 보기·체크만 허용 | 폰에서 핀치로 도면이 확대되지 않고 구조·전기 도구가 보이지 않아 PC와 너무 달랐음 |
| §44 PC 화면 그대로 | 기기 폭이 1000px 미만이면 viewport를 `width=1200`으로 바꿔 PC 화면을 축소해 보여 주고, 2D 핀치 줌 추가 | PC 화면 축소가 아니라 폰 크기에 맞는 화면을 원했음 |
| §48 1열 배치 | viewport는 `device-width`, 같은 도구와 패널을 캔버스 → 속성 → 도구 순으로 세로로 쌓음. 기능 제한 없음 | 현재 방침 |

세 라운드 모두 스펙을 덮어쓰지 않고 새 절로 쌓았습니다. §44 첫 줄에는 「§33을 철회한다」와 사용자 보고 내용이, §48 첫 줄에는 「§44.1의 viewport 고정과 안내 문구를 철회한다」가 적혀 있습니다. 그래서 지금 코드만 보면 이상해 보이는 선택, 예를 들어 「모바일 전용 기능 제한을 두지 않는다」가 왜 그런지 문서에서 바로 찾을 수 있습니다.

직접 써 보기 전에는 정답을 알기 어려운 문제였고, 보기 전용에서 1열 배치까지 7시간이 안 되는 사이에 PR 세 개로 정리됐습니다. 한 번에 정답을 맞히기보다 빨리 만들고 바로 써 보는 짧은 루프가 이런 문제에는 더 맞았습니다.

### 철회하지 않고 남은 것: 2D 핀치 줌

§44에서 넣은 2D 핀치 줌은 §48 이후에도 그대로 남았습니다. 터치 포인터를 id별로 추적하다가 두 개가 되면 핀치를 시작하고, 이동할 때마다 누적하지 않고 **시작 시점의 viewBox·중점·거리 기준**으로 다시 계산합니다. 매번 직전 값에 배율을 곱하면 작은 오차가 쌓여 화면이 흔들리기 때문입니다. 아래는 원리만 새로 쓴 예시입니다.

```ts
type ViewBox = { x: number; y: number; w: number; h: number };
type Pt = { x: number; y: number };

// v0, mid0, dist0: 두 번째 손가락이 닿은 순간의 값. size: SVG 요소의 화면 크기(px)
export function pinch(v0: ViewBox, size: { w: number; h: number },
                      mid0: Pt, mid: Pt, dist0: number, dist: number): ViewBox {
  const factor = dist / dist0;
  const w = Math.min(50000, Math.max(50, v0.w / factor));
  const h = w * (v0.h / v0.w);
  // 시작 중점 아래에 있던 평면 좌표가 지금 중점 아래에 오도록 옮김(줌 + 팬)
  const px = v0.x + (mid0.x / size.w) * v0.w;
  const py = v0.y + (mid0.y / size.h) * v0.h;
  return { x: px - (mid.x / size.w) * w, y: py - (mid.y / size.h) * h, w, h };
}
```

손가락 하나를 떼면 핀치와 팬을 모두 끝냅니다. 남은 손가락이 화면을 튀게 하지 않기 위해서입니다.

## 공개 배포에서 실제 집 정보 지키기

앱은 GitHub Pages로 공개 주소에 배포됩니다. 그래서 「무엇이 공개되는가」를 처음부터 나눠 두었습니다. 주소, 단지명, 매물 링크, 원본 평면도 이미지는 gitignore된 `private/`에만 두고, 저장소와 번들에는 이름이 「우리 집」인 평면 프리셋과 단지명을 지운 평면도 배경만 들어갑니다.

여러 겹으로 막았습니다.

| 장치 | 하는 일 |
|---|---|
| 스캔 스크립트 | `private/`의 금지어 목록으로 스테이징된 변경, 추적 파일, 커밋 로그, 빌드 결과를 각각 검사. 출력에는 금지어 자체가 아니라 `term#N` 번호만 표시 |
| CI | PR과 `main` push마다 같은 스캔 실행. 금지어는 저장소 secret으로 넣어 목록 자체가 공개되지 않음. secret이 없으면 잡이 실패해 조용히 통과하지 않음 |
| 번들 가드 | 빌드 후 허용된 평면도 외 이미지, `private/` 흔적, 잘못된 base path를 검사. 하나라도 걸리면 배포 중단 |
| 입장 PIN | 공개 주소에 집 평면이 실리므로 가족만 들어오도록 4자리 PIN을 물음. 스펙에 「가림막이지 보안 장치가 아니다」라고 명시 |
| 내보내기 | PNG/PDF에 원본 평면도 이미지를 넣지 않음 |

![공개 주소에 접속하면 보이는 입장 화면](/assets/images/posts/mobile-layout-private-deploy/02-pin-gate.webp)
*공개 주소의 첫 화면입니다. 정적 사이트라 PIN 해시와 실패 횟수가 브라우저에 있어, 이 화면은 보안 장치가 아니라 가림막입니다. 민감한 정보는 처음부터 번들에 넣지 않는 것이 실제 방어선입니다.*

### 소스는 비공개, 배포는 빌드 결과만

처음에는 소스 저장소 자체를 공개하고 Pages를 돌렸습니다. 이후 코드는 비공개로 두고 사이트만 공개하기로 정했는데, GitHub Free에서는 비공개 저장소의 Pages를 쓸 수 없습니다. 그래서 저장소를 둘로 나눴습니다(§53).

1. 소스 저장소를 이름을 바꿔 비공개로 돌리고, 개발·PR·개인정보 스캔은 그대로 여기서 합니다.
2. 같은 이름의 공개 저장소를 새로 만들고, 소스 저장소의 Actions가 `npm ci → typecheck → test → build → check:dist`를 통과하면 `dist/`를 커밋 하나로 만들어 deploy key로 강제 push합니다. 공개 쪽에는 소스도 이력도 남지 않습니다.
3. 사이트 주소와 base path는 바뀌지 않습니다.

여기서 주의할 지점이 하나 있었습니다. 평면을 GitHub 저장소에 저장하는 기기 간 동기화 기능(§45)은 기본 저장소 이름을 브라우저 설정에 저장해 둡니다. 저장소 이름을 바꾸면 옛 이름이 그대로 남은 브라우저는 **새로 만든 공개 배포 저장소**에 평면을 쓰려고 하게 됩니다. 설정을 읽을 때 옛 이름을 새 이름으로 바꾸는 변환과 테스트를 같은 라운드에 넣었습니다.

또 하나, 이미 공개였던 기간의 이력은 회수할 수 없다는 점도 스펙에 적었습니다. 저장소를 비공개로 돌려도 그전에 복제되거나 캐시된 것은 남습니다. 처음부터 공개 범위를 나눠 둔 것이 결과적으로 가장 중요한 장치였습니다.

## 이 라운드들을 돌린 Claude Code 작업 방식

10-08부터 10-11까지 `main`에 머지된 PR은 56개입니다. 흐름은 매번 같았습니다.

- **요청마다 워크트리 하나.** 요청이 오면 `git worktree`로 별도 디렉터리와 브랜치를 만듭니다. 여러 세션이 같은 저장소를 동시에 만져도 서로의 변경을 밟지 않습니다.
- **메인 세션은 설계, 구현은 서브에이전트.** 메인 세션은 브레인스토밍하고 스펙 절과 계획을 씁니다. 승인되면 구현은 서브에이전트에게 맡기고, 리뷰는 「스펙과 다른 것」을 결함으로 취급합니다.
- **끝나는 방식을 고정.** typecheck → 단위 테스트 → e2e → 실제 브라우저 탐색 QA → 문서 동기화 → 개인정보 스캔 → PR → 머지 → 워크트리·브랜치 정리까지가 한 라운드입니다. 머지된 브랜치나 워크트리가 남아 있으면 그 라운드의 결함으로 봅니다.

반복되는 절차는 `CLAUDE.md`에 길게 쓰지 않고 프로젝트 스킬로 뺐습니다. `CLAUDE.md`에는 규칙과 「언제 어떤 스킬을 부르는가」 표만 남습니다.

| 스킬 | 언제 |
|---|---|
| `committing-safely` | 커밋·PR 전. 워크트리 확인, 경로를 하나씩 지정해서만 `git add` |
| `checking-privacy` | 커밋·문서·내보내기·배포 근처 |
| `syncing-docs` | 라운드 마무리. 어떤 문서의 어느 절을 갱신할지 표로 |
| `migrating-plan-schema` | 스키마 변경. 버전 증가 + 마이그레이션 + 테스트 |
| `adding-catalog-product` | 제품 추가, 샘플 치수를 공식 사양으로 교체 |
| `exploratory-qa` | 테스트가 다 통과한 뒤 실제 브라우저 확인 |

### 규칙으로 만든 교훈

- **리뷰만으로는 런타임 버그를 못 잡습니다.** 리뷰를 통과한 변경이 실제 브라우저에서 3D가 안 뜨거나 드래그가 안 되는 일이 있었습니다. 그 뒤로 「테스트 통과 후 실제 브라우저 QA」를 완료 조건에 넣었고, 이 규칙은 스펙의 테스트 절에도 적혀 있습니다.
- **테스트를 초록으로 만드는 꼼수를 명시적으로 금지합니다.** 기대값 수정, 테스트 skip, e2e에서 실제 사용자 조작 대신 store를 직접 호출하기를 규칙으로 막았습니다.
- **문서도 완료의 일부입니다.** 매 라운드 `HANDOFF.md`(현재 상태·다음 할 일), 기능 → 코드 → 스펙 지도, 모듈 메모를 같이 갱신합니다. 새 세션이 문서 몇 개만 읽고 바로 이어 갈 수 있습니다.
- **쌓인 군더더기는 따로 치웁니다.** 기능 라운드가 이어지면서 쓰이지 않는 export가 쌓였고, 정리만 하는 PR 하나로 미사용 export 117개와 죽은 타입 4개를 걷어 냈습니다.

## 남은 일과 정리

- 실제 구매할 가전 모델 목록을 받아 샘플 치수를 공식 사양으로 교체해야 합니다.
- 기기 간 동기화와 1열 배치는 실제 휴대폰 Safari에서 더 써 봐야 합니다.

네 편을 정리하면 이렇습니다. 설계 문서와 계획을 먼저 쓰게 하고, 요구가 바뀔 때마다 스펙을 새 절로 쌓고, 한 라운드가 끝나는 조건을 테스트·브라우저 QA·문서·개인정보 스캔까지로 고정하면, 마흔 번 넘게 요구가 바뀌어도 「왜 이렇게 됐는지」를 잃지 않습니다. 이제 이 도구로 실제 업체 미팅에 들어가 볼 차례입니다.

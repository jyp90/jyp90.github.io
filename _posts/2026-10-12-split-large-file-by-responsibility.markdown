## 문제와 배경

브라우저에서 AI 코딩 에이전트 세션을 관리하는 개인 웹앱을 몇 주째 만들고 있었습니다. Node 서버와 React SPA로 된 평범한 구조인데, 기능을 하루에 몇 개씩 붙이다 보니 어느 날 파일 크기가 이렇게 되어 있었습니다.

| 파일 | 줄 수 | 하는 일 |
|------|------:|---------|
| 사이드바 컴포넌트 | 1,842 | 목록 계산, 드래그, 새로고침, 렌더링 |
| 세션 매니저(서버) | 1,818 | 세션 수명주기, 권한, 서브에이전트, 알림 |
| 라우트 파일(서버) | 1,234 | 모든 REST 엔드포인트 |
| 전역 스토어 | 1,133 | 타입, 저장 설정, 리듀서, 액션 |

문제는 크기 자체보다 **수정할 때마다 무관한 코드를 같이 읽어야 한다**는 점이었습니다. 사이드바의 정렬 하나를 고치려면 드래그 처리와 새로고침 타이머를 지나가야 했고, 테스트도 컴포넌트를 통째로 띄워야만 쓸 수 있었습니다. AI 에이전트에게 작업을 맡길 때도 마찬가지입니다. 파일 하나가 컨텍스트를 크게 차지하니 수정 범위를 정확히 잡지 못하고 엉뚱한 곳을 건드리는 일이 늘었습니다.

## 접근

"줄 수가 많으니 반으로 나누자"로 시작하면 실패합니다. 위아래로 자르면 서로를 import하는 두 파일이 생길 뿐입니다. 그래서 순서를 정했습니다.

1. **쪼개기 전에 책임부터 나열한다.** 파일을 위에서 아래로 읽으며 "이 블록은 무엇을 책임지는가"를 한 줄씩 적습니다. 코드는 한 줄도 옮기지 않습니다.
2. **순수 로직부터 뽑는다.** React나 HTTP에 의존하지 않는 계산(목록 정렬·그룹핑, 상태 전이)을 먼저 함수로 꺼냅니다. 테스트하기 가장 쉽고, 나머지 분리의 기준점이 됩니다.
3. **상태와 부수효과는 훅/모듈로, 화면은 작은 컴포넌트로.** 남은 코드는 "무엇을 기억하는가(상태)"와 "무엇을 그리는가(뷰)"로 나눕니다.
4. **원래 파일은 조립만 남긴다.** 분리 후 원래 파일은 뽑아낸 조각을 연결하는 얇은 층이 됩니다.
5. **같은 PR 안에서 테스트를 옮기고, 모듈 지도를 갱신한다.**

한 PR에 한 덩어리(서버 세션, 서버 라우트, 웹 뷰, 웹 사이드바·스토어)씩, 하루에 PR 4개로 끝냈습니다.

## 구현

### 1단계: 책임 목록

전역 스토어의 책임 목록은 이렇게 나왔습니다.

```text
- 타입 정의: 세션, 메시지, 패널 상태 ……………… 약 300줄
- 저장되는 사용자 설정 (localStorage 읽기/쓰기) …… 약 130줄
- 서버 이벤트 → 상태 변환 (순수 리듀서) ………… 약 440줄
- 액션과 스토어 생성 ……………………………… 나머지
```

이 목록이 곧 새 파일 목록이 됩니다. `storeTypes.ts`, `storeSettings.ts`, `storeReducer.ts`, 그리고 조립만 남은 `store.ts`. 결과적으로 스토어는 1,133줄에서 284줄이 되었습니다.

### 2단계: 순수 로직 먼저 — 리듀서 추출

서버 이벤트를 상태로 바꾸는 부분은 원래 스토어의 `set()` 콜백 안에 섞여 있었습니다. 이것을 "이전 상태 + 이벤트 → 다음 상태" 함수로 꺼냅니다.

```ts
// storeReducer.ts — React도, 스토어 라이브러리도 import하지 않는다
import type { ChatState, ServerEvent } from './storeTypes';

export function applyEvent(state: ChatState, ev: ServerEvent): ChatState {
  switch (ev.type) {
    case 'message':
      return { ...state, messages: [...state.messages, ev.message] };
    case 'status':
      return { ...state, status: ev.status };
    default:
      return state;
  }
}
```

```ts
// store.ts — 조립만 남는다
import { create } from 'zustand';
import { applyEvent } from './storeReducer';
import { loadSettings } from './storeSettings';

export const useChatStore = create<Store>()((set) => ({
  ...initialState(loadSettings()),
  receive: (ev) => set((s) => applyEvent(s, ev)),
}));
```

리듀서가 순수 함수가 되자 테스트가 단순해졌습니다. 스토어나 컴포넌트를 띄울 필요 없이 입력과 출력만 비교하면 됩니다.

```ts
it('status 이벤트는 상태만 바꾼다', () => {
  const next = applyEvent(base, { type: 'status', status: 'idle' });
  expect(next.status).toBe('idle');
  expect(next.messages).toBe(base.messages); // 참조 유지
});
```

### 3단계: 상태는 훅으로, 화면은 작은 컴포넌트로

사이드바(1,842줄)는 같은 기준으로 다섯 갈래가 되었습니다.

- 세션 트리 계산 (그룹·정렬·고정) → 순수 함수 + 테스트
- 목록 상태와 필터 → `useSessionLists`
- 드래그 앤 드롭 → `useSessionDrag`
- 주기적 새로고침 → `useSidebarRefresh`
- 남은 렌더링 → 행·그룹 컴포넌트

```tsx
// 분리 후 사이드바는 조각을 연결하는 역할만 한다
export function Sidebar() {
  const lists = useSessionLists();
  const drag = useSessionDrag(lists.reorder);
  useSidebarRefresh(lists.refresh);
  return <SessionTree groups={lists.groups} drag={drag} />;
}
```

결과는 1,842줄 → 933줄입니다. 절반이 남은 것은 실패가 아니라, 남은 부분이 실제로 화면을 그리는 코드라서입니다. 목표는 "작게"가 아니라 **한 파일에 한 가지 이유로만 바뀌게** 하는 것입니다.

### 4단계: 서버에도 같은 패턴

라우트 파일은 책임 목록이 곧 URL 접두사였습니다. 세션, 파일, 회의록 라우트를 각각 모듈로 옮기고, 원래 파일에는 공통 미들웨어와 등록만 남겼습니다(1,234줄 → 500줄).

```ts
// routes.ts — 보안 미들웨어를 먼저 걸고, 모듈을 등록만 한다
export function buildRoutes(deps: Deps) {
  const app = new Hono();
  app.use('/api/*', csrfGuard());       // 모든 라우트보다 먼저
  app.route('/api', sessionRoutes(deps));
  app.route('/api', fsRoutes(deps));
  app.route('/api', meetingRoutes(deps));
  return app;
}
```

이렇게 나누면 "새 라우트가 보안 미들웨어보다 앞에 등록되는" 실수가 구조적으로 어려워집니다. 등록 순서가 한 화면에 다 보이기 때문입니다.

세션 매니저(1,818줄)는 수명주기라는 핵심을 남기고, 세션 핸들 타입, 서브에이전트 메시지 라우팅, 접속 상태 반영, 알림 힌트처럼 "매니저를 거쳐 가지만 매니저의 일은 아닌" 것들을 모듈로 옮겼습니다. 이 과정에서 같은 이벤트를 두 번 내보내던 코드와 핸들 종료 처리 중복도 드러나서 함께 정리했습니다. 쪼개면 중복이 보입니다.

## 함정과 트레이드오프

**동작을 바꾸고 싶은 유혹.** 코드를 옮기다 보면 고치고 싶은 것이 계속 보입니다. 리팩터링 PR에서는 옮기기만 하고, 발견한 버그는 별도 커밋으로 분리했습니다. 실제로 웹 뷰 분리 PR 직후에 명령 실행 상태가 해제되지 않는 문제가 보였는데, `finally`에서 해제하는 수정은 별도 fix 커밋으로 뺐습니다. 그래야 리뷰어가 "이 diff는 이동뿐"이라고 믿고 읽을 수 있습니다.

**순환 import.** 타입을 먼저 별도 파일로 빼지 않으면, 리듀서와 스토어가 서로의 타입을 import하는 순환이 생깁니다. 그래서 순서가 늘 **타입 → 순수 로직 → 상태 → 뷰**입니다.

**파일이 늘면 길을 잃는다.** 4개 파일이 20개가 되면 "이 기능이 어디 있지?"가 새 문제가 됩니다. 그래서 패키지마다 모듈 지도(`MODULE-MAP.md`)를 두고, 파일마다 "무엇을 소유하고 무엇을 지키는지"를 한두 줄로 적었습니다. 이 문서는 통째로 읽지 않고 파일 이름으로 grep해서 씁니다. AI 에이전트에게도 "모듈 지도에서 파일 이름을 grep하라"고 규칙을 걸어 두니 컨텍스트를 덜 쓰면서 위치를 찾았습니다.

**AI에게 맡길 때의 분할.** 이번 리팩터링은 Claude Code 서브에이전트가 PR 단위로 구현하고, 메인 세션이 리뷰한 뒤 병합했습니다. 효과가 컸던 것은 "책임 목록 → 새 파일 목록"을 먼저 사람이 확정하고 넘긴 점입니다. 경계가 정해져 있으니 에이전트는 옮기는 일에만 집중했고, 리뷰는 "목록에 없는 변경이 있는가"만 보면 됐습니다.

## 정리

큰 파일을 나눌 때 쓴 체크리스트입니다.

1. 코드를 옮기기 전에 **책임 목록**을 적는다. 그 목록이 새 파일 목록이다.
2. **타입 → 순수 로직 → 상태(훅/모듈) → 뷰** 순서로 뽑는다.
3. 원래 파일에는 **조립만** 남긴다.
4. 리팩터링 PR에는 **이동만** 담고, 발견한 버그는 별도 커밋으로 뺀다.
5. 뽑아낸 순수 로직에는 그 자리에서 **단위 테스트**를 붙인다.
6. 파일이 늘어난 만큼 **모듈 지도**를 갱신한다.

줄 수는 결과일 뿐입니다. 이번에도 사이드바는 절반이 남았지만, 정렬을 고칠 때 열어야 하는 파일은 72줄짜리 하나가 되었습니다.

2편까지 만든 것은 「배치해 보는 도구」였습니다. 실제 인테리어에 쓰려면 두 가지가 더 필요했습니다. 하나는 시공업체 미팅에 들고 갈 문서이고, 다른 하나는 방마다 바닥재·벽지를 입혀 볼 수 있는 방 영역입니다. 3편은 구현 계획 4(전기·체크리스트·PDF)와 그다음 날 이어진 스펙 라운드들을 다룹니다.

## 전기 계획: 벽에 붙는 설비와 전용 회로 확인

콘센트·스위치·조명은 「전기 설비」라는 별도 모델로 둡니다. 벽 가까이(30cm 이내)를 클릭하면 벽면에 붙고, 설치 높이와 메모를 가집니다. 배치된 가전 중 전용 회로가 필요한 제품(세탁기, 에어컨, 인덕션 등) 근처 150cm 안에 전용 회로 콘센트가 없으면 경고합니다.

![계획 4 시점의 전기 탭](/assets/images/posts/contractor-pdf-room-detection/01-electrical.webp)
*계획 4 시점: 전기 탭입니다. 왼쪽 아래에 「전용회로가 필요한 가전 — 드럼세탁기, 150cm 이내 전용회로 콘센트 없음」 경고가 뜨고, 오른쪽은 선택한 전용 회로 콘센트의 위치·설치 높이입니다.*

여기서 생긴 문제는 벽을 고친 뒤였습니다. 벽 길이나 두께를 바꾸거나 끝점을 끌면, 벽에 붙어 있던 콘센트가 허공에 남았습니다. 벽이 바뀌어도 그 벽에 붙은 설비의 좌표를 다시 계산하지 않았기 때문입니다. 벽이 바뀔 때 같은 벽면 위의 비율 위치로 설비를 다시 맞추고, 설비 종류를 조명으로 바꾸면 벽에서 떼고, X/Y를 직접 고쳐 벽면을 벗어나면 벽 연결을 끊도록 고쳤습니다.

## 체크리스트: 기본 항목과 배치에서 생기는 항목

체크리스트는 공정(철거, 목공·전기, 타일, 도배, 주방 등)별 기본 항목에, 평면에서 자동으로 생기는 항목을 더합니다. 예를 들어 전용 회로가 없는 가전이 있으면 「[자동] 전용회로 확인」 항목이, 문 열림 공간이 부족한 가구가 있으면 그에 맞는 항목이 붙습니다.

![계획 4 시점의 체크리스트 탭](/assets/images/posts/contractor-pdf-room-detection/02-checklist.webp)
*같은 시점의 체크리스트 탭입니다. 공정별로 묶인 항목마다 체크와 메모가 있고, 현재 배치안과 전기 계획에서 만든 자동 항목이 함께 표시됩니다.*

`CLAUDE.md`에는 체크리스트와 PDF 문구에 관한 규칙을 따로 적었습니다. 참고 자료의 문구를 그대로 옮기지 않고 새로 쓰며, 예산 금액과 업체 평가 기준은 앱 데이터와 PDF에 넣지 않습니다. 업체에 건네는 문서에 우리 쪽 판단 기준이 섞여 나가는 일을 막기 위해서입니다.

## 업체용 PDF: 페이지 계산과 렌더링을 나누기

PDF는 두 단계로 나눴습니다.

1. `export/pages.ts`: 어떤 페이지에 무엇이 들어가는지, 긴 표를 어디서 끊는지, 긴 글을 어디서 줄바꿈하는지 계산하는 순수 함수입니다. React도 jsPDF도 import하지 않아 단위 테스트로 쪽 나눔을 검증할 수 있습니다.
2. `export/pdf.ts`: 계산된 페이지 데이터를 jsPDF와 svg2pdf.js로 그립니다. 평면도는 앱이 쓰는 것과 같은 SVG 생성 함수를 PDF용 옵션으로 호출해 만들고, 3D 보기는 고정된 시점 세 곳에서 캔버스를 캡처합니다. 라이브러리와 한글 글꼴은 「PDF 내려받기」를 누를 때 지연 로딩합니다.

![업체용 PDF 중 치수 평면도, 배치도, 전기 계획도, 3D 보기 페이지](/assets/images/posts/contractor-pdf-room-detection/03-pdf-pages.webp)
*같은 시점에 예시 평면으로 내려받은 PDF 10쪽 중 4쪽입니다. 치수 평면도, 가구·가전 배치도(번호는 제품 목록과 대응), 전기 계획도(범례 포함), 고정 시점 3D 보기입니다. 나머지는 표지, 전기 설비 목록, 빌트인 상세, 제품 목록, 공사 체크리스트입니다.*

한글 PDF에서는 함정이 몇 가지 있었습니다.

| 증상 | 원인 | 대응 |
|---|---|---|
| PDF 안 SVG 글자에 한글 글꼴이 적용되지 않음 | svg2pdf는 등록한 글꼴 이름을 SVG에서 명시해야 적용함 | PDF용 SVG의 `<text>`에 `font-family="Pretendard"` 지정 |
| 흰 외곽선을 두른 라벨이 앱 화면처럼 나오지 않음 | svg2pdf가 `paint-order`를 지원하지 않음 | 같은 `<text>`를 외곽선 층과 글자 층 두 겹으로 그림 |
| 사용자가 입력한 이름 일부가 깨짐 | Pretendard에 이모지 글리프가 없음 | PDF용 텍스트에서 이모지·변형 선택자·접합자를 제거 |
| 치수 평면도에서 문 위치 라벨과 폭 라벨이 겹침 | 두 라벨의 자리를 따로 잡지 않았음 | 위치 라벨과 폭 라벨을 분리해 배치 |

PDF 쪽 수정은 대부분 실제로 내려받은 파일을 열어 봐야 보이는 것들이었습니다. 단위 테스트는 쪽 수와 표 분할을 확인할 뿐이고, 글꼴이 실제로 적용됐는지는 빌드 결과에서 PDF를 받아 확인하는 별도 e2e(`e2e:preview`)로 나중에 묶었습니다.

## 다음 날: 「실제로 쓰기에 부족한 점」 라운드

계획 4까지 끝낸 뒤 「실제 인테리어용으로 부족한 점을 찾아 개선」을 요청했습니다. Claude Code가 조사해 정리한 결과는 이랬습니다. 카탈로그가 샘플 6개뿐이라 실제 집 배치안이 비어 있었고, 벽걸이·상부장·천장형 가전의 설치 높이를 정할 수 없었으며, 충돌 검사가 높이를 보지 않았습니다. 이 결과가 스펙 §20(카탈로그 확충·설치 높이) 라운드가 됐습니다.

설치 높이가 들어오면서 충돌 규칙이 바뀌었습니다. 아이템마다 세로 구간 `[설치 높이, 설치 높이 + 높이]`를 두고, 평면 OBB가 겹치고 세로 구간도 겹칠 때만 충돌로 봅니다. 문 열림 영역은 문 높이 구간과 겹치는 아이템만, 제품 앞 공간은 장애물의 세로 구간이 겹칠 때만 막힌 것으로 봅니다. 그래서 상부장 앞 냉장고는 막힘, 상부장 아래 식탁은 통과입니다.

같은 날 방 바닥재·벽지(§19), 3D 문짝과 창 유리(§23), 코너 싱크대와 레인지후드(§29), 배치된 가구 목록 패널(§28)이 각각 별도 PR로 들어갔습니다.

![방 영역에 바닥재와 벽지를 입힌 3D 화면](/assets/images/posts/contractor-pdf-room-detection/04-room-finish-3d.webp)
*§19 방 바닥재·벽지 머지 시점: 방마다 바닥 영역을 지정하면 거실에는 나무 바닥, 침실에는 타일과 녹색 벽지처럼 방별 마감이 3D에 입혀집니다. 이 시점에는 방 영역을 손으로 그려야 했습니다.*

![3D 문짝과 창 유리가 들어간 화면](/assets/images/posts/contractor-pdf-room-detection/05-openings-3d.webp)
*§23 3D 문짝·창 유리 머지 시점: 그전까지 벽에 뚫린 구멍이던 문과 창에 문짝과 유리가 생겼습니다.*

![코너 하부장과 상부장을 놓은 3D 화면과 배치된 가구 목록](/assets/images/posts/contractor-pdf-room-detection/06-corner-cabinet.webp)
*§29 코너 싱크대·레인지후드 머지 시점: 거실 왼쪽 위 모서리에 코너 하부장·상부장과 싱크대 하부장·상부장을 놓은 화면입니다. 왼쪽 「배치된 가구」 목록(§28)에서 충돌·경고 배지를 한눈에 볼 수 있습니다.*

## 닫힌 벽에서 방 영역 자동 인식

방마다 바닥재를 입히려면 방의 다각형이 필요한데, 벽을 다 그린 뒤 방 윤곽을 또 그리는 것은 번거로웠습니다. 실제 집 평면을 넣어 보니 방 라벨은 있는데 영역이 하나도 없어 마감이 적용되지 않았고, 이것이 §35 라운드의 출발점이었습니다. 방 이름 라벨 위치를 씨앗으로 삼아 영역을 자동으로 찾습니다.

1. 벽 전체 바운딩 박스를 한 칸씩 넓힌 5cm 격자를 만들고, 칸 중심이 벽 OBB 안이면 막힌 칸으로 표시합니다. 문·창이 있어도 벽은 경계로 봅니다.
2. 씨앗 칸에서 4방향 flood fill을 합니다. 넓힌 테두리 칸에 닿으면 벽이 닫히지 않은 것이므로 실패입니다.
3. 채운 칸들의 경계 변을 이어 가장 긴 고리(외곽)만 취하고, 일직선 위의 꼭짓점을 지웁니다.
4. 각 꼭짓점을 가까운 벽 **마감면 모서리**에 스냅해 격자 계단을 정확한 정수 cm 좌표로 되돌립니다.

아래는 1–2단계만 새로 쓴 최소 예시입니다.

```ts
type Cell = [number, number];

export function floodFill(
  cols: number, rows: number,
  blocked: (c: number, r: number) => boolean,
  seed: Cell,
): Set<string> | null {
  const filled = new Set<string>();
  const stack: Cell[] = [seed];
  while (stack.length > 0) {
    const [c, r] = stack.pop()!;
    const key = `${c},${r}`;
    if (filled.has(key) || blocked(c, r)) continue;
    if (c === 0 || r === 0 || c === cols - 1 || r === rows - 1) return null; // 테두리에 닿음: 벽이 열려 있음
    filled.add(key);
    stack.push([c + 1, r], [c - 1, r], [c, r + 1], [c, r - 1]);
  }
  return filled;
}
```

격자 근사로 영역을 찾고 기하 스냅으로 좌표를 정리하는 조합이라, 다각형 연산 라이브러리 없이도 결과 좌표가 마감면과 정확히 맞습니다. 단위 테스트는 직사각형 방이 마감면 좌표와 정확히 같은지, L자 방, 문이 있는 벽, 벽이 안 닫힌 경우, 씨앗이 벽 안에 있는 경우를 확인합니다. 각진 벽의 마감면 스냅과 방 안 기둥은 범위 밖으로 남겼습니다.

![구조 탭에서 「영역 없는 방 자동 인식」을 누른 화면](/assets/images/posts/contractor-pdf-room-detection/07-auto-room-area.webp)
*§35 방 영역 자동 인식 머지 시점: 「영역 없는 방 자동 인식」을 누르면 「2개 방의 영역을 인식했습니다」 배너와 함께 두 방에 바닥 영역이 생기고 기본 바닥재가 칠해집니다.*

배경 도면을 흑백으로 바꾼 것도 같은 라운드입니다. 컬러 평면도 이미지의 색이 2D에 비쳐 방이 이미 칠해진 것처럼 보였기 때문입니다.

## 정리

- 문서 출력은 「무엇을 어느 쪽에 넣을지」 계산하는 순수 함수와 실제 렌더러를 나누면 쪽 나눔을 단위 테스트로 잡을 수 있습니다. 글꼴 적용처럼 렌더러에서만 보이는 문제는 실제 파일로 확인하는 e2e가 따로 필요합니다.
- 「부족한 점을 찾아 달라」는 열린 요청도 결과를 스펙 라운드로 정리하게 하면, 이후 PR 단위로 나눠 진행할 수 있습니다.
- 다음 편에서는 모바일 대응을 세 번 바꾼 과정과, 공개 배포에서 실제 집 정보를 지키기 위해 저장소를 나눈 과정, 그리고 이 모든 라운드를 돌린 Claude Code 작업 방식을 다룹니다.

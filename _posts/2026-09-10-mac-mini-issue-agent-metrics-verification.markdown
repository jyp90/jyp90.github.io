7편에서는 실행당 비용을 재는 원장의 결함과, 비용 대부분이 캐시를 다시 읽고 쓰는 데서 나오는 구조를 다뤘습니다. 이 편에서는 측정이 조용히 틀리는 지표를 어떻게 스스로 의심하게 만들었는지, 자동 검증과 배포의 경계를 어디에 그었는지, 이미 구현된 요구를 받았을 때의 규칙, 그리고 사람이 처리한 것과 에이전트가 처리한 것을 왜곡 없이 비교하는 방법을 다룹니다.

## 조용히 틀리는 지표

### 0은 두 가지를 뜻합니다

깨진 측정은 대개 예외를 던지지 않습니다. 찾는 문자열이 없으면 0건이고, 읽을 파일이 없으면 빈 집합입니다. 리포트에 찍힌 0은 「일이 없었다」와 「세는 장치가 망가졌다」를 동시에 뜻하는데, 사람은 그것을 앞의 뜻으로 읽습니다. 고장이 실적으로 보고되고, 아무도 놀라지 않으니 오래 갑니다.

이 에이전트에서 실제로 난 경우는 세 가지였습니다.

- 폴러가 세션 실행 방식을 동기에서 비동기로 바꾸면서 로그 문구도 바뀌었는데, 다이제스트 스크립트는 옛 문구를 세고 있었습니다. 주간 리포트는 오랫동안 「트리거 0회」를 보고했고, 일일 리포트는 「활동 0건이면 보내지 않는다」는 가드에 걸려 아예 발송되지 않았습니다.
- 원장 적재 누락으로 총액이 조용히 작아졌습니다(7편의 원장 결함 참고).
- 집계 블록이 죽어도 스크립트의 종료 코드가 0이라 cron이 성공으로 봤습니다.

첫째와 셋째는 [실패했는데 성공으로 끝나는 시스템 — 종료 코드 0과 fail-open 게이트](/blog/2026/10/07/silent-failure-exit-code-fail-open.html)에서 로그 문구가 계약이 되는 문제와 종료 코드 판정을 자세히 다뤘으므로 여기서는 반복하지 않습니다. 이 글에서는 지표 쪽에 넣은 방어만 정리합니다.

세 경우 모두 관측 대상과 관측 장치가 따로 진화해서 생겼습니다. 폴러는 문구를 바꿨는데 다이제스트는 바꾸지 않았고, 폴러는 적재에 실패했는데 집계기는 원장만 믿었고, 집계기는 죽었는데 호출자는 종료 코드만 봤습니다. 그래서 방어의 방향도 「더 정확히 세자」가 아니라 「어긋났는지 스스로 묻자」로 잡았습니다.

### 정합성 배너: 조용한 0을 금지합니다

리포트가 스스로를 의심하고, 의심스러우면 본문 맨 위에 경고를 답니다.

```bash
banner=""
if [ "$log_lines_read" -eq 0 ]; then
  banner="지표 수집 이상: 로그를 읽지 못했습니다. 아래 수치는 모두 무효입니다."
elif [ "$launched" -gt 0 ] && [ $((completed + failed)) -eq 0 ]; then
  banner="지표 수집 이상: 발사 기록은 있는데 종료 기록이 없습니다. 종료 마커 불일치를 의심합니다."
elif [ "$ledger_rows" -gt 0 ] && [ "$completed" -eq 0 ]; then
  banner="지표 수집 이상: 원장에는 실행이 있는데 로그 완료가 0입니다. 마커 불일치를 의심합니다."
elif [ "$cost_main" != "$cost_check" ]; then
  banner="지표 수집 이상: 비용 집계 두 경로가 다릅니다. 비용 수치를 신뢰하지 마십시오."
fi
```

첫 조건이 가장 중요합니다. 로그를 한 줄도 읽지 못하면 나머지 조건이 모두 성립하지 않으므로, 이 조건이 없으면 「경고 없는 전부 0 리포트」가 나갑니다. 그것이 정확히 처음 사고의 모양입니다.

배너 문구에는 관측 사실만 씁니다. 원장 적재 결함을 고친 뒤 「적재 결함 재발 의심」이라는 이름으로 경고를 만들었는데, 이 경고가 매일 뜨기 시작했습니다. 조사해 보니 재발이 아니라 앞에서 말한 창 필터 누락과 격리 오염 때문이었습니다. 경고가 결함 이름을 직접 부르니 조사가 엉뚱한 곳에서 시작됐습니다. 원인 판정은 사람에게 넘기고 경고는 「무엇이 무엇과 어긋났는가」만 말하게 했습니다.

### 이중 경로 교차 검증

비용은 두 경로로 따로 계산해 대조합니다.

- **주 경로**: 원장, 실행 스크립트, 세션 로그를 대조해 미적재분까지 회수하는 분석기입니다. 읽는 파일이 많아 정확하지만 실패할 여지도 넓습니다.
- **대조 경로**: 원장 하나만 읽어 합산하는 짧은 코드입니다. 회수는 못 하지만 실패 경로가 짧습니다.

두 값이 어긋나면 배너가 뜹니다. 주 경로가 죽으면 대조 경로 단독으로 축소 집계하고, 그 사실도 배너와 집계 경로 표시로 알립니다. 짧은 쪽을 대조군으로 남겨 두는 것이 요점입니다.

### 실패는 막고, 저하는 알립니다

- 지표 집계 자체가 실패하면 리포트를 보내지 않고 cron 로그에 실패를 남깁니다.
- 비용 분석기만 실패하면 리포트는 보내고 배너를 답니다.

비용 하나 때문에 나머지 지표를 모두 버리면 「리포트가 오랫동안 발송되지 않았다」는 사고와 같은 종류의 손실이 생깁니다. 전부 막거나 전부 통과시키는 대신, 무엇을 잃었는지 말하면서 통과시킵니다.

마커 검사도 회귀 테스트로 넣었습니다. 집계가 세는 마커를 폴러 소스와 최근 며칠의 실제 로그 양쪽에 대조합니다. 한쪽만으로는 잡히지 않습니다. 소스만 보면 진단용 경로에 남아 있는 옛 문구 때문에 통과하고, 로그 전체를 보면 문구가 바뀌기 전의 기록에 속습니다. 마커 패턴에는 실제 이슈 키 형식의 앵커를 넣어서 테스트용 키로 남은 로그가 실적으로 세지지 않게 했습니다. 이슈 키 패턴은 정규식에 박지 않고 설정에서 읽습니다. 다른 프로젝트 키가 섞이는 순간 마커, 집계, 이슈 추출이 동시에 0이 되기 때문입니다.

## 자동 검증의 한계와 배포 경계

### 에이전트가 할 수 있는 검증은 환경이 정합니다

이 에이전트가 다루는 코드는 Java와 JSP로 된 레거시 웹 애플리케이션이었습니다. 운영 초기에는 Mac mini에 그 프로젝트가 요구하는 JDK가 없어 빌드가 되지 않았습니다. 그러면 「구현 및 자체 검증」 단계의 실행 근거는 매번 사람에게 넘어갑니다. 이것은 설계한 경계가 아니라 환경이 비어서 생긴 경계였습니다.

빌드가 되지 않는 동안에도 근거가 되는 정적 검증은 있었습니다.

| 검증 | 방법 | 잡는 것 |
|---|---|---|
| 의도 반영 | `git diff` 전체를 확정된 설계와 항목별로 대조 | 설계 이탈, 누락, 초과 구현 |
| 문법 | 바뀐 Java 파일만 단독 컴파일하고 오류를 종류별로 분류 | 문법 오류 |
| 템플릿 구조 | 바뀐 블록만 떼어 태그 짝과 XML 정형성을 검사 | 닫히지 않은 태그, 중첩 오류 |
| 메시지 키 | 쓴 메시지 키가 모든 언어 번들에 있는지 대조 | 빈 문구, 키가 그대로 노출되는 화면 |

단독 컴파일은 클래스패스가 없으니 반드시 오류를 많이 냅니다. 오류 개수로 판정하면 늘 실패로 읽히므로, 심볼을 찾지 못한다는 계열 외의 오류가 0건인지를 봐야 근거가 됩니다.

나중에 JDK를 맞추고 의존성 캐시를 갖춰 컴파일 검증은 에이전트가 직접 하게 됐습니다. 그래도 화면 검증은 여전히 못 합니다. 서버를 띄우려면 사내망 접속, 애플리케이션 서버, 메모리가 모두 필요하기 때문입니다. 빌드가 된다고 화면이 검증되는 것은 아닙니다.

### 권한은 세 층이 같은 문자열을 공유해야 열립니다

에이전트에게 개발 브랜치 반영을 맡기기로 한 뒤에도 반영은 여러 번 막혔습니다. 원인은 층마다 달랐습니다.

- 이전 사이클이 만든 임시 워크트리가 개발 브랜치를 체크아웃한 채 남아 있어, 다른 워크트리에서 그 브랜치를 쓸 수 없었습니다. 사이클 종료 시 임시 워크트리를 회수하도록 바꿨습니다.
- 호스트 `settings.json`의 deny 규칙이 프롬프트의 지시보다 우선했습니다.
- 허용 규칙에는 스크립트 실행 형태가 등록돼 있었는데, 계약 문서는 그 앞에 `cd 저장소루트 &&`를 붙여 실행하라고 지시했습니다. 확인해 보니 막은 것은 문자열 불일치가 아니라 세션 작업 디렉터리 바깥으로 나가는 `cd`였습니다. 허용 규칙에 `cd`를 넣는 방식으로는 풀리지 않아서, 스크립트가 저장소 루트를 스스로 찾게 고쳐 `cd`를 없앴습니다.

교훈은 계약 문서, 스크립트, 호스트 권한 세 층이 같은 명령 형태를 공유해야 한다는 것입니다. 계약만 고치면 호스트가 막고, 권한만 열면 형태가 어긋나서 다시 막힙니다. 그리고 막혔을 때 에이전트가 명령 형태를 바꿔 재시도하게 두면 안 됩니다. 가드를 무력화할 뿐 아니라 이런 층간 불일치를 드러나지 않게 덮습니다. 이 에이전트는 막히면 중단하고 보고합니다. 권한 규칙이 어떻게 매칭되는지는 [Claude Code 훅을 직접 써 보며 부딪힌 함정 6가지](/blog/2026/09/30/claude-code-hook-pitfalls.html)에서 다룬 훅 동작과 함께 보면 좋습니다.

### 경계를 어디에 둘 것인가

운영하며 정리된 경계는 다음과 같습니다.

| 단계 | 에이전트 | 사람 |
|---|---|---|
| 원인 분석, 계획, 설계 | 수행 | 승인 |
| 구현, 정적 검증, 컴파일, 설계 대조 | 수행 | 결과 확인 |
| 개발 브랜치 병합과 개발 서버 빌드 트리거(Jenkins API) | 수행 | 배포 결과 확인 |
| 개발 서버 화면 검증 | 못 함 | 요청자가 확인 |
| 검수 브랜치 PR, 운영 배포 | 하지 않음(정책) | 수행 |

기준은 「되돌리기 쉬운가」와 「에이전트가 판정 근거를 가질 수 있는가」 두 가지였습니다. 개발 서버는 여러 사람이 공유하지만 되돌리기 쉽고, 빌드 성공 여부를 에이전트가 API로 확인할 수 있습니다. 화면이 요구를 충족했는지는 에이전트가 근거를 가질 수 없습니다. 운영 반영은 되돌리기 어렵습니다.

이 경계에서 자주 헷갈린 것이 하나 있습니다. 개발자가 「개발 서버에 배포했습니다」라고 댓글을 달면 승인처럼 읽히지만, 그것은 배포 실행 보고이지 화면 검증 결과가 아닙니다. 이 댓글에 상태를 전이하면 아무도 화면을 보지 않은 채 다음 단계로 넘어갑니다. 에이전트는 상태를 유지하고 요청자에게 확인을 요청합니다. 같은 댓글에 판정과 무관한 유용한 정보(예를 들어 배포 일정)가 섞여 오면, 판정은 보류하되 그 정보는 바로 산출물에 반영합니다. 사람이 같은 말을 두 번 하지 않게 됩니다.

그리고 못 한 것을 못 했다고 쓰는 편이 빠릅니다. 빌드와 화면 확인을 하지 못했다고 그대로 알리자 개발자가 곧바로 개발 서버 배포를 지시해 다음 할 일이 한 번에 정해진 적이 있습니다. 추정으로 통과시켰다면 문제는 더 늦게 드러났을 것입니다.

## 이미 구현된 요구를 받았을 때

### 만들지 않는 것이 지시를 따르는 것입니다

요구를 분석해 보니 이미 코드에 들어가 있는 경우가 있었습니다. 에이전트의 기본 충동은 「요청을 받았으니 만든다」입니다. 그러면 같은 조건이 코드 두 곳에 생기고, 나중에 한쪽만 고쳐졌을 때 원인을 추적할 수 없습니다. 「일반 화면에서만 적용하고 특정 화면은 제외해 달라」는 요구를 그대로 받아 제외 분기를 넣었다면, 이미 있는 제외 조건 위에 같은 조건이 한 겹 더 얹혔을 것입니다.

그래서 무변경(no-op) 결론에도 규칙을 뒀습니다.

1. 요구 항목마다 그것을 충족하는 코드 위치를 줄 단위로 적습니다. 「이미 되어 있습니다」 한 줄로 끝내면 확인하지 않고 넘긴 것과 구별되지 않습니다.
2. 조건부 차단이라면 막아야 할 것만 막혔는지 경계값과 인접 기능을 회귀 항목으로 세웁니다.
3. 변경이 0이면 개발 브랜치로 승격하지 않습니다. 작업 브랜치의 기준 브랜치에는 다른 사람의 커밋이 쌓여 있어서, 변경 없이 승격하면 그 커밋들만 이 이슈 이름으로 개발 브랜치에 들어갑니다.
4. 변경 전후 화면이 같으면 화면 비교 검증은 통과 기록만 남는 껍데기입니다. 생략하고, 생략했다고 적습니다.
5. 마지막 단계는 PR 요청이 아니라 배포 일정 확인입니다. 열 PR이 없으므로, 남은 종결 조건은 코드가 아니라 그 변경이 언제 운영에 실리는가입니다.

### 「반영됐는가」에는 서버마다 다른 답이 있습니다

무변경 이슈에서 에이전트가 여러 사이클 동안 같은 오판을 반복한 적이 있습니다. 선행 구현이 릴리스 브랜치 어디에도 없다는 사실을 근거로 「어느 서버에도 반영되지 않았다」고 기록했습니다. 그 사실 자체는 맞았지만 적용 범위가 틀렸습니다. 서버마다 배포 소스 브랜치가 다르고, 개발 서버는 개발 브랜치를 빌드합니다. 선행 구현은 개발 브랜치에 이미 있었으므로 개발 서버에서는 처음부터 확인할 수 있었습니다.

이 오판은 문서 정확도 문제로 끝나지 않았습니다. 에이전트는 「올릴 코드가 없는데 개발 서버 확인을 요청하는 모양이 된다」며 이슈를 멈추고 사람을 부르는 쪽을 검토하고 있었습니다. 잘못된 배포 판정은 이슈를 멈추게 합니다.

규칙은 단순합니다. 「반영됐는가」를 물으면 「어느 서버에」를 먼저 정합니다. 확인은 명령 하나로 됩니다.

```bash
# 구현 커밋을 포함한 원격 브랜치 목록이 곧 서버별 답입니다
git branch -r --contains <구현 커밋>
```

결과를 서버와 브랜치의 표로 만들어 산출물에 남깁니다.

## 사람이 직접 처리한 것과 비교하기

### 자연 대조군

자동화의 효과를 재려면 같은 일을 사람이 했을 때와 비교해야 하는데, 처음 시도는 비교가 성립하지 않았습니다. 이유는 세 가지였습니다.

- 다른 개발자의 대화형 세션 기록은 각자의 노트북에만 있어서 사람 쪽 작업 시간을 모을 수 없었습니다.
- 에이전트가 사람 계정으로 Jira에 쓰고 있어서 사람과 기계의 활동을 가를 수 없었습니다.
- 사람이 처리했다고 고른 표본 중 일부가 실제로는 에이전트가 처리한 것이었습니다.

둘째는 에이전트가 전용 계정으로 쓰게 바꿔 해결했습니다. 그리고 비교에 좋은 표본이 우연히 생겼습니다. 같은 요구가 두 번 접수돼서 한 번은 사람이, 한 번은 에이전트가 처리한 경우입니다. 요구, 요청자, 담당자, 작업 성격이 모두 같고 처리 주체만 다릅니다. 같은 단계에 도달한 시점까지를 같은 규칙으로 쟀습니다.

### 무엇은 믿을 수 있고 무엇은 믿을 수 없는가

- **리드타임과 착수 지연은 왜곡이 적습니다.** 양쪽 모두 이벤트 타임스탬프로 직접 측정되기 때문입니다.
- **리드타임 단축의 대부분은 작업이 빨라진 것이 아니라 대기가 사라진 것입니다.** 사람 처리분은 접수 후 한참 동안 그 이슈를 위한 작업이 없다가 배포 일정에 맞춰 한꺼번에 처리됐습니다. 에이전트는 이슈가 처리 대상으로 올라오면 다음 폴에서 착수합니다. 그래서 「개발이 몇 배 빨라졌다」가 아니라 「대기가 사라져 같은 일이 훨씬 일찍 확인 대기 상태에 도달했다」고 써야 정확합니다.
- **사람 쪽 공수는 하한만 잴 수 있습니다.** 커밋 시각은 일이 끝난 시점만 남기므로 조사, 설계, 코딩 시간이 통째로 빠집니다. 커밋 간격이 유휴 임계를 넘으면 활동 구간이 0으로 잡히기도 합니다. 작업 시간 자기신고도 비어 있었습니다. 사람 쪽 분자가 과소 계상되므로 이 값으로 절감률을 말하면 안 됩니다.
- **기계 쪽 축은 폴러의 실행 기록만 씁니다.** 세션 기록 축에는 사람의 대화형 세션이 섞여 기계 시간이 부풀었습니다.
- **봇 계정 분리를 빼면 결론이 뒤집힙니다.** 에이전트가 남긴 댓글과 전이를 사람 활동으로 세면 「자동화했더니 사람 손이 더 많이 들었다」는 반대 결론이 나옵니다.

자동화에 유리한 편향도 함께 적어야 합니다. 대조 쌍 하나는 앞 절의 무변경 이슈였으므로 구현 시간이 자동화 쪽에 아예 계상되지 않았습니다. 다른 하나도 사람이 먼저 만든 구현을 넓히는 작업이라 대상 지점이 이미 특정돼 있었습니다. 그리고 자동화 쪽은 최종 확인 단계에서 사람을 기다리고 있었으므로, 사람 쪽에 온전히 들어 있는 검수 왕복이 아직 빠져 있었습니다.

### 쓰지 않기로 한 표현

보고서를 쓰면서 숫자보다 표현을 고르는 데 시간이 더 들었습니다. 이 에이전트에 대해서는 다음 표현을 쓰지 않기로 했습니다.

- 「사람보다 빠르다는 사실을 입증했다」: 대조 표본이 너무 적습니다.
- 「공수를 몇 퍼센트 절감했다」: 사람 쪽 값이 하한입니다.
- 「사람 개입 없이 완료했다」: 확인 지점과 운영 반영은 사람이 맡았습니다.
- 「토큰 비용을 몇 퍼센트 줄였다」: 절감 전후를 같은 조건으로 잰 표본이 없습니다.
- 「설계대로 구현했으므로 품질이 확보됐다」: 설계 대조율은 설계대로 만들었는지를 잰 값이고, 요구를 충족했는지는 별개입니다. 설계와 구현이 잘 맞았는데 검수에서 여러 번 되돌아간 이슈가 실제로 있었습니다.
- 비용 수치를 「지출」로 쓰기: 구독 세션의 사용량을 종량제 단가로 환산한 값이지 실제 청구액이 아닙니다.

대신 원자료를 그대로 씁니다. 백분율 하나보다 「기록된 단계 이동 중 몇 번을 시스템이 처리했는가」처럼 분자와 분모가 보이는 문장이 낫습니다.

## 정리

8편에 걸친 시리즈를 마치며 운영에서 남은 것을 모읍니다.

- **리포트는 스스로를 의심해야 합니다.** 로그를 못 읽었을 때 전부 0을 내지 말고 무효라고 말하게 합니다. 짧은 대조 경로를 남겨 두고, 경고에는 관측 사실만 씁니다.
- **검증의 경계는 환경이 정하고, 배포의 경계는 되돌릴 수 있는가와 판정 근거를 가질 수 있는가가 정합니다.** 하지 못한 검증은 하지 못했다고 씁니다.
- **만들지 않는 것도 결론입니다.** 이미 구현된 요구는 충족 위치를 줄 단위로 적고, 승격하지 않고, 배포 판정은 서버 단위로 냅니다.
- **사람과 비교할 때는 무엇이 왜곡 없이 재지는지부터 가립니다.** 이벤트 타임스탬프는 믿을 수 있고, 커밋 기반 공수는 하한입니다. 사람과 기계의 계정을 가르지 않으면 결론이 뒤집힙니다.

돌아보면 운영 중에 고친 결함 상당수는 기능이 아니라 측정에 있었습니다. 에이전트가 일을 잘하는지는 측정이 맞아야 알 수 있고, 측정이 틀리면 에이전트가 잘하는지 못하는지도 알 수 없습니다. 상주 에이전트를 만든다면 기능만큼 원장과 리포트도 공들여 설계하는 편이 좋습니다.
